# Inline Remote Desktop Reconnect

## Problem statement

An iOS-to-desktop remote session becomes terminal when its local transport fails. The desktop closes the QR invitation listener, while iOS discards the scanned invitation. A temporary Wi-Fi or Airplane Mode interruption therefore requires a new QR scan.

## Solution summary

Keep the desktop listener and its signed invitation for the active host-session intent. After a verified QR connection, save the controller ID and the exact full invitation on iOS. On transport loss, show `Reconnecting`, keep the background session alive, and retry only that invitation on Wi-Fi or Ethernet. Do not use multicast discovery, an extracted IP address, or any fallback endpoint.

## Detailed technical design

- The Haskell host supervisor owns one listener and invitation until a local stop, an authenticated remote stop, deletion, fatal initial setup error, or app shutdown.
- A transport loss changes the host state from connected to connecting, closes only that TLS/HTTP2 transport, and waits on the same listener.
- Each new handshake must match the paired mobile identity fingerprint before reverse HTTP2 starts.
- `connectRemoteCtrl` starts a cancellable dial and returns its session sequence without waiting for the dial to complete. `/_abort remote ctrl <sessionSeq>` silently detaches the matching controller session in any state; the coordinator uses it for a rejected attempt. `/_drop remote ctrl <sessionCode>` closes only the matching connected transport.
- iOS stores one atomic `{remoteCtrlId, invitation}` value only after session verification succeeds.
- iOS changes to reconnecting on the network-path event. It retries only on Wi-Fi or Ethernet. It tries immediately, then waits 1, 2, 4, 8, and 10 seconds between attempts; later waits stay at 10 seconds. It resumes after chat start or app activation and never retries on cellular.
- iOS allows one controller connection request at a time after QR entry or controller confirmation. Generation and session-sequence checks reject stale results and events. A late successful request that lost ownership is aborted by its exact sequence.
- Automatic reconnect verifies the saved paired identity without a user prompt and creates fresh TLS and session keys.
- The UI uses connecting, pending-confirmation, connected, and reconnecting states without presenting a stopped alert during a retained retry.
- The macOS UI serializes remote-host state and selection changes. It correlates host-session lifecycle events that carry a session sequence. Successful Stop and Delete record a tombstone so that late events cannot restore the host or override a later selection.
- With an active authenticated transport, an explicit iOS disconnect sends the encrypted `remoteCtrlStopped` event before TLS closes. The desktop treats that event as terminal and closes the retained listener. A macOS Stop sends the authenticated encrypted `/_stop remote ctrl` command; iOS reports `controllerStopped` and clears its retry target. A raw transport close remains reconnectable.
- Without a transport, a local iOS Disconnect or macOS Stop clears only that app's session intent because it cannot notify the peer. iOS needs a local Disconnect to stop retrying; macOS needs a local Stop, Delete, or app shutdown to close its listener.
- Chat suspension silently detaches the iOS transport and preserves the retry target. Database deletion clears the target.
- This design covers transport reconnection during one desktop process lifetime. It does not persist the desktop invitation private keys across a desktop restart.
- Both peers require remote protocol version `7.1.0.0` or later for these semantics.

Threat model: only a successfully verified controller can create a saved reconnect target. A reconnect accepts the original signed invitation and the stored paired identity only. An unpaired client can consume a handshake attempt but cannot replace the paired controller. No alternate address or discovery result can redirect a retry.

## Detailed implementation steps

1. Add a host-session regression test that reconnects with the exact invitation after forced TLS loss.
2. Retain the host listener in `Remote.hs` and preserve a connecting state across transport loss.
3. Synchronize explicit stops over the active encrypted transport in both directions.
4. Persist and retry the verified full invitation in the iOS controller.
5. Keep the iOS sheet, background keepalive, and desktop host row consistent with reconnecting state.
6. Update `apps/ios/product/`, `apps/ios/spec/`, `apps/multiplatform/product/`, and `apps/multiplatform/spec/` for PC27.
7. Run the remote handshake tests, Swift build, Kotlin desktop compile, and physical-device builds.
