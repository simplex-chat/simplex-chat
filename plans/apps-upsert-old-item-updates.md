# Apps: an update of an earlier message is shown as a new message

## Problem

When the core reports an update of a chat item (`ChatItemUpdated`, file status events, delivery statuses, deletions that keep the item), both apps pass it to `upsertChatItem`. If the item is not among the items loaded in the open chat, `upsertChatItem` adds it at the bottom of the chat and reports it as added:

- Kotlin `ChatModel.ChatsContext.upsertChatItem`: `addToChatItems(cItem)`, `itemAdded = true`; for `ChatItemUpdated`, `chatItemUpdateNotify` then shows a notification (`ntfManager.notifyMessageReceived`), subject to `allowedToShowNotification()` or the chat not being open.
- iOS `ChatModel.upsertChatItem` / `_upsertChatItem`: inserts the item at the bottom, and for the open chat also replaces the chat preview with it; for `ChatItemUpdated` and file events, `chatItemSimpleUpdate` then adds a notification.

So an update of an old message, for example an edit, a moderation, a file status change, a delivery status change, or the "file was sent before you connected to the sender" marker from #7638, makes that old message appear at the bottom of the open chat (until it is reopened) and become the chat preview on iOS. Edits and the #7638 marker (`ChatItemUpdated`) also show a notification with the item's text on both platforms. File status changes reported by file events do so only on iOS (Kotlin `chatItemSimpleUpdate` never notifies); file errors and resets reported as `ChatItemUpdated` do so on both platforms. Moderation, deletions and delivery statuses never notify.

## Why the item is added at all

`ChatItemUpdated` can also report a new item: when an update arrives for a message the user never received (for example a live message whose first message was not received, or a message deleted locally), the core creates the item and reports it with `ChatItemUpdated` (`messageUpdate` and `groupMessageUpdate` in `Subscriber.hs`). Adding and notifying is correct for such items.

## Change

Chat item IDs only grow, so an item created by an update is newer than every other item in the chat, and an update of an earlier message is not. `upsertChatItem` on both platforms adds an item that is not loaded only if:

- the newest items of the chat are loaded: there are no `chatState.splits`, or the last split is not the ID of the last loaded item. Splits are ordered from the top of the chat to the bottom (`ChatItemsLoader` on both platforms), so the last one is the bottommost. The check is written inline on both platforms: iOS `ItemsModel.lastItemsLoaded` and Kotlin `lastItemsLoaded` in `ChatView.kt` (private) compare the first split, which is the bottommost only while there is at most one split, and
- its ID is greater than every loaded item's ID and, for an item of the main chat, not less than the chat preview's item ID. The preview's item itself can be missing from the loaded items when it was received while the first page was being read: it then is the newest item and is added. Only the loaded items bound the ID of an item of a member support chat. Such items update the preview only for a pending member (`addChatItem`), and `upsertChatItem` does not compare with it; that is harmless, because the support chat's loaded items bound the ID as for any other member support chat.

Otherwise the item is not added, and the update is kept until the item is added or loaded (below). On iOS the open chat's preview is replaced by an item that is not loaded only by the same rule.

While the newest items are not loaded (the chat was opened at the first unread item, or after a jump to a quoted or found item), neither the loaded items nor the preview bound the IDs of the items that are not loaded: in groups the preview is the item with the latest timestamp, not the highest ID, and after the last item is deleted the preview is a placeholder with ID -1. Once a new item is added at the bottom, the newest items count as loaded again; that is safe, because every earlier item has a lower ID than the new item. The same check applies to member support chats and reports, which use their own loaded state.

Updates of items that are not added or loaded yet. An update can reach `upsertChatItem` before the item it updates is in the loaded items:

- Send response, both platforms: the core can report a status change or a file status change of a message the user has just sent before the app adds that message from the send response. If a message received in between (`NewChatItems`) was added first, it has a higher ID; while the newest items are not loaded, no such message is needed.
- Android and desktop: `NewChatItems` is handled in a background coroutine (`withBGApi`), while `ChatItemUpdated`, `ChatItemsDeleted` with a changed item, statuses and file events are applied in order on the main thread. So an edit, a moderation, a deletion mark, a status or a file status of a message that has just been received can come before the message is added. iOS handles events in order.
- Page loads, both platforms: `ChatItemsLoader` reads a page from the database in the background and merges it on the main thread, so an update of an item of that page that arrives in between is applied to neither.

So when `upsertChatItem` does not add an item that is not loaded, it keeps the update by item ID (Kotlin `ChatsContext.droppedUpdates`, iOS `ItemsModel.droppedUpdates`), whatever the direction of the item. A later kept update of the same item replaces it, and keeps the earlier status when `shouldKeepOldSndCIStatus` prefers it, as for a loaded item.

- `addChatItem` adds the kept item instead of the item it got when the kept item's `updatedAt` is not earlier. Every event about an item is read from the database after the item was created, status and content changes set `updatedAt`, and file status changes do not change it, so the kept item is the newer state. Otherwise (only when the clock went back) it adds the item it got with the kept status when `shouldKeepOldSndCIStatus` prefers it. So the send response does not replace a kept status (`SndSent`, `SndRcvd`) or file status with `SndNew` and the initial file status, and on Android and desktop `NewChatItems` does not replace an edit, moderation or deletion mark that came first.
- When `ChatItemsLoader` merges a page (all pagination kinds), it replaces a loaded item by its kept update only when the kept item's `updatedAt` is later: an update kept before the page was read is already in the page. A file status change kept while the page was read does not change `updatedAt`, so the page shows the older file status until the next file event of that item.
- A kept update is removed when `addChatItem` adds its item or a merged page contains its item. It stays when `upsertChatItem` adds its item or a chat is shown from items that are already loaded (Kotlin `openLoadedChat`); that is harmless, because a merged page applies only a kept update that is newer than the page's item.

The kept updates are of one chat only: they are cleared when an update of another chat is kept (on Android and desktop, also of the same chat of another remote host). Member support chats and reports have their own (`secondaryChatsContext`, `secondaryIM`). Kept updates of a chat that is no longer open stay until an update of another chat is kept, and they are applied only to the chat and database they were kept for: `addChatItem` and page merges apply them only to items of the same chat (and remote host), and they are cleared when the database is deleted (also by the self-destruct passcode and migration) or imported, and on Android and desktop when the remote host is switched (`ChatModel.clearDroppedUpdates`). At most 100 updates are kept; above that, the one with the lowest ID is removed, because the items that are still to be added are the newest. Most kept updates are of items above the loaded part of the chat, for example receipts or edits of old messages; they are removed when that part is loaded, and are not applied because the page already has them.

`addChatItem` otherwise is unchanged: on iOS it calls `_upsertChatItem` with `add: true`.

Not changed:

- A chat that is not in the chat list is still added with the item, as before: without its last item the app cannot tell whether the item is new.
- Android and desktop still notify for every `ChatItemUpdated` of a user that is not active (iOS does not).
- Live message placeholders have negative IDs (`-2`) and do not affect the comparison.
- If the user sends a message after the core created an item from an update but before the app received that update, the created item is no longer newer than every loaded item, so it is shown only when the chat is reloaded, without a notification. An item created from an update while the newest items of the chat are not loaded is likewise shown when they are loaded, without a notification. Only the core reporting such items as new items (`NewChatItems`) would close this; that is a core change.
- In groups, items are loaded in the order of their timestamps (`item_ts`), not their IDs. A message received late, for example while catching up after being offline, when members' messages arrive in any order, can be placed above more than a page of messages with later timestamps, and still have a higher ID than every loaded item and the preview. An update of it is still added at the bottom while the newest items are loaded. Only the core change above would remove this.
- While the user writes a live message, its placeholder is the last item, so the newest items count as loaded, as they do for `ChatView`, and only the ID rule applies.
- In the chat list, the preview shows the item as the send response or `NewChatItems` reported it, not a kept update, as before, until the next update of that item.
- iOS: when a status or file update of a message that has just been sent comes before the send response and adds the message (it is the newest item and the newest items are loaded), the send response then updates the message in place: its status is kept by `shouldKeepOldSndCIStatus`, but its file status from the send response replaces the newer one until the next file event, as before. Android and desktop do not change an item that is already loaded when it is added.
- Android and desktop: when an update of a message that has just been received comes before `NewChatItems` and adds the message (as above), `ChatItemUpdated` shows a notification and `NewChatItems` shows another one, as before.
- Until a chat is the open chat (`chatId`), updates of its items are neither applied nor kept, so an update that arrives while the chat is being opened can be missing from its first page until it is reopened, as before.
- Only updates are kept, not deletions (`ChatItemsDeleted` without a changed item): on Android and desktop a message that is deleted before `NewChatItems` adds it is still added, and an item deleted while a page is read stays in the merged page on both platforms, until the chat is reopened, as before.
