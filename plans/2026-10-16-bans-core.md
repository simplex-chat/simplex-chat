# Bans and chat actions: core (PR 1)

Haskell only. UI is planned in plans/2026-10-16-bans-ui.md.
Design: plans/2026-10-16-moderation-ux.html.
Line numbers refer to branch ep/link-notices at a503e09ef.
The branch's own changes: `git diff origin/master...HEAD`.

## Scope

- notice on rejoining or reconnecting in x.grp.mem.del and x.direct.del
- silent removal and deletion, per role
- timed blocks: end time in x.grp.mem.restrict, applied by receivers
- automatic unblock message when a timed block ends, sent by the app that set the block
- block items and placeholders shown only to admins and moderators
- deletion with a notice for contacts and business chats ("Delete and ban" in the UI)
- moderators can block members pending approval or review
- archive without clearing, for contacts including deleted ones
- keep conversation when an owner deletes a group, channel or business chat
- CLI commands, view output, tests, protocol doc, generated API docs and types
- removal of the old-design app changes on the branch

## Terms

This plan uses the code's terms. UI text says "ban" for both.

Block: the ban while the member is in the group (UI: "Ban member", "Lift ban"):
- x.grp.mem.restrict with an optional end time; code: `blockedByAdmin`, `APIBlockMembersForAll`, `/block for all`
- hides the member's messages from members below moderator
- ends at its end time, when unblocked, or when the member leaves
- does not prevent rejoining: a rejoining member is a new member record with a new member ID (host: random ID, or the joiner's ID only if unused, Store/Groups.hs:2093-2103, 2107-2110; joiner: new membership ID, Store/Groups.hs:659-662)
- a block stored without an end time (set before the upgrade, received while on version 22 or earlier, or introduced by a host without one) lasts until it is unblocked or the member leaves; the automatic unblock does not end it on version-23 receivers

Notice: the ban at removal or deletion (UI: "Ban and remove", "Delete and ban", the "Not allowed" alert):
- `LinkNotice` in x.grp.mem.del or x.direct.del, stored in link_notices; prevents rejoining or reconnecting via the link the receiver used, for its duration counted from the removal
- independent of any block: "Ban and remove" and "Delete and ban" send a notice and no block
- does not apply to members and contacts on older versions: they ignore the notice (stable Protocol.hs:1434, 1459), the sender refuses a notice for them (APIRemoveMembers and APIDeleteChat errors), and the UI offers no notice for them (moderation-ux.html:598)

## Protocol

### Version

- linkNoticeVersion and currentChatVersion are 23, set in the master merge of 2026-10-20: v7.1.0-beta.7 was released with version 22 (groupInvVersion) and without notice handling
- if master releases version 23 first, both become the next version, with the "9-23" strings in ProtocolTests.hs and the docs version statement updated

### LinkNotice

- type: `LinkNotice {ttl :: Maybe Int64}` (Protocol.hs:315-321)
- `reason` field removed; a later version can add it as an optional key without a version bump, as unknown keys are ignored by the parser
- `ttl` is seconds counted from the server timestamp of the message that includes the notice
- `ttl` absent: no end time
- JSON: `{"ttl": 86400}`, or `{}` for no end time
- removed with `reason`: `ToField`/`FromField ReportReason` (Protocol.hs:311-313), the `"illegal"` alias (Protocol.hs:298) and its test (ProtocolTests.hs:284-286), all added by the branch
- the core alias is removed; the apps' ReportReason rename was restored by 5c6a25920: the apps encode `"content"` and decode both `"content"` and `"illegal"` as content (iOS ChatTypes.swift ReportReason, Kotlin ChatModel.kt ReportReason); master apps encode `"illegal"` and decode `"content"` as an unknown reason

### Silent and notice

- protocol: `silent` and `notice` are independent keys in x.grp.mem.del and x.direct.del
- API: a notice is always sent with `silent` (APIRemoveMembers, APIDeleteChat), as the UI offers only the combined action

| silent | notice | removed member or contact | other members |
|---|---|---|---|
| no | no | as today | as today |
| no | yes | as today, notice stored | removal item |
| yes | no | quiet path | no item |
| yes | yes | quiet path, notice stored | no item |

- exception: a removed member that forwards messages processes its removal as today (see Receiving, x.grp.mem.del)

### x.direct.del

- unchanged from the branch: `XDirectDel :: Bool -> Maybe LinkNotice -> ChatMsgEvent 'Json` (silent, notice)
- older apps parse x.direct.del without params (stable Protocol.hs:1434) and show the deletion; the sender refuses a notice for them

### x.grp.mem.restrict

- `MemberRestrictions {restriction :: MemberRestrictionStatus, expiresAt :: Maybe UTCTime}` (Types.hs:1152-1155)
- `expiresAt` is set by the sender to the current time plus the chosen duration; absent: no end time
- JSON derived as today (Types.hs:2394); `defaultJSON` omits `Nothing` (simplexmq Parsers.hs:153); older parsers ignore the key and keep the restriction until the unblock message
- x.grp.mem.intro includes it through `memberRestrictions` (Types.hs:1157-1160, Internal.hs:1271-1275), which sets `expiresAt = blockedUntil m`
- automatic unblock message: `restriction` unrestricted with the `expiresAt` of the ended block; an explicit unblock has no `expiresAt`

### End time bound

- `capExpiry :: Maybe UTCTime -> Maybe UTCTime`: `fmap (max minExpiry) . mfilter (< maxExpiry)`, with maxExpiry year 10000 (extracted from Store/Shared.hs:1017-1018) and minExpiry 1970-01-01, exported
- the lower bound keeps rows readable: sqlcipher-simple writes a negative year as text that its parser rejects (Database/SQLite/Simple/Time/Implementation.hs:47-50, 125-127), and every member read includes the column
- used in `upsertLinkNotice`, in `xGrpMemRestrict` and createIntroReMember for received end times, and in `APIBlockMembersForAll` for the sent end time

## Security

- a notice applies only to the link this receiver used for this group or contact (Store/Shared.hs:991-1000); a sender can set a notice for a receiver only from its own address or group
- x.grp.mem.del: sender role admin or above and not below the removed member (Subscriber.hs:3736-3739), as today
- x.grp.mem.restrict: sender role moderator or above and not below the member (Subscriber.hs:3660), checked before the state check, so the forwarded no-op unblock path cannot be used by members below moderator to make relays forward their messages
- a notice in a forwarded removal is used only from a relay with a verified signature, so a host admin in a group without relays cannot forge a silent removal or a notice, with or without a key it introduced
- received end times are clamped to [1970, year 10000), so a malformed or negative value cannot make member rows unreadable
- a forwarder ignores silence for its own removal, so a notice cannot stop forwarding of the removal or keep a removed relay serving
- notice ttl: negative values give an end time in the past; `capExpiry` gives no end time from year 10000 on
- block `expiresAt` is set by the sender's clock; `capExpiry` bounds it on both sides, so the Postgres range and SQLite text comparison in `getExpiredBlocks` are not affected by five-digit years
- block `expiresAt` is inside the signed body in relay groups (XGrpMemRestrict_, Protocol.hs:1365), so a relay cannot shift it; the forward header is a separate element before the signed one (Protocol.hs:1040-1050)
- one notice per link hash (unique index), so repeated notices cannot grow the table
- silent removal: the removed member's messages are sent to nobody with a connection; members without one get pending rows or forwarded statuses, as for any member not yet connected (Internal.hs:2774-2792)
- an automatic unblock states the end time of the block it ends, so version-23 receivers ignore it and a late unblock cannot cancel a newer block; older receivers apply it as today
- a modified app can ignore a notice; enforcement is local by design
- notices are stored only in the app database; nothing is stored outside it
- blocks of pending members go to moderators only, or to nobody
- regular members store no chat item, no file and no message row for blocked members' messages, updates and file descriptions
- a blocked pending member cannot be accepted, so regular members never get it without the block
- the notice is inside the signed body in relay groups (requiresSignature, Protocol.hs:1358-1371); for forwarded removals the notice time base is the forward header's fwdBrokerTs, outside the signature (Protocol.hs:1040-1050, Subscriber.hs:3935); the base is the earlier of it and the receipt time, so a forwarder or server can only shorten a notice
- link_notices has no user_id: a notice received in a hidden profile is reported when another profile on the device plans to connect via the same link (see Open decisions)

Unchanged behaviour noted by the review:
- events of a blocked sender are not forwarded (Subscriber.hs:1004), including x.grp.leave, so members not connected to a blocked member do not learn that the member left
- a sender with the same role as the target passes the restrict check (Subscriber.hs:3660)
- in channels, applyAtRosterVersion ignores an owner-signed x.grp.mem.del at a stale roster version, and the notice with it (Subscriber.hs:3356-3377, 3687)
- a blocked member's edits of items received before the block are applied (Subscriber.hs:2325-2326, 2343-2359)
- a blocked member's reactions are stored and shown (Subscriber.hs:2128-2163)
- a directory service removed from a channel with a notice takes the silent path (it is a subscriber, Directory/Service.hs:959-976), so the channel stays listed (see Open decisions)
- moderators in a full-deletion group keep the content of a blocked member's update of an unknown item (Subscriber.hs:2302-2307), as for "block for all" today
- the blocked member's app receives x.grp.mem.restrict about itself from relays (Subscriber.hs:4262-4305) and, for a member pending review, from admins forwarding in the support scope (Subscriber.hs:4383-4391); it is ignored (Subscriber.hs:3651) but stored in messages until cleanup (see Open decisions)
- link_notices rows remain after the profile that received them is deleted, until they expire (see Open decisions)
- a member added by a direct invitation stores no notice, because the group has no link hash (Store/Shared.hs:993); such a member can join later via the group link
- once the host stores a pending member's block, forwarders stop forwarding that member's support-scope messages to moderators (Subscriber.hs:1004)
