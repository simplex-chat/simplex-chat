# Channel multi-owner — implementation plan

Companion to the design overview (`2026-07-15-channel-multi-owner.md`) — read that first for *why*. This covers *what to build*: data model, migrations, types, protocol events, commands, and sequencing. It is a map for implementing agents, not an exhaustive edit list; trivial wiring (JSON instances, `CMEventTag` cases, view strings) is implied.

The sequencer frame (overview §1) drives everything: link data and owner keys are sequenced by the SMP server via **hash-CAS** (the server keys on a content hash, not a version counter); the roster has no sequencer and converges by a deterministic blob tie-break plus owner-side auto-retry; the subscriber count is cosmetic and any owner corrects it on channel open. Each owner has **one key** — its member key is its `OwnerAuth.ownerKey`, its link-data signing key (the creator's link-data writes stay root-signed) and its link-queue recipient key — so the published owners chain is also the queue's key map.

## Sequencing

Two repos, in order. **simplexmq first** (the relay version bump, hash-CAS on the SMP link queue, the foreign-link write path, the creator's key rotation, forgetting a connection without `DEL`), then **simplex-chat** (data model, events, logic, apps). Multi-owner is gated on the link queue's server negotiating the new SMP relay version; below it, promotion is blocked, not degraded. Relays must accept channels with several owners a release before promotion is enabled (Part 8).

## Part 1 — simplexmq

### 1.1 SMP server — hash-CAS on the link queue

- **Version bump.** New `VersionSMP` `linkCasSMPVersion = 24`; bump **both** `currentClientSMPRelayVersion` and `currentServerSMPRelayVersion` 23 → 24 (`Transport.hs:228-232`). The negotiated session version is the *min* of the two peers' relay ranges, so the client constant must also advance for a client to perceive and exercise v24. `proxiedSMPRelayVersion` stays at 23 (`:241-242`): recipient commands are not proxied. This is the SMP *relay* version (`VersionSMP`, gating `Command`/`BrokerMsg` encoding) — **not** `currentSMPClientVersion`, which rides the client↔client envelope and gates nothing server-facing.
- **The CAS token is a content hash, not a counter.** For link data it is SHA-256 of the stored *encrypted* user-data bytes (nonce + ciphertext, exactly as uploaded — the only thing the server can key on, since it cannot read the content); for `recipientKeys` it is SHA-256 of the encoding of the sorted key set. The server stores `recipientKeys` sorted, so it and the owners hash the same bytes. No server version counters.
- **The CAS is atomic in both queue stores** (the journal message store uses one or the other, `MsgStore/Journal.hs:107-117`). STM store: compare inside the existing STM transaction (`addQueueLinkData`, `QueueStore/STM.hs:168-188`; `updateKeys`, `:200-206`). Postgres store, with or without its cache: an `UPDATE … WHERE` predicate for both — link data `… AND sha256(user_data) = ?` (the blob is not loaded on the normal path: `rowToQueueRec` uses empty placeholders, `QueueStore/Postgres.hs:726-730`), keys `… AND recipient_keys = ?` against the value just read — because the Postgres message store runs with no cache and a no-op queue lock (`MsgStore/Postgres.hs:84`, `:100`), so each command holds its own copy and an in-memory compare would let two concurrent writes both pass. A 0-row update reads and returns the current value.
- **Two new recipient commands** (`Command Recipient`, gated ≥ v24; new tags rather than extending `LSET`/`RKEY`, so version-gating is clean):
  - **`LSETH expectedHash linkId userData`** — hash-CAS on the user data only; the server keeps the stored fixed data. (`LSET` must resend the fixed data byte-identical, `QueueStore/STM.hs:178`, `QueueStore/Postgres.hs:319`, which a promoted owner cannot reproduce: encryption uses a fresh nonce and the read path keeps only the decrypted data.) If `hash(stored) == expectedHash`: store, reply `OK`. Else reply the current encrypted user data. The link-id check stays as in the `LSET` handler (`Server.hs:1575-1579`).
  - **`RKEYH expectedHash keys`** — hash-CAS replace of the key set (as `RKEY`, `Server.hs:1574`). Accept: store sorted, reply `OK`. Else reply the current set.
- **One new `BrokerMsg`** for a rejection, carrying the current value (user data or key set); success is the existing `OK`, and the writer computes the new hash itself. Returning current state on rejection is what removes the writer's pre-read.
- **Auth unchanged:** both are recipient commands, so any key in `recipientKeys` authorises them (`Server.hs:1289-1290`, `:1333-1334`) — this is what lets a promoted owner write. `recipientKeys` stays `NonEmpty` (the parser rejects a zero-length set), so an `RKEYH` can never empty the set; the server has no notion of owner/revocation, so "≥ 1 *live* owner" is a client-side concern (Part 5).
- **Tests** (`tests/ServerTests.hs`, for each queue store): two concurrent `RKEYH` adds both land after one retry; of two concurrent `LSETH`, one is rejected with the winner's blob; `LSETH` cannot change the fixed data; the new commands' AUTH timing matches the existing "Timing of AUTH error" tests.

### 1.2 SMP agent — hash-CAS APIs, foreign-link write, key rotation, local forget

- **Stateless hash-CAS APIs.** Chat keeps the hashes; the agent takes the expected hash and returns either `OK` with the new hash (computed from the exact ciphertext it uploaded — never by re-encrypting, since encryption uses a fresh nonce) or, on conflict, the decrypted current data with its hash. The agent never re-merges (merge policy is chat's). No new agent-store columns.
  - `setConnShortLinkCAS` — synchronous, on the device's own link queue.
  - **An async variant** of the agent's `LSET` command (`setConnShortLinkAsync`, processed at `Agent.hs:2255-2258`), because the creator's link writes mostly run asynchronously: on success the `LINK` event carries the expected hash the command was issued with and the new hash; on conflict a new event returns the expected hash, the decrypted current data and its hash, and chat reconciles and re-enqueues. (The expected hash is the `baseHash` the announcing event needs, overview §2; reading it from chat's state when the event arrives would be wrong after an intervening reconcile.)
  - `updateRcvKeysCAS` — `RKEYH` on the own queue.
  - A local read of the own link queue's recipient id, which the creator puts in the promotion `inv` (today it is reachable only through `getConnectionQueueInfo`, a `QUE` round-trip to the server).
- **Foreign-link path** — a promoted owner does not own the link queue. `setForeignLinkData`, `updateForeignRcvKeys` and `deleteForeignLinkQueue` (`DEL`, for destroying the channel) take **explicit credentials**: `SMPServer`, the link-queue recipient id (`linkRcvId`, delivered in the promotion `inv`; it is *not* derivable from the public short link, which yields only the sender-side `linkId`), the `LinkKey`, `rootPubKey`, the owner's member private key (it signs the user data and authorises the commands), and the expected hash. Validation builds the link credentials in memory with the root key set, so `validateOwners` checks that the signing key is a chain key (`Agent/Protocol.hs:1991-2001`) — no `rcv_queues` row and no stored `linkRootSigKey` (`AgentStore.hs:2903` keeps `Nothing` for the creator, whose signing key is the root). Prefer this over materialising a fake `RcvQueue`/`ContactConnection`, which would need an `rcvDhSecret` the owner must not have and risks it subscribing to the creator's queue. Reads use the existing `getConnShortLink`. Foreign calls are **synchronous**: an agent async command delivers its result to a connection, and a promoted owner has no link connection to receive it. They run on a transport session of their own, one per link (the default session is shared per user and server, `mkTSession`, `Agent/Client.hs:1442-1443`), so the link server cannot tie them to the owner's other queues.
- **Creator key rotation** — `setConnRcvAuthKey connId privKey` replaces the own queue's recipient key with the given one in three resumable steps: `RKEYH` adding the new key, persisting it as the queue's `rcv_private_key`, `RKEYH` dropping the old key. A rejected step returns the current set, from which the next step is decided.
- **Forget a connection without `DEL`** — a new local-only deletion; today every agent deletion path sends `DEL` (`deleteConnectionsAsync_`, `Agent.hs:1022-1030`).
- **`Crypto/ShortLink.hs`:** extract `mkOwnerAuth :: OwnerId -> PublicKeyEd25519 -> PrivateKeyEd25519 -> OwnerAuth` (an existing owner key — the promotee's member key — signed by the signer's private key); redefine `newOwnerAuth` on it; export (kills the formula duplicated in chat at `Internal.hs:1680`). The creator signs a new owner with the **root** private key (as `Commands.hs:2757` already does for itself), keeping the chain flat; a non-creator owner signs with its **own member** key (delegation). `validateLinkOwners` is **unchanged** — it accepts "signed by root or an earlier entry", which holds as long as chat writes the owners list in insertion (signer) order (Part 2), so no order-independence change is needed.
- **Tests** (agent): a conflict is returned on the sync and the async path, with the expected hash; a foreign-link write signed by a non-creator owner's key is accepted by a reader; a foreign `DEL` by a non-creator owner deletes the queue; the rotation completes after a crash between each pair of steps.

## Part 2 — simplex-chat: data model & migration

One migration `M20260721_channel_multi_owner` (register in `Migrations.hs` + `.cabal`, both SQLite and Postgres; `chat_schema.sql` regenerates from tests). All new columns nullable / defaulted, so `ALTER TABLE ADD COLUMN` is safe on the STRICT tables and remote-desktop JSON stays forward-compatible.

### `group_members` (columns)
| column | on which rows | purpose |
|---|---|---|
| `owner_auth_sig BLOB` | owners | chain entry signature (with the existing `member_pub_key` = the entry's `ownerKey`, this is the full `OwnerAuth`) |
| `owner_auth_index INTEGER` | owners | **insertion (signer) order** in the chain — a new entry is appended after the entry that signed it; load-bearing for `validateLinkOwners`, *not* a memberId sort |
| `relay_subscriber_count INTEGER` | relays | latest absolute count that relay reported |
| `relay_subscriber_count_ts TEXT` | relays | the relay's own timestamp for that reading (the freshness token; cleared with the count on `GSMemRemoved`/`GSMemLeft`) |
| `promote_invitation_id BLOB` | the promotee (invitee row on O1; own membership on M) | pending promotion |
| `promote_role TEXT` | ″ | offered role |
| `promote_status TEXT` | ″ | invited / accepted / key_added / entry_published / rejected / cancelled / expired — the step reached drives resume and the undo on cancel or expiry (Part 5) |
| `promote_link_rcv_id BLOB` | M's own row | link-queue recipient id (from `inv`) |

`MemberRoleProposal` (Part 3) is *derived* from `promote_*`, not a stored column.

### `groups` (columns)
| column | purpose |
|---|---|
| `link_data_hash BLOB` | the hash this device holds for the published link data — the value it CASes on (from its accepted writes, rejections, and events whose base hash matched) |
| `key_set_hash BLOB` | last known key-set hash |
| `published_relays BLOB` | the last published relay list this device knows (from reconcile, accepted writes, and adopted events); a write's relay list is this plus the owner's own in-progress additions minus its own removals (Part 6). `NULL` until first filled: a promoted owner reads the link data to fill it before its first write |
| `stored_roster_owner_id BLOB` | cross-device author `memberId` of the **stored roster blob**, written beside `stored_roster_version` only by `setGroupLiveRoster`; the tie-break key (supersedes the device-local `roster_sending_owner_gm_id` for comparison) |
| `link_rcv_id BLOB` | for this user as a non-creator owner: the link queue's recipient id. With the server and `LinkKey` from the channel link and the existing `root_pub_key` and `member_priv_key` columns, it completes the foreign-link credentials (the creator keeps `GroupKeys` unchanged) |

Do **not** add a `roster_version_owner_id` on the gate `roster_version` — the delta path (`setGroupRosterVersion`) must advance the gate *without* writing any blob author, or a delta would corrupt the blob tie-break (Part 6).

### `group_revoked_owners` (new table)
`(group_id, member_id, member_key, key_drop_enforced, removal_step)` — on every member's and relay's device, one row per revoked owner. It lives outside `group_members` because member cleanup deletes a removed channel member's row a day after removal when it has no chat items (`deleteOrUpdateMemberRecordIO`, `Internal.hs:2192-2203`; `cleanupRemovedMembers`, `Commands.hs:5960-5966`; `getRemovedMembersToCleanup`, `Store/Groups.hs:1375-1382`). Rows come from `revokedOwners` at join and at relay invite, from link-data refresh, and from removal and leave events; they are never deleted.
- `member_id` — the replay record: `x.grp.owner.add` for it is ignored, a relay refuses an owner join for it, and promotion refuses it (Parts 4–6).
- `member_key` — the key the heal drops (`NULL` when this device never knew it).
- `key_drop_enforced` — false when the revocation was first seen in the link data and the key drop is not yet confirmed; true once confirmed, or once the removal/leave event arrived (it is sent after the key drop). Drives the heal (Part 6).
- `removal_step` — for a removal this device runs: revoked / key_dropped / announced, so a crash is re-driven at chat start.

### `group_pending_role_changes` (new table)
`(group_id, group_member_id, target_role, pre_role, roster_version, created_at)` — an owner's role changes not yet confirmed converged. Drives the roster auto-retry (overview §4): re-apply a row only while it is unsatisfied **and** the member still sits at `pre_role` in an *observed* roster (another owner's event or blob, or a relay-served blob — never this owner's own apply); **clear** the row as soon as an observed roster shows the member at `target_role` or at a role other than `pre_role` (this is what stops an old delta from resurrecting a value and ping-ponging with a legitimate later change).

### No pending-edit record for whole-value fields
Profile/prefs edits are synchronous and write-then-commit (Part 6), so nothing is stored while they are in flight. Owners and revoked owners merge as a union keyed by memberId; a relay this owner is adding or removing is already durable in its relay row.

### Published link data (not DB — chat's `GroupShortLinkData` JSON)
`GroupShortLinkData` (`Protocol.hs:1621`), carried in `UserContactData.userData`, gains optional fields — simplexmq's `UserContactData` encoding is unchanged: `linkDataVersion` (advisory ordering — recipients drop older events; correctness rests on the server hash-CAS and reconcile, so a corrupted value only degrades live-event ordering, never stored state), `revokedOwners :: [MemberId]`, and `subscriberCountTs` beside `publicMemberCount` in `PublicGroupData` (`:1616`). `group_revoked_owners` locally mirrors `revokedOwners`.

## Part 3 — new Haskell types

- **`MemberRoleProposal = MRProposed GroupMemberRole | MRRejected GroupMemberRole`** (`Types.hs`); `GroupMember` gains `memberRoleProposal :: Maybe MemberRoleProposal` (derived from `promote_*`) and the app-facing `promotionPending :: Bool`.
- **`PromotionRoleData`** for the wire: a role-tagged sum with an opaque fallback — `PRDOwnerInv { linkRcvId }` / `PRDUnknown` (decode an unrecognised tag to `PRDUnknown`, do **not** error — `omittedField` only covers an *absent* field, not a present unknown one).
- **`ForeignLinkKeys`** — the input to the Part 1.2 foreign-link APIs: `SMPServer`/`linkRcvId`/`LinkKey`/`rootPubKey`/member private key, assembled from `groups` columns, plus the expected hash.
- **`GroupLinkWriter = GLWOwn Connection GroupLink | GLWForeign ForeignLinkKeys`** — resolved once per link write (Part 6).
- Reuse: `OwnerAuth` (simplexmq), `MemberId`, `MemberKey`, `VersionRoster`.

## Part 4 — new protocol events (`ChatMsgEvent`, `Protocol.hs`)

All `requiresSignature`. Wire is JSON with optional-field forward-compat (`.=?` / `opt`).

| event | dir | fields | delivery |
|---|---|---|---|
| `x.grp.promote.inv` | O1→M | `invitationId, memberRole, roleData?` (`roleData` = `PRDOwnerInv{linkRcvId}`) | M's support scope |
| `x.grp.promote.acpt` | M→O1 | `invitationId, memberKey, roleData?` (none for owner) | support scope |
| `x.grp.promote.reject` | M→O1 | `invitationId` | support scope |
| `x.grp.promote.cancel` | O1→M | `invitationId` | support scope |
| `x.grp.owner.add` | owner→all | `memberId, ownerAuth` (+ the link-data hash fields below) | `DJSGroup` — all members and relays |
| `x.grp.relay.count` | relay→owners | `count, ts` (the relay's own clock) | sent directly to owners, as the relay sends the join announcement (`introduceInChannel`, `Internal.hs:1320-1326`) — not a `DJSGroup` job, which would fan out to every member |

`memberKey` in `acpt` is M's existing key; O1 checks it **equals the key it already holds for M** and adds the key it holds (a consistency check, distinct from the advisory OOB verification in Part 7).

**`x.grp.owner.add` is the promotion commit.** A member or relay applies it only if its sender (the message signer) is a current owner, `memberId` is not in `group_revoked_owners`, `ownerAuth` validates — signed by the stored root key (`root_pub_key`) or by a current, non-revoked owner's key — and `ownerAuth.ownerId` is `memberId`; it then sets the member's `member_pub_key` to `ownerAuth.ownerKey` (logging a warning when a relay-asserted key differs), creates the member if unknown, and sets its role to owner. M, receiving it for itself, becomes owner (Part 6). It is a new event rather than `x.grp.mem.role … GROwner`, which would apply the role to a relay-asserted key (`Subscriber.hs:3465-3468`) and never create an unknown owner (`:3458`); clients that predate it ignore it and keep rejecting the new owner's admin messages (Part 8). The sender check stops a removed owner reinstating itself with its own still-valid root-signed entry; the revoked check stops a relay re-delivering an old add. `group_revoked_owners` survives member cleanup (Part 2), and a revoked memberId is never promoted again (Part 5), so no version gate is needed — which would also drop adds that relays merely reordered. On receiving `x.grp.owner.add`, a relay sends the new owner its current `x.grp.relay.count` reading.

Additive: `linkDataVersion`, `linkDataBaseHash` and `linkDataHash` become optional fields on the events that announce link-data writes — `XGrpInfo`, `XGrpRelayNew`, `x.grp.owner.add`, and `x.grp.mem.del` of an owner — present only when the event describes its write's entire change (a write that activates several relays at once carries none). Order: write first (`LSETH`), then broadcast. A receiving owner adopts `linkDataHash` into `link_data_hash` only when `linkDataBaseHash` equals the value it holds (overview §2); otherwise it applies the content and keeps its hash.

The roster tie-break needs **no wire field** — the author is the message signer (`withAuthor`), already available at the completion gate; store its cross-device `memberId` in `stored_roster_owner_id` at completion and compare there.

The new events are added to the relay forwarding set (`isForwardedGroupMsg`, `Protocol.hs:528`) and the relay's dispatch, or relays silently drop them.

## Part 5 — commands (`ChatCommand`, `Controller.hs`)

- **`APIAcceptRolePromotion GroupId`** — M sends `acpt`, marks accepted; the async chain (overview §6) then runs on O1. M holds at most one pending promotion: an `inv` received while one is pending is answered with `reject` automatically. M's record clears on `cancel`, when the inviter is revoked, and — only until M accepts — on its own TTL; after acceptance it holds `promote_link_rcv_id`, which the commit needs.
- **`APIRejectRolePromotion GroupId`** — sends `reject`, clears.
- **`APICancelRolePromotion GroupId GroupMemberId`** — O1 sends `cancel`. If the chain already added M's key (`promote_status` `key_added`), it drops the key with `RKEYH`; if the entry was published (`entry_published`), it also revokes M (the removal chain below); then clears the proposal. The same undo, followed by `cancel` to M, runs when the inviter's record expires. Both sides' records (M's only before it accepts) expire after a fixed TTL in `ChatConfig`, checked at chat start (with the re-drive of pending records) and by a per-user step in the periodic cleanup manager (`cleanupUser`, `Commands.hs:5922-5933`) — not by the relay-request pattern, whose TTL is checked only on a temporary error inside its own worker (`retryTmpError`, `Subscriber.hs:4554-4559`), which an invitation waiting on a person never reaches.
- Route **`APIMembersRole … GROwner`** on a channel into the invite flow — single-target (reject a multi-member owner promotion, as the existing guards do: channel owner-role guard `Commands.hs:2994-2995`, multi-member admin guard `:2990-2991`). Before any key change the chain refuses a memberId in `revokedOwners` (its key would be added but its entry never written, since the merge excludes revoked memberIds) and checks that the link data still fits with M's entry added (user data is padded to 13,784 bytes, `ShortLink.hs:46`), refusing the promotion with a clear error otherwise. The creator's first promotion then rotates its link-queue key to its member key (Part 1.2).
- Route owner **removal** (`APIRemoveMembers` of an owner) into the removal flow (overview §7): an async command that writes the revocation **first** (`LSETH` adding the target to `revokedOwners`), **then** drops the key (`RKEYH`; the target's key is its chain entry's `ownerKey`), **then** sends `x.grp.mem.del`. Each `RKEYH`/`LSETH` payload is built by applying the delta to the server's *current* set/blob (the believed one, or the one returned on a conflict) — never rebuilt from the chain, which could drop a concurrently-added owner's key whose chain entry is not yet published. A crash between the steps heals via reconcile (Part 6). Refuse removing/leaving the last *live* owner (local `owners` minus `revokedOwners`); a stale view under concurrent leave+removal or mutual removal is an accepted, disclosed residual, not auto-healed.
- **Leave** (`APILeaveGroup`, `Commands.hs:3233-3253`) by an owner while another live owner remains: revoke itself (`LSETH`), drop its own key (`RKEYH`), then `x.grp.leave`. The creator then forgets its link connection without `DEL` (Part 1.2) instead of `deleteGroupLinkIfExists` (`Internal.hs:1739-1748`), which would `DEL` the shared queue. The same applies where the creator processes its own removal (`Subscriber.hs:3736`) and where an owner that is no longer current deletes the chat (`Commands.hs:1400`). Destroying the channel still deletes the queue: the creator through its link connection as today, and a non-creator owner, which has none, with `deleteForeignLinkQueue` (Part 1.2) — only in the branch where a current, non-revoked owner sends `x.grp.del` (`doSendDel`, `APIDeleteChat`, `Commands.hs:1394-1400`). `deleteGroupLinkIfExists` at `:1400` runs regardless of `doSendDel`, so the foreign `DEL` must not join it there: a removed owner whose key a crash left live would otherwise destroy the channel by deleting its chat.

The promotion and removal chains are async commands resumable from their durable records (the `promote_*` columns / `group_revoked_owners.removal_step`) — no new durable-worker type.

## Part 6 — key logic changes (anchors)

- **One writer for every link write.** Each link-write site resolves a `GroupLinkWriter` once: the creator's own link connection and group link, or a promoted owner's `ForeignLinkKeys`. Today every site needs the creator's group link row or link connection — `setGroupLinkData'` silently skips the write without one (`Internal.hs:1581-1586`, used by the profile edit at `Commands.hs:4190`), and `setGroupLinkData`/`setGroupLinkDataAsync` (`:1588-1604`), `updatePublicGroupData` (`:1624`), relay add (`Commands.hs:2790`) and relay connect/ack (`Subscriber.hs:946-947`, `:3663-3665`) throw. Foreign writes are synchronous (Part 1.2); a caller that is asynchronous today runs them in a thread, and its intent is already durable (relay rows, promotion records, `group_revoked_owners.removal_step`), so reconcile at chat start re-drives an interrupted one. The body of the `LINK` handler (`Subscriber.hs:1431-1481`: relay activation to `RSActive`, `XGrpRelayNew` to other relays, `CEvtGroupLinkDataUpdated`) becomes a function of the written data and the resolved writer — not a re-read of the group link (`Subscriber.hs:1439`), which a promoted owner has no row for — called from the `LINK` event and after a foreign write returns `OK`, which produces no `LINK` event.
- **`groupLinkData`** (`Internal.hs:1670`, self-only owners at `:1676-1682`) → build the write from local state via the **reconcile** routine; delete the `GRKPrivate` singleton / `[]` fallback; read the stored chain (insertion order). The relay list is `published_relays` (read from the link data first when it is still `NULL`) plus this owner's in-progress additions minus its own removals, and a write whose relay list is empty is refused unless this owner is removing the last relay — not only its own `group_relays` rows (`getPublishableGroupRelays`, `Store/Groups.hs:1528-1545`), which reference its own chat relays (`chat_schema.sql:840`) and are empty for a promoted owner. The count fields are the published `(publicMemberCount, subscriberCountTs)`, unchanged, except in the gated count publish.
- **Reconcile** = merge published link data into local, by field kind: owners and revoked owners merge as an idempotent union keyed by memberId, minus revoked entries no current entry depends on (dropped, below); relays: `published_relays` is replaced by the published list, and this owner's in-progress relay rows (being added and not yet published, or being removed) are kept; profile/prefs adopt the published value. Subscribers' link-data refresh (`updateGroupFromLinkData`, `Internal.hs:1634-1654`, today profile and count only; called only from `Commands.hs:1966`, `:4624`, `:4651`) also applies the chain: validated entries as owners (keys from `ownerKey`), `revokedOwners` into `group_revoked_owners`. Relays never call it; a relay applies the chain the same way in its periodic check, which already fetches the link data every 15 minutes (`checkRelayServedGroups`, `Commands.hs:6001-6020`), and at once when an owner join or `x.grp.owner.add` names a memberId it does not hold as owner — relays don't forward to each other, so an owner event from an owner not connected to a relay never reaches it otherwise. Run it **on channel open** (owners run `APIGetUpdatedGroupLinkData` like subscribers — remove the owner exclusion at `Commands.hs:1968` and the apps' owner branch, `ChatView.swift:764-779` and its Kotlin counterpart), **at chat start** for each channel the user owns (owners that never open the channel view — CLI, bots — still heal and publish the count), **on a CAS conflict** (adopt the returned blob, rebuild), and as the **missed-event backstop**.
- **Owner relay step** in reconcile, instead of `syncSubscriberRelays` (`Commands.hs:3992-4011`), which would delete this owner's relays that are not yet published and join other owners' relays as a subscriber: deactivate relays absent from the published data that this owner is not adding, and connect to relays other owners added by joining through the relay's link as itself, signed with its member key.
- **Relay accepts an owner's join.** In `memberJoinRequestViaRelay` (`Subscriber.hs:1690-1720`), an existing member is accepted onto its row only for roster roles (`:1702-1706`); any other existing member falls through to a fresh insert, which violates `UNIQUE(group_id, member_id)`. Add the owner case: an existing, non-revoked owner row plus a join signed with that owner's key, under the same `viaRelay` replay check as the roster branch (`verifyKey`, `:1711-1714`), is accepted via `acceptJoin` with the existing row and role owner; a memberId in `group_revoked_owners` is refused. Without it no owner can connect to a relay another owner added, so its posts never reach that relay's subscribers. On the owner's side, completing the join (the relay answers with `XGrpLinkInv`, handled for a `GCHostMember` at `Subscriber.hs:830-842`) updates only the relay member: `updatePreparedUserAndHostMembers'` (`Store/Groups.hs:821-844`) would replace the owner's group profile with the relay's copy and, unless the membership is `GSMemConnected` (the creator's is `GSMemCreator`), rewrite its membership role and status.
- **Profile edit** (`runUpdateGroupProfile`, `Commands.hs:4164-4204`) becomes write-then-commit: today it commits the profile locally (`:4172-4174`) before the synchronous link write (`:4190`). Keep the starting profile in memory; on a conflict, merge field by field against it — a field only this owner changed keeps its value, a field only the other owner changed takes theirs, a field both changed differently keeps the published value and is surfaced as "profile edit superseded" — then retry.
- **Removal heal** (runs during reconcile, and it is what makes the revoke-first ordering crash-safe): for each `group_revoked_owners` row with `key_drop_enforced` false and a known `member_key`, issue one `RKEYH` whose expected set is the believed set plus that key and whose new set is the believed set (on a conflict, the returned set shows whether the key is still there), then set `key_drop_enforced`. Merging `revokedOwners` into local state alone does *not* evict a still-live key; this explicit `RKEYH` is required. An owner that receives the removal or leave event sets `key_drop_enforced` directly — the event is sent only after the key drop — so only a revocation first seen in the link data (the crash case) costs a direct connection to the link server. A removal this device runs and that crashed is resumed from its `removal_step` at chat start, through the announcement.
- **Relay activation** stays on the `LINK` event (and, for a foreign write, its `OK`, through the extracted function above), which the agent emits only after the server accepted the write (`Agent.hs:2255-2258`); under CAS it follows the accepted `LSETH` and carries the data written after any re-merge. Relays another owner removed produce no `LINK` here (the TODO at `Subscriber.hs:1475-1477`); the owner relay step deactivates them.
- **Roster** (overview §4): the event gate stays **version-only, author-blind** (`applyAtRosterVersion`'s `fresh` check, `Subscriber.hs:3414`, `version >= held`), so concurrent *different-member* deltas both apply. The `(version, authorMemberId)` tie-break is added **only at the completion gate** (`Subscriber.hs:3572-3578`): keep the existing downgrade reject (`pendingVer < roster_version` gate) and, at the equal-version case that today overwrites by arrival order, accept iff `pendingVer > stored_roster_version` **or** (`pendingVer == stored_roster_version` **and** `author > storedAuthor`) — comparing the incoming blob's signer against `stored_roster_owner_id`, never the gate. Store the cross-device author with the blob in `setGroupLiveRoster` (`:3578`; `Store/Groups.hs:1716-1724`). A completed blob reverts privileged members absent from it (`processRosterEntries`, `Subscriber.hs:3610-3619`), so the losing owner's delta is reverted on relays until its retry. Applying any roster skips members who are currently owners (in `processRosterEntries`, `Subscriber.hs:3610-3630`, which today sets each listed member to its listed role, `:3601-3608`, `:3622-3628`): a member promoted to owner from a roster role stays in relays' stored blob, which a later joiner receives right after its owner intros (`Internal.hs:1330-1331`), and would otherwise be set back. **Relay setup under concurrent roster changes:** a roster ack below the owner's current version during relay setup re-sends the current roster to that relay (`sendGroupRosterToRelay`, `Internal.hs:2657-2662`) instead of only warning (`xGrpRosterAck`, `Subscriber.hs:3654-3667`) — another owner's delta can advance the version between send and ack, and this owner re-sends only when it bumps the roster itself (`broadcastRoster`, `Internal.hs:2642-2654`), so the relay would stay unpublished. **Retry**: when an observed roster shows a pending delta's member still at its pre-role, the owner re-applies its unsatisfied deltas to its local roster and sends blob + deltas at one above the highest version seen; both owners do this, so the served blob converges without waiting on any one owner. Existing members converge from the re-sent deltas (`DJSGroup` → all members). No leader, no relay-to-owner blob forwarding.
- **Count** (overview §5): `x.grp.relay.count` is produced by the relay branch of `updatePublicGroupData` (`Internal.hs:1628-1630`) and sent directly to owners; owners store `(count, ts)` per relay, with `ts` clamped to the broker timestamp of the message that carried it; the estimate is the **max** count over current relays, carrying **that max-holder's own `ts`**. Only a sole live owner, while no current relay supports `x.grp.relay.count`, uses its own tally with its own clock as `ts` (no other owner publishes then; promoting a second owner requires count-capable relays, Part 8). During reconcile (channel open, chat start) any owner publishes `(estimate, that ts)` iff the estimate differs from the published count **and** the max-holder's `ts` is newer than `subscriberCountTs` (a `subscriberCountTs` later than the owner's clock counts as stale). Every other write carries the published count fields unchanged, and the owner branch stops recounting its tally (`Internal.hs:1623`). The owner branch of `updatePublicGroupData` (`Internal.hs:1620-1627`) stops publishing for subscriber joins, leaves and removals — call sites `Subscriber.hs:3253`, `:3268`, `:3286`, `:3773`, `:3820`, `Commands.hs:3152` — and publishes only when the publishable relay set changed (a relay member removed or left). The `XGrpRelayNew` announcement threshold (`Subscriber.hs:1445-1449`, `publicMemberCount > 1`, which assumes one owner) uses the relay-sourced estimate. Clear a relay's `(count, ts)` on `GSMemRemoved`/`GSMemLeft` (`Types.hs:1430-1431`).
- **Owner materialisation** threads the full `OwnerAuth` (sig + append index): `createLinkOwnerMember` (`Store/Groups.hs:3575`; the key is `ownerKey`, as today), `updateRelayGroupKeys` (`Store/Groups.hs:2353`; create the owner row if missing — today it throws, `:2366-2368`). Joiners and relays skip entries listed in `revokedOwners` as owners and record them in `group_revoked_owners` (Part 2). Root-sign when the adder is the creator (holds the root private key), else delegate. A revoked entry is dropped from the written chain unless it is an ancestor, through any number of delegations, of a current entry (every entry must be signed by root or an earlier one, `Agent/Protocol.hs:2012`; an orphan would make every owner's agent refuse every write); `revokedOwners` keeps its memberId, so the union merge cannot restore it (overview §7: the blob is fixed-size, each entry is about 124 bytes).
- **`x.grp.owner.add`** handling, for members and relays: validate and apply as in Part 4.
- **Promoted owner commit:** on receiving `x.grp.owner.add` for itself, M sets its own role to owner and stores `link_rcv_id` (from the inv), which completes its `ForeignLinkKeys`; its agent can then issue foreign `LSETH`/`RKEYH`, signing with its member key.
- **Creator's root key is unrevocable:** "removing the creator" evicts its link-write key and marks its owner entry revoked, but it retains root signing authority (the immutable trust anchor in `FixedLinkData`); true creator eviction would need a root-key rotation, out of scope.

## Part 8 — version gating and compatibility

- **Link server:** detect the link queue's negotiated server version (the relay-handshake `thVersion`); **require ≥ v24 to promote a second owner** (the hash-CAS `LSETH`/`RKEYH` all need it). On an older link server, block promotion with a clear error rather than degrade — a blind `RKEY` there evicts other owners (replace with no CAS). Because the negotiated version is the min of the two peers' relay ranges, both relay constants (Part 1.1) must reach 24 before a client perceives v24.
- **Relays:** a relay invited to a channel with two or more owners throws on the owner it has no row for (`updateRelayGroupKeys`, `Store/Groups.hs:2366-2368`, called from `Subscriber.hs:4604`), so adding a relay to such a channel fails. A relay that predates multi-owner also never forwards `x.grp.owner.add` (`isForwardedGroupMsg`, `Protocol.hs:528`, unknown events → `False`), keeps the promoted owner an observer and drops its posts (`memberCanSend`, `Subscriber.hs:1737-1738`), rejects that owner's join (Part 6), and sends no `x.grp.relay.count`. So the relay side — tolerant `updateRelayGroupKeys`, `x.grp.owner.add`, the owner join, `x.grp.relay.count` — ships in a release before promotion is enabled, and at runtime promotion requires every current relay to support the multi-owner chat version (owners already check a relay's version, `supportsVersion`, `Subscriber.hs:933`), else it is refused with a clear error. Adding a relay to a channel with more than one owner cannot be checked up front — a relay's version is known only once it answers — so it fails closed: an older relay throws before answering (`Subscriber.hs:4604`, its error recorded only on the relay, `:4565-4567`), and the owner times out the unanswered invitation and shows an error — checked by the same `cleanupUser` step as the promotion TTLs (Part 5), since today nothing on the owner's side expires an `RSInvited` relay. A sole owner whose relays predate the count event falls back to its own tally (Part 6).
- **Older members** ignore `x.grp.owner.add`: they keep rejecting the new owner's admin messages until they upgrade — failing closed rather than trusting a relay-asserted key. **Older joiners** take every chain entry as an owner, including revoked ones; a revoked owner's key is gone and relays have dropped its connection, so its messages do not reach them.
