# Plan: several directories as a generic service layer

Run: 012-service-layer · Base branch: master once the directory search pull request (#7588) has merged, since groups A and B build on its directory RPC and its body compression; f/directory-search if that pull request is held · Repos: simplex-chat-3 (simplexmq for the telemetry prerequisite) · Estimated diff: ~6,300 changed lines in five groups of slices; the first release (groups A, B and the two app slices) ~5,000

Pages (decision, screens, details): https://claude.ai/artifact/493JgCBa4ZCLZQXwAQpVQT

## Summary

**What it builds.** Several directories as services: a service is a bot's contact address whose profile says it answers MCP requests, as the draft "Agent protocols over SimpleX" defines; a role is a job defined by tool names, and a service whose tools include `simplex.directory.search` can be used for search. Services are listed per operator and under Your servers like chat relays, SimpleX Directory is built in, and one search asks every directory in use and shows one list. Usage statistics is the second role, later. First release ~5,000 changed lines, about six working days (groups A, B, C1, C2); ~5,400 with the long-press menu (C3); ~6,300 with usage statistics (D), which also needs a privacy policy change and a simplexmq change.

**The screens** (mock-ups beside today's app, in [sketches/services](sketches/services/)): the operator's servers with a Services section ([today](sketches/services/operator-servers-today.svg), [proposed](sketches/services/operator-servers-services.svg)); Your servers with the same section ([today](sketches/services/your-servers-today.svg), [proposed](sketches/services/your-servers-services.svg)); Add server › Service ([today](sketches/services/add-server-today.svg), [proposed](sketches/services/add-server-services.svg)); New service and its test ([New chat relay today](sketches/services/new-chat-relay-today.svg), [New service](sketches/services/new-service.svg), [test failed](sketches/services/test-service-failed.svg)); the enable alert naming every directory ([today](sketches/services/enable-alert-today.svg), [proposed](sketches/services/enable-alert-services.svg)); results from two directories ([today](sketches/services/results-today.svg), [proposed](sketches/services/results-services.svg)); one directory failing ([today](sketches/services/failed-today.svg), [proposed](sketches/services/failed-services.svg)); the long-press menu ([today](sketches/services/menu-today.svg), [proposed](sketches/services/menu-services.svg), [submenu](sketches/services/submenu-services.svg)); later, usage statistics ([Privacy today](sketches/services/privacy-today.svg), [proposed](sketches/services/privacy-statistics.svg), [alert](sketches/services/statistics-alert.svg)).

**The questions** (section 0, with costs in section 9): the request format (MCP as the draft defines it; this alone starts group A); ship the one-directory search first; no adapter for directories that don't speak MCP; services listed per operator and under Your servers; later, the statistics report's content and who runs it; and, since the draft's Revision 2, whether agents that serve only A2A should fill roles (question 13).

This is a decision document and a plan for the whole design. It builds on the draft "Agent protocols over SimpleX" (docs/protocol/agent-protocols.md on master, Revision 1 of 2026-10-19; Revision 2 of 2026-10-21 adds an A2A binding and leaves the MCP binding over Service RPC as this plan uses it), which already defines the Service RPC envelope and the MCP binding. Roles here are MCP tool names, so an agent that serves only A2A (skills, no tool list) can't fill a role in this design; whether A2A skills should map to roles is a later question (section 9, question 13). What it adds: roles defined by required tools, a stored list of services, the apps' use of the directory role, telemetry as the second role, and consent.

## 0. Decisions asked

Recommended, in one line: **build directories as services over the draft's MCP binding, with roles defined by namespaced tool names; ship the directory search pull request as it is first; store services per operator like chat relays; telemetry second, after a simplexmq change to how service requests are routed.**

The decisions, each with the recommendation first (section 9 has the costs):

1. Protocol: the draft's Service RPC envelope with MCP 2026-07-28 messages (recommended), or our own MCP-shaped JSON, or today's request types plus a "describe" request. With it, three amendments to the draft (section 4, "Amendments to the draft"): sizes stated after compression, the role-tool naming convention, and requests without `clientInfo`.
2. Order: release the one-directory search now and the service layer in a later release (recommended), or hold the search for the service layer.
3. Old directories that don't speak MCP: not supported by new apps, the bot is updated instead (recommended), or a permanent adapter in the core.
4. Where services are configured: in each operator's servers and under Your servers (recommended), or one Services list.
5. Telemetry's content: date, platform and app version only (recommended), or also network health per operator. Either way the privacy policy, which today rules out analytics code in the apps, changes first (section 4, Telemetry).
6. Who runs usage statistics: SimpleX Chat (recommended) or Flux, or not built. Either way a report must not travel through, or leave its return queue with, the operator that runs it, and today's agent can't guarantee that (a default device's return queues are all on SimpleX Chat's servers, and the proxy to SimpleX's bots is SimpleX Chat's own about 4 times in 7); so statistics need a simplexmq change in which the agent enforces this at send time and refuses otherwise (section 4, Telemetry).

What each decision unblocks: decision 1 before the first run (the MCP layer in the core and the directory); decisions 3 and 4 before the second (the search call adapts old directories or not; services are stored per operator or in one list); decision 2 only decides whether the one-directory search waits; decisions 5 and 6 only before the statistics group. No outside date drives them; the first run can start once decision 1 is answered.

One part first, if preferred: group A alone (slices A1–A5) is useful without the rest. It is the part of the draft marked "Planned" (the core's `protocols` key, a bot helper) plus SimpleX Directory answering MCP, so software can search it through a raw `/_service_request`, and AI agents through `@simplex-chat/mcp` once its planned `mcp_call` exists; the apps don't change.

## 1. Goal and acceptance criteria

What the user gets (all groups): any contact address that declares the MCP protocol and offers the directory tool can be added as a directory; SimpleX Directory stays preset; a search goes to every directory in use at once and the results arrive as one list, with a retry per failed directory; the enable alert names every directory that will receive the text; a second kind of service, usage statistics, is opt-in, sends once a day the date, platform and app version, and is configured with the same screens.

Acceptance criteria, each checkable by a named test or command (tests named in section 6):

- AC1 (declaration): a profile's `preferences.protocols` round-trips through the core (JSON, the profile store) and reaches the profile the core sends (address link data, `XInfo`) and a business chat's `groupPreferences`; an older core keeps a received one as raw JSON. Test: `testProtocolsPreference`, `testProtocolsBusinessChat`, JSON tests.
- AC2 (MCP client): the core sends `tools/list` and `tools/call` in the envelope of agent-protocols.md, accepts only well-formed JSON-RPC results with `id` 1, and maps envelope errors, JSON-RPC errors and `isError` to typed errors. Test: `testServiceTools`, `testServiceToolErrors`, unit tests of the parsers with hostile inputs.
- AC3 (test a service): `/_service test <userId> <address>` returns the address's name, its declared MCP versions, its tool names (first page, at most 64, each valid) and the roles it fills; failures are typed (not a contact address, no MCP declaration, no Service RPC, unsupported version, no answer, bad answer). Test: `testServiceTest`.
- AC4 (directory bot over MCP): SimpleX Directory answers `server/discover`, `tools/list` and `tools/call simplex.directory.search` in the envelope, declares `protocols.mcp` in its profile, and still answers today's `{"type":"search"}` unchanged. Tests: `testDirectoryMCP*`, today's `testDirectorySearchRpc*` unchanged.
- AC5 (directory role call): `/_directory search <userId> <serviceId> <json>` sends the search only to a stored service of this user that is in use for search (it has the directory tool, the directory role is turned on, and its operator group is enabled), and returns typed results with at most 50 entries, each a group or channel link, or a typed timeout error within the timeout. - AC6 (storage): services are a list in each operator group of `/_servers`, saved, validated (duplicate address), preset (SimpleX Directory for the SimpleX Chat operator), merged at start-up, copied to a new profile, with the compatibility rules of plan 015 (an app or core without the key saves and reads nothing for services). Tests: plan 015's AC1–AC6, retargeted (section 6, group B).
- AC7 (apps, first release): Settings lists services per operator and under Your servers; "Add server › Service" tests and adds one; search fans out to the services in use for search; per-service retry; the alert names them; `DIRECTORY_SERVICE_LINK` is gone from both apps. Checked on the CI runners (ios-sim, desktop-linux, android-emu) and by review; not compiled in the container.
- AC8 (telemetry, later group): with the switch on, at most one report per UTC day per device to each service in use for statistics in the active, non-hidden profile, holding exactly `day`, `platform`, `appVersion`; sent only when the link fetch and the request go through a proxy of a preset operator other than the statistics operator and the return queue is on such an operator's server, otherwise refused with "Not sent: your network settings would identify you" (section 4, Telemetry); none from a desktop while it controls a phone. In the core: a unit test that `APISubmitTelemetry` marks the request strict and names the operator `matchingHost` finds for the service's host, and none for a host no operator claims; a core case with a short window (refused "too soon" right after start and after `/_network info` online, then the agent's refusal once the window passes); `testTelemetrySubmit` end to end (window 0 in `testCfg`) with the chat test servers, which all sit on localhost with no operator (tests/ChatClient.hs:214-215@M), so the agent refuses and the core reports "your network settings would identify you" and the bot receives nothing; a run where the agent's routing is satisfied is the simplexmq tests' part; telemetry bot tests; app behaviour on runners, including the fresh draw after a "too soon" refusal (by review where a runner can't trigger it).

## 3. Current state

From research.md (file:line there):

- The draft defines the envelope `{"protocol": "mcp", "request": …}` → `{"response": …} | {"error": {code, message?, retryAfter?}}`, the MCP binding (revision 2026-07-28 or later, one JSON-RPC request with its `_meta`; `server/discover`, `tools/list`, `tools/call`), declarations `preferences.protocols.<name> = {versions, transports {chat, rpc}}`, sizes (≤ 10,000 bytes of JSON), and lists the core's `protocols` key and a bot helper as "Planned" (docs/protocol/agent-protocols.md@M).
- MCP 2026-07-28 is stateless: no `initialize`, each request carries `io.modelcontextprotocol/protocolVersion` and `clientCapabilities` in `_meta`; earlier revisions need a handshake first, which one-shot Service RPC can't do. Tool names are 1–128 chars of `A-Za-z0-9_.-`; MCP itself warns that aggregators meet name collisions ("two servers each exposing a `search` tool").
- Service RPC today: `/_service_request` (Commands.hs:1508-1509, :6401@B), a new connection per request, no profile, optional signature, 10 s timeout from the apps (agent default 30 s), bodies ≤ 10,737 bytes compressed and ≤ 64 KiB decompressed with JSON depth ≤ 32 (Protocol.hs:1075-1110@B, compression only @B), errors `A_SERVICE …` (research §3).
- The reply queue is on one of the user's own servers, picked at random preferring another operator when the agent knows the target's operator, created on the session that carries the user's other queues on that server (`mkTSession`, simplexmq Client.hs:1441-1442@Q); the request itself goes through a proxy under the apps' default private routing ("always", AppGroup.swift:78, SimpleXAPI.kt:5434@M), so the service's server doesn't see the IP address unless the user chose another mode; but the proxy is picked at random from the user's enabled proxy servers and then kept for every later request to that server (Client.hs:695-705@Q), so for a default device the proxy to SimpleX's bots is SimpleX Chat's own about 4 times in 7. iOS's default was "unknown servers" until 2026-10-21 (3126d9b54), and iOS users who saved network settings before keep it; under it a request to a server in the user's list goes directly. By default Flux doesn't store messages (Presets.hs:42@M), so a default user's return queues are all on SimpleX Chat's servers; and because SimpleX's own bots sit on preset servers that are disabled by default (smp4–6, Presets.hs:86-97@M), the agent doesn't know their operator and can't avoid it (section 4, Telemetry).
- The directory answers only `{"type":"search"}` with `entries`, `searchCursor`, `moreCount`, `pageSize`, and "unsupported request" otherwise (Directory/Rpc.hs:26-51, Service.hs:379-380@B); global in-flight cap 8; page size 10; image ≤ 12,500 chars; the cursor is a JSON object.
- The apps hard-code one address (`DIRECTORY_SERVICE_LINK`, DirectorySearch.swift:14, .kt:14@B), build and parse the search JSON themselves, keep consent in an app preference ("Directory search", default off), and on desktop-with-phone the phone's core sends the request.
- Chat relays give the storage pattern: a table per list with `domains` linking rows to operators, presets in `PresetOperator`, a start-up merge, closed warning types in the apps, `ListDef` for keys an older peer omits (research §7, §8). Plan 015 applied it to directories and converged; its last review left four P2s (research §7).
- Remote desktop pairs run nearly the same release (minimums 7.1.0.11, raised in most version bumps); an unknown command gives `CECommandError`, an undecodable reply `RPEInvalidJSON`.
- Profiles keep unknown preference keys as raw JSON (`_json`, Types/Preferences.hs:166-182@M); a contact address's link data carries the profile, so the declaration is readable without connecting.
- The badge service already speaks its own versioned RPC (Badges/Service.hs@M); nothing submits telemetry today; the core keeps per-server statistics (Stats.hs@M).

Invariants to keep: every warning and error the core returns is one the asking app decodes; every core in a supported remote pair decodes the other's replies; a stored preset keeps the user's choices; bodies are bounded before any app sees them; a search or report carries no profile; consent is checked on every path that sends text.

## 4. Design

### The model in one paragraph

A **service** is a contact address whose profile declares `protocols.mcp` with `transports.rpc` (the draft) and whose `tools/list` names its tools. A **role** is a contract SimpleX defines: a set of required tool names with fixed inputs and outputs. A service **fills** a role when the role's tools are a subset of the service's tools. The apps keep a list of services per profile, as they keep chat relays, and each role asks "which services in use fill me?" instead of using a constant. Directory search is the first role; usage statistics (telemetry) the second. Adding a third role is a contract, a call, and a screen line, not a new storage or protocol.

```
contact address ──link data──▶ profile.preferences.protocols.mcp {versions, transports.rpc}
        │
        └─ Service RPC {"protocol":"mcp","request": tools/list} ──▶ tools: [simplex.directory.search, …]

role directory  requires {simplex.directory.search}   ⊆ tools → fills
role telemetry  requires {simplex.telemetry.submit}   ⊄ tools → doesn't
```

What gets removed: `DIRECTORY_SERVICE_LINK` and the search JSON building and parsing in both apps (the core does it once, typed); CI's editing of app sources to point at the test directory (it adds the test service in Settings instead).

### Protocol (question 1)

Recommended: **the draft's Service RPC envelope with MCP 2026-07-28 messages**, as specified, plus three SimpleX rules:

1. Requests carry `id: 1` (one request per connection), `_meta` with `io.modelcontextprotocol/protocolVersion: "2026-07-28"` and `io.modelcontextprotocol/clientCapabilities: {}`, and **no** `clientInfo` (the draft's privacy note: every SimpleX app then sends the same bytes apart from the arguments).
2. Role tools have namespaced names, `simplex.<role>.<action>`, so a third-party MCP server's own `search` tool never makes it a directory by accident. The name is the contract: changes are additive (new optional fields); a breaking change is a new name.
3. Services serving roles answer `server/discover` (MCP requires it) and list role tools on the first page of `tools/list`; the core reads only the first page.

Role tools return their data in `structuredContent`; the core reads only that. Whether `content` also carries the JSON as text (MCP's "SHOULD", for older MCP clients) is the service's choice: the page fit runs on the final compressed body, so either fits.

Sizes: the bound is the compressed body, 10,737 bytes, at most 64 KiB once decompressed, JSON depth ≤ 32 (Protocol.hs:946-947, :1075-1110@B). The draft says "SHOULD NOT exceed 10,000 bytes of JSON", which describes master, where bodies aren't compressed; the directory search branch adds compression (Protocol.hs:1075-1096@B, not on master); one allowed directory image (12,500 characters) is already over 10,000.

#### Amendments to the draft

Proposed for "Agent protocols over SimpleX", in the docs slice of group A, if accepted:
- "Message size" for Service RPC: the limit is 10,737 bytes after the core's compression and 64 KiB after decompression; `too_large` refers to the compressed size.
- A "Roles" section: SimpleX-defined tools are named `simplex.<role>.<action>`; a client uses a service for a role when the service lists all of the role's tools; the contracts of `simplex.directory.search` and `simplex.telemetry.submit`.
- Privacy: SimpleX clients omit `clientInfo` and send `id: 1`.

An example exchange, a search (the envelope fields are the draft's; `_meta` is shortened after the first request):

```json
{"protocol": "mcp",
 "request": {"jsonrpc": "2.0", "id": 1, "method": "tools/call",
   "params": {"name": "simplex.directory.search",
              "arguments": {"searchText": "cinews"},
              "_meta": {"io.modelcontextprotocol/protocolVersion": "2026-07-28",
                        "io.modelcontextprotocol/clientCapabilities": {}}}}}
```

```json
{"response": {"jsonrpc": "2.0", "id": 1,
  "result": {"resultType": "complete",
    "content": [{"type": "text", "text": "3 groups, 0 more"}],
    "structuredContent": {"entries": [ … ], "moreCount": 0, "pageSize": 10}}}}
```

The search contract keeps today's field names (`searchText`, `searchCursor` in; `entries`, `searchCursor`, `moreCount`, `pageSize` out; the entry type of Directory/Rpc.hs), so the directory's paging code and the apps' entry decoding carry over; only the wrapping changes. The entry types move from the directory app into the core library so the bot and the core share one definition of an entry (a move commit). The request and response records of the contract are new, untagged records in the core (MCP `arguments` and `structuredContent` have no `"type"` field), with `searchCursor :: Maybe J.Value`, opaque and at most 1,024 bytes encoded: the core never parses a directory's cursor, so each directory keeps its own; SimpleX Directory converts its `SearchCursor` with its existing JSON instances.

What literal MCP buys: one vocabulary with the draft and with `@simplex-chat/mcp` (an AI agent's planned `mcp_call` reaches the same services with the same messages); MCP tooling and SDK types for TypeScript services; any MCP server can become a SimpleX service through a thin bridge. What it costs: about 300 core lines for the envelope and JSON-RPC types (versus about 150 for our own JSON); about 250 bytes of overhead per request and 120 per response before compression; tracking MCP revisions (the core speaks one, a service answers -32022 with its versions, and the core says "needs an app update"). Phones never handle JSON Schema: the core reads only tool names, and each role's inputs and outputs are Haskell types, so a schema can't make a phone do work.

Alternatives:
- **Our own MCP-shaped JSON** (`{"type":"tools"}`, `{"type":"call","tool":…}`): about 150 fewer core lines and ~150 fewer bytes per request, the same style as today's directory; but a second dialect beside the draft, a mapper for every MCP client, and the badge service already shows how dialects accumulate. Not recommended.
- **Today's request types plus a "describe" request** (run 010's form): the smallest change (about 100 lines in the bot, nothing in the core's protocol), but each new role is a new ad-hoc request type and nothing is reusable by AI agents. It is what plan 015's option B would have done.

How today's directory fits: the bot gains the MCP binding beside its current request (it keeps `{"type":"search"}` for released apps), declares `{"mcp": {"versions": ["2026-07-28"], "transports": {"rpc": true}}}` in its profile (not `chat`: declaring the chat transport would oblige it to answer `/_call` in conversations), and is upgraded before any app that uses the service layer ships (it already has to be upgraded for its address keys before release). New apps don't map old directories (question 3): every directory runs the same open-source bot, so an old one is updated, not adapted. An adapter would cost about 60 core lines and a test, kept for as long as any old directory might exist.

### Roles (question 2)

- **Definition.** In the core, a closed type `ChatServiceRole = CSRDirectory` (with `CSRTelemetry` added by D1, when statistics are built; not `SR…`: simplexmq's `SMPServiceRole` already has `SRMessaging | SRNotifier | SRProxy`, Transport.hs:592@Q), JSON `"directory"`, `"telemetry"`, with `roleTools :: ChatServiceRole -> NonEmpty ToolName`. `serviceRoles tools = filter (all (`elem` tools) . roleTools) [minBound ..]` is the only matching rule. The apps decode roles as strings and ignore unknown ones, so a newer core's role doesn't break an older app; the core likewise drops role names it doesn't know when reading the `roles` column and the `/_servers` JSON, so a database written by a newer version (a desktop downgrade, or an Android export imported into an older app) doesn't fail the start-up merge, which reads every user's servers in one transaction (Chat.hs:171@M).
- **Contracts.** `simplex.directory.search`: in `{searchText (≤ 100 chars), searchCursor?}`, out `{entries, searchCursor?, moreCount, pageSize}`. `simplex.telemetry.submit`: in `{day, platform, appVersion}`, out `{accepted}`. The services publish matching `inputSchema`/`outputSchema` for MCP clients; the core validates with its own parsers, not with the schemas.
- **In use.** A service is in use for a role when it fills the role, the user turned the role on for it ("Use for search"), it isn't deleted, and its operator is enabled (the custom group counts as enabled) — plan 015's rule with "enabled" made per role. The core checks all four before sending a role call (the operator check as `opEnabled` does for relays, Operators.hs:584, :592-593@M).
- **Two or more services fill a role.** Directory: each search goes to all services in use for it at once, at most five, in settings order (question 7); results merge as boards 14–15 draw; each failed service gets its own retry row. Telemetry: each service in use for statistics gets the day's report (normally only the preset one).
- **Role screens.** Directory: today's results, the load row, per-service retry, the Directories submenu (boards 14–17, unchanged). Telemetry: a switch and a one-line status in Privacy settings, nothing else.
- **Concurrency.** Each role runs on its own trigger (a search, a daily timer); within a role all services are asked at once with a 10 s timeout each; nothing in the core serialises them (research §3). On iOS each request runs off the cooperative thread pool (plan 015's finding: the FFI call blocks its thread for up to the timeout).

### Telemetry (question 3)

- **What:** `{"day": "2026-10-22", "platform": "ios", "appVersion": "7.1"}`: the UTC date, one of ios, android, desktop, and the major.minor version. Nothing else in the first version. Optional later (your call, each with its cost): per preset operator, bucketed counts of failed and successful message sends that day (useful for operators' reliability; buckets rather than counts, because exact counts fingerprint a device).
- **When and from where:** at most once per UTC day per device to each service in use for statistics, at a random moment while the app runs that day but never within 5 minutes of the agent's last (re)connection to the user's servers (`CONNECT`/`UP`, Subscriber.hs:197-200@M) or the last network-online the app reported (iOS and Android send it, Commands.hs:1918@M; desktop relies on reconnections). When the moment falls inside that window, or passed while the device slept, was offline or (on iOS) had the app suspended, a fresh random moment is drawn over the rest of the day, never anchored on the reconnection or the window's end; if none remains, the day is skipped. Each start, resume, network change or wake reconnects the device's queues, for a default device all on SimpleX Chat's servers (`APIActivateChat` → `subscribeUsers True`, Commands.hs:608-619@M; after a settings change Agent.hs:733, :747-751@Q; after a physical change through disconnection and resubscription, Client.hs:780-842@Q), so a report right after one would narrow to the devices that just reconnected. iOS suspends and resumes the core with the app (SuspendChat.swift:31, SimpleXAPI.swift:366-378@M), so only foreground sessions over 5 minutes report; the counts under-count every platform that sleeps or suspends, iOS most (INFERENCE), accepted and said with the counts. Reports come from the active profile if it isn't hidden (its services and servers); a day whose report failed (the service didn't answer) or was skipped is never sent later or retried, and reports are never batched. A desktop that controls a phone sends nothing while connected (its commands would run on the phone's core and servers). The once-a-day mark is kept by the app per device, keyed by UTC day and service address (not by the per-profile service id), so three profiles holding the same preset still send one report, and switching profiles mid-day doesn't send again.
- **Consent:** its own switch, "Share usage statistics" in Privacy settings, off by default. Turning it on shows an alert with the exact report and the services' names; each service has "Use for usage statistics" (preset: on for the statistics service; user-added services: off until the user turns it on). Status under the switch: "Last sent today to [service]", "Not sent: no service in use", "Not sent: your network settings would identify you" (below), or "Not sent today: the service didn't answer".
- **The privacy policy first:** it says client apps "should not include any tracking or analytics code" and "must not send anything not directly required for users communications without explicit users' consent", and that SimpleX Chat Ltd "does not have information about how many people use SimpleX Chat applications" (PRIVACY.md:201, :203, :207@M), and the core shows that file as the operators' usage conditions (`usageConditionsText`, Operators.hs:68-70@M). Statistics need that text changed, and so a new conditions version users accept, before group D ships; the consent switch alone doesn't satisfy the first sentence. (Found in the operators design's plan; it holds in either design.)
- **What the service can learn:** per report, the three fields, the time it arrived, and the server of the return queue (the service needs it to answer, simplexmq Agent.hs:2287-2290@Q); no profile, no device key, and no key that links two reports. Whether it also learns the IP address and the user's session depends on the route (below).
- **How the agent routes a service request, today.** Besides the service's own server, two servers carry it: the proxy, chosen from the enabled servers with the proxy role (`getSMPProxyClient` → `getNextServer c userId proxySrvs [destSrv]`, Client.hs:695-705@Q) and then pinned for that destination server: every later send and link fetch to it reuses that proxy until the proxy disconnects (`smpProxiedRelays`, Client.hs:698, :705, :801, :1010@Q; not reset by `setProtocolServers`, Agent.hs:3192-3195@Q); and the return queue, chosen from the enabled servers with the storage role (`withNextSrv … storageSrvs`, Agent.hs:2282-2284@Q), on the session that carries the user's other queues there (`mkTSession`, Client.hs:1441-1442@Q). The core fetches the service's short link through the same pinned proxy right before each request (`resolveServiceTarget` → `getShortLinkConnReq`, Commands.hs:5993-6010@B; `getQueueLink` → `sendOrProxySMPCommand`, Client.hs:2014-2016@Q). Both choices prefer operators the target's host doesn't belong to, but the agent knows the target's operator only through a server in the same enabled list sharing its host (`usedOperatorsHosts`, Client.hs:2516-2522@Q; `mkUserServers`, Env/SQLite.hs:136-140@Q). SimpleX's own bots sit on preset servers disabled by default (smp4–6, Presets.hs:86-97@M: SimpleX Directory on smp4, the badge service on smp5, Chat.hs:74@M), so no operator is avoided for them. A profile created since 2024-08 enables 4 random SimpleX Chat SMP presets and 3 random Flux ones (`useSMP = 4`, `= 3`, Chat.hs:87, :96, `chooseRandomServers` :320-336@M), all with the proxy role, and Flux's have storage off (Presets.hs:42@M; onboarding turns it on only when no other enabled operator stores, ChooseServerOperators.swift:205-215, .kt:338-347). So for a default device every return queue is on a SimpleX Chat server, and the proxy to SimpleX's bots is SimpleX Chat's own about 4 times in 7. Custom servers have no operator (`Nothing`, Operators.hs:464-465@M) and the proxy role by default (:191-193), so the agent treats them as "another operator". Older installs that stored smp4–6 as enabled behave differently (Operators.hs:411-433@M).
- **What a report must not reveal, as requirements.** The statistics operator could link a report to its sender if it also saw the sender's IP address or session (by running the proxy, or through a direct send), or the return queue (by running its server); and a custom server, usually the user's own, would name the user in every report, as proxy or as return queue. So a statistics request is sent only when both hold, at send time:
  1. The link fetch and the request go through a proxy of a preset operator other than the statistics service's operator: never directly, never through a custom proxy.
  2. The return queue is on a server of a preset operator other than the statistics service's operator, never a custom server.
  3. Otherwise the request is refused with a typed error, and the status line says "Not sent: your network settings would identify you".
  Only the agent knows, at send time, the pinned proxy and the chosen return queue, so the agent enforces these; a prediction in the core can't (the pin and the link fetch defeat it). The core marks every statistics request strict and names the service's operator, found from the address's host and the operators' server domains as it already matches servers to operators (`matchingHost`, Operators.hs:467-470@M), and maps the typed error to the status line.
- **The simplexmq change (D0), for simplexmq to design.** A sketch that meets the requirements: a service request can be marked strict, and can name an operator to avoid (statistics requests are always strict; strict with no operator named still means a preset operator's proxy and return queue, never direct, never custom). For a strict request the agent's service-request call fetches the short link itself and keys both the fetch and the request by one fresh per-request id (the new connection's, created inside `serviceRequest_`, Agent.hs:1847@Q), on a destination session it closes after the answer, so no earlier pin can apply: today the core fetches the link in a separate call (Internal.hs:1694-1696@B), keyed by the user's session or, under per-connection isolation, by the link id that every ordinary fetch of that address shares (Client.hs:1437-1442, :2016@Q), and an existing pin wins even over an explicitly chosen proxy (:705); and before sending, the agent checks the proxy it actually got and refuses if it breaks the rule. Points for simplexmq's plan: (a) the connection can only be created from the fetched address (`newConnToJoin` needs it, and `serviceRequest_` checks its ratchet keys first, Agent.hs:1470-1497, :1842-1847@Q), so the id is drawn first and passed in (`createConn_` keeps a given id, AgentStore.hs:541-543@Q), or the fetch gets its own fresh id; (b) in the default transport mode `mkTSession` drops the entity id, so the strict path builds `(userId, destSrv, Just id)` whatever the mode (Client.hs:1437-1442@Q); (c) a proxied request has no destination client, so what closes is the proxy client `(userId, proxySrv, Just id)`, which also drops its relay pins, after an answer, a refusal or a timeout (:700-706, :800-801); (d) the fetch runs synchronously inside the call, not as a stored command, since stored commands resume right after start (Agent.hs:2001, :2221-2224@Q); (e) the core passes the restored short link (Internal.hs:1690-1696@B). A simpler variant for that plan to weigh: no fetch at report time, using the full address kept from the preset or the last "Test service" (`CTFullContact` is already a valid target), so only the request needs the strict route and its connection id is fresh by construction; its cost: the core must keep the full address, a column in the `services` table (a DB format change here) or full-link presets, since today it keeps only short links (Chat.hs:74@M); and if the bot rotates its keys, reports fail until an app update or a manual "Test service", whose fetch goes through today's route. The agent picks the proxy and the return queue among preset operators' enabled servers other than the named operator, allows servers without the storage role for the return queue (Flux, for default users; they sit in the proxy list, so the choice spans both lists, Env/SQLite.hs:123-140@Q), never falls back to a direct send (bypassing `directAllowed`, Client.hs:1253-1254@Q), and refuses with a typed error when no server qualifies or when private routing is "never". The return queue stays on today's connection to its server: isolating it too would mean changing every later command on it (its acknowledgement, deletion and resubscription derive the session from the global setting, Agent.hs:3853-3855, :2305-2309, Client.hs:1445-1455@Q), and it buys little, since requirement 2 already keeps it away from the statistics operator; it is listed as an optional extra, over 600 lines more with its tests. In the other modes the request goes through a proxy even where the user's mode would send directly ("unknown servers" with the host in the list, or "unprotected" with the host in the list or the IP address protected, Client.hs:1193-1208@Q), since a proxy only adds privacy and the user opted in; otherwise iOS users who kept the old default would never report, because disabled preset hosts count as known (`knownHosts`, Env/SQLite.hs:140@Q). `JRServiceReq` is a stored async command (Agent/Protocol.hs:2283-2286, Agent.hs:2207-2209@Q), so the new fields need an encoding that still reads old rows. Rough size: 600–1,000 lines with tests (a new entry point with the fetch inside, mode-independent session keys, an operator-filtered proxy choice over both server lists and its check, never-direct, a refusal error, closing the proxy client, the stored-command fields, and about 14 agent scenarios with two operators' servers; INFERENCE from today's service-request tests, tests/AgentTests/FunctionalAPITests.hs:1381-1478@Q), its own plan in simplexmq. It serves either design: the operators design's statistics worker sends a service request too and knows its operator from the preset. Searches could use the same as a preference with fallback instead of refusing, and a fallback after the other operator's servers fail, so an outage at Flux doesn't block search; badge requests aren't strict and name no operator (they are signed per purchase, so they gain nothing, Commands.hs:5415, :5837@M).
- **Who runs it (decision 6).** The mechanism is the same either way; the choice is who holds the counts.
  - **Recommended: SimpleX Chat runs the statistics service.** With D0, default devices send through Flux's proxies, with return queues on Flux's servers, held for seconds and deleted after the answer (Agent.hs:1842-1858@Q); Flux holding such queues for users who left Flux's storage off is your call.
  - Flux runs it. With D0, default devices send through SimpleX Chat's proxies and return queues; without D0, only devices where the bot's Flux server is one of their 3 enabled Flux servers would have Flux marked as "used" (about half), and nothing would enforce the requirements, so D0 is needed here too. Flux operates the service and holds the counts, an arrangement between the operators.
  - Not building statistics: group D is dropped; nothing else depends on it.
- **What still links:** the report is with one operator and the proxy and return queue with the other, so linking needs the two operators to share data, which the policy rules out for preset operators (PRIVACY.md:154@M). What the statistics operator alone keeps is presence: the report's arrival against which devices are connected to its own servers at that moment (on iOS, which are in the foreground), narrowed by platform and version; the 5-minute rule above removes the sharpest part, right after a reconnection, and the rest stays (INFERENCE on its strength). The alert promises only what holds: no profile and no identifier are sent.
- **What it counts:** reports per day per platform and version among devices that turned the switch on (it is off by default), so a lower bound of opted-in daily active devices, not of all users. Weekly or monthly actives can't be computed without linking reports; that is the price of having no identifier. The counts can't be authenticated: reports carry no key by design, so anyone can send any number of them, and nothing can rate-limit them without linking. The numbers are indicative, not a measurement anyone can rely on against a motivated sender.
- **The bot:** a small bot, `simplex-telemetry-service`, on the shared MCP helper, counting reports per day, platform and version and keeping nothing else (no return-queue addresses, no times finer than the day).

### Storage, presets and compatibility (question 5)

Plan 015's option A carries over with "directory" replaced by "service" and two new columns:

- Table `services (service_id, user_id … REFERENCES users ON DELETE CASCADE, address BLOB, display_name TEXT, domains TEXT, preset INTEGER, tools TEXT, roles TEXT, created_at, updated_at)`, `STRICT`, unique `(user_id, address)`, index on `user_id`. `tools` is the comma-joined tool names (the MCP name charset has no comma); `roles` the roles the user turned on. No `deleted` (nothing references a service) and no `tested` (stored tools are the test result).
- Type `UserService' s {serviceId, address :: ShortLinkContact, displayName, domains, preset, tools :: [ToolName], roles :: [ChatServiceRole], deleted}` with `UserService`, `NewUserService`, `AUserService`; the API adds the derived `availableRoles` (from `serviceRoles tools`) so the apps don't repeat the matching rule.
- In `UserOperatorServers` as `services :: ListDef UserService` (an older phone's reply parses as none); in `UpdatedUserOperatorServers` as `services :: Maybe [AUserService]` (`Nothing` from an older app saves and validates nothing for services). Validation: duplicate address error; a "no service for search" warning only when the request carries services (plan 015's R1-1 and R2-1 fixes).
- Presets: SimpleX Directory in the SimpleX Chat operator with tools `[simplex.directory.search]` and role directory on; later the statistics service with `[simplex.telemetry.submit]` and role telemetry on (nothing is sent until the Privacy switch is on). A preset's stored row takes the preset's tools on each start and keeps the user's roles; a role the preset newly offers starts as the preset says.
- Start-up merge: plan 015's adoption before grouping (a custom row at a preset's address becomes the preset once and for good) and its handling of presets an operator stops listing, with the four P2s of its last review applied: the claim narrowed to "its operator still preset"; tests for the `-s` shape, for an operator missing from the presets, and for adoption before the drop check; a restart test with `testCfg` variants; and question 8 answered "keep it, turned off, as the user's own", which needs no new store function.
- Names: normalised with `mkValidName` where app input enters the core; a service's name is its own profile's name.
- Older apps and cores: unaffected; they ignore the new key, the directory keeps `{"type":"search"}`. A newer app on an older core (desktop with an older phone): `/_servers` has no services, so the app shows none and hides "Search in Directory"; the new commands return `CECommandError`. In practice desktop and phone run the same release (the minimum versions rise with each release).
- Bot API: the new commands stay undocumented like the servers commands beside them (bots/src/API/Docs/Commands.hs `undocumentedCommands`); `Preferences.protocols` is documented (it is part of the profile type bots use). For services written as bots, a Haskell helper module (`Simplex.Chat.Bot.MCP`) answers the envelope, `server/discover`, `tools/list` and `tools/call` from a list of tools with handlers; the directory and statistics bots use it; a TypeScript helper (the draft's "planned" bot-library helper) is a follow-up.
- Migration: one, `M2026MMDD_services`, dated after the newest on master and on the branch when group B starts; SQLite and Postgres.

### Core API (new commands)

- `APITestService {userId, address, requestTimeout}` (`/_service test <userId> <address> [timeout=<s>]`, 10 s by default) → `CRServiceTestResult {serviceProfile, mcpVersions, tools, availableRoles, moreTools :: Bool, testFailure :: Maybe ServiceTestFailure}`, like `APITestChatRelay`. Steps: fetch the link data (no connection); require a contact address whose profile declares `protocols.mcp` with `transports.rpc` and a version the core speaks; send `tools/list`; parse.
- `APIDirectorySearch {userId, serviceId, requestTimeout, request :: {searchText, searchCursor?}}` (`/_directory search <userId> <serviceId> [timeout=<s>] <json>`, 10 s by default) → `CRDirectorySearchResults {user, serviceId, results}`; refuses a service that isn't in use for search: not this user's, doesn't fill the role, the role turned off, or its operator turned off.
- `APISubmitTelemetry {userId, serviceId, report}` (group D) → `CRTelemetrySubmitted`; the same refusals for the telemetry role, "too soon" after a reconnection, and the agent's refusal when it can't route the report away from the statistics operator (section 4, Telemetry), each a distinct error so the app can show its status line; the report is a closed record the core encodes, so an app can't add fields.
- Generic use (bots, AI agents) needs nothing new: `/_service_request` already carries any envelope.

### What the core validates and what the apps do

The core: the envelope and JSON-RPC shape (`id` 1, `resultType` absent or "complete"); tool lists (first page, at most 64 names, each 1–128 chars of the MCP charset, others dropped; schemas, descriptions, icons and annotations ignored, never stored, never fetched); role results through typed parsers (entries decoded one at a time, bad ones dropped, capped at 50, each must be a group or channel link, images ≤ 12,500 chars as today, `searchCursor` ≤ 1,024 bytes encoded, counts bounded); names via `mkValidName`; that the role is in use before sending. The apps: consent, the fan-out, per-service state, rendering.

### Alternatives considered (the whole design)

- **Directories like chat relays (plan 015, option A; the operators design):** a directory is its own list, no roles; the apps build and read its MCP requests; about 450 fewer lines for several directories, the long-press menu included in both, by that design's own plan (section 11), inside both estimates' error; a later kind of service that users choose from a list needs its own storage, presets and screens again, while one with a single receiver per operator (statistics) is an operator setting there, about the same size as here. Choosing that design now and moving to services later costs, by its plan, about 1,400 lines then, or about 2,750 with the core taking over requests and the `protocols` key (mostly screens, a migration and a settings key kept a release). What this design buys sooner is one MCP layer in the core (one parser and bound for every role, not request code in Swift and Kotlin), the core checking every role call, and no second settings format to carry. Part of the extra, the `protocols` key (A1), is work the draft already lists as planned; both designs build the bot helper. This design reuses its storage pattern almost entirely.
- **Services matched by schema compatibility instead of tool names:** would let a service name its tools freely, but needs a JSON Schema comparator in the core, which is undecidable in general and a denial-of-service surface on phones. Rejected.
- **App-side MCP (apps build and parse the envelope):** no new core commands, but the same parsing twice (Swift, Kotlin), no bound in one place, and no check in the core that a role is in use. Rejected.
- **The core fans out a search itself and streams events:** one command per search, but per-service progress and retry would need events and remote-desktop forwarding of them. Rejected: the apps fan out, as plan 015 planned.

## 5. Compatibility and security

- Wire protocol: no change to the chat protocol or agent; Service RPC payloads change only for new apps calling new services. The directory serves both shapes. Profiles gain an optional `preferences.protocols` key (the draft; older clients keep it as raw JSON).
- The amended size limit: a body over 10,737 bytes is sent compressed (`compressBodyTo` passes smaller bodies through unchanged, Protocol.hs:1066-1076@B). Every app version that searches has the decompression (it came with the search branch); software on an older core (before #7588) reads only bodies small enough to travel uncompressed, which covers today's badge service exchanges and the directory's legacy pages that fit. A service talking to such software keeps its answers under 10,737 bytes.
- Database: one migration (`services`), up and down, SQLite and Postgres; no backfill (presets arrive through the start-up merge).
- Older and newer clients: section 4, "Storage, presets and compatibility".
- Adversary, a hostile or careless service the user added:
  - Oversized or deep bodies: bounded before parsing (10,737 bytes compressed, 64 KiB decompressed, depth 32; unchanged). Test: existing `serviceBodyTests`.
  - A huge or odd tool list: first page only, at most 64 names, invalid names dropped, everything but names ignored. Test: `testServiceToolsBounds` (a list of 1,000 tools, names with spaces, 200-char names, schemas with `$ref` to a URL: none fetched).
  - Claims the directory tool and returns junk: the typed parser rejects the response (that service's retry row), drops bad entries, caps at 50. Test: `testDirectoryRoleJunk`.
  - Claims a role it later drops, or adds one: stored tools change only on "Test service"; a role a user-added service gains starts off. Test: `testServiceRoleDefaults`.
  - Many services: at most five asked per search (question 7). Test (app): runner check with six services.
  - One slow service: 10 s timeout each, results shown as each arrives. Tests: `testDirectoryRoleTimeout` (a service that never answers gives a typed timeout error within the timeout); that a slow service doesn't hold up another is the apps' fan-out, checked on the runners with one test directory that never answers (a core chat test runs one command at a time, Terminal/Input.hs:58-65@M).
  - Name spoofing ("SimpleX Directory" added by anyone): the screens show the address's host under the name; the alert marks the user's own services; `mkValidName` strips format characters.
  - Prompt-like text in results: shown as data, as today's directory entries are.
- Adversary, the network or a service's operator: unchanged by this design for search (research §3, section 10: for a default user the return queue's server and, about 4 times in 7, the proxy are SimpleX Chat's, so the directory's operator can link a user's searches); searches could later use the simplexmq change's preference with fallback. Statistics wait for that change, in which the agent refuses a report it can't route away from the statistics operator (section 4, Telemetry; question 6).
- Consent per role: the Directory search switch (exists) and the Share usage statistics switch (new, off); per service, a switch per role; the core refuses a role call to a service not in use for that role (role off, or its operator off), so a bug in an app can't send to a service the user didn't choose for that role. The global switches stay app preferences, as "Directory search" is today: the core can't check them.

## 8. Risks

- Riskiest assumption: that a service request carrying the draft's envelope with MCP 2026-07-28 messages fits every role within 10,737 bytes, including a directory page with images. A4 tests it first: the directory's page fit runs on the enveloped response, and `testDirectoryMCPSearch` pages two image entries.
- MCP revisions change: the core speaks one revision; a service answering -32022 gives "needs an app update". The tools part of MCP has changed only additively across revisions (research §2), and roles read only `structuredContent` and names.
- Remote desktop pairs: new keys are optional and new commands fail cleanly; pairs run the same release in practice.
- The live directory must be upgraded (MCP and its address keys) before the first app with the service layer ships; a release-checklist item, not code. If it isn't: older apps are unaffected (they send today's request, which the directory keeps answering), but in new apps every search to SimpleX Directory fails with its retry row ("Test service" says it doesn't declare MCP), until the directory is updated.
- Telemetry depends on decision 6, on a simplexmq change outside this repo that isn't planned yet (without it no report can be kept away from the operator that runs statistics), on changing the privacy policy, which today rules out analytics code in the apps, and on deploying the statistics bot; its counts are indicative only (opt-in, unauthenticated).

## 9. Open questions

Each with the recommended answer and what changes otherwise. Questions 1–6 are the decisions of section 0; 7–13 are smaller.

1. Protocol. Recommended: the draft's envelope with MCP 2026-07-28, the three rules of section 4, and the three amendments to the draft. If our own MCP-shaped JSON: ~150 fewer core lines, a second dialect beside the draft. If today's requests plus "describe": ~1,000 fewer lines now (group A shrinks to a "describe" request in the bot and its parsing in the core), no reuse by AI agents, each role its own request type. Under either alternative only group A changes: services are still stored with their tools and roles (group B), and the apps (group C) don't see the wire format, since the core's role call hides it.
2. Order. Recommended: release the one-directory search pull request first; the service layer replaces its constant and request in a later release, and the bot keeps the old request until those versions are unsupported. If held: the search waits for groups A, B, C1 and C2 (about six working days of runs, the app checks on runners included, plus the host's full test suite) and the old request never ships.
3. Old directories. Recommended: no adapter; directories are updated. If an adapter: ~60 core lines and a test, kept as long as any old directory exists.
4. Where services are configured. Recommended: per operator and under Your servers (boards 10–12 renamed). If one Services list: a new screen, operators no longer cover preset services.
5. Telemetry content. Recommended: date, platform, major.minor version. Either way the counts cover only devices that opted in and can be inflated by anyone (no key, by design). If network health is added: bucketed send success and failure per preset operator, more useful and more identifying.
6. Who runs statistics (section 4, Telemetry). Recommended: SimpleX Chat; with the simplexmq change, default devices send through Flux's proxies with return queues on Flux's servers for seconds, which Flux must accept for users who left Flux's storage off. If Flux runs it: the same change, mirrored (SimpleX Chat's proxies and return queues), and the counts are with Flux, an arrangement between the operators; without the change only about half of default devices would even avoid Flux, and nothing would enforce it. If statistics aren't built: group D is dropped, nothing else changes. No option works without the simplexmq change (question 12).
7. Services asked per search. Recommended: at most five, in settings order; Settings says which. If no cap: every added directory receives every search and each costs a reply queue.
8. A preset an operator stops listing. Recommended: kept, turned off, as the user's own (no new store function; the user's choice survives a later re-preset). If deleted: plan 015's delete path and its tests.
9. Consent. Recommended: one switch per role in Privacy plus a switch per role on each service, and the core refusing role calls to services not in use for that role (role or operator off). If one switch per role only: a user-added service that also offers statistics would receive reports when the global switch is on.
10. Tool lists refreshed. Recommended: only on "Test service" (and presets by app updates). If by MCP's `ttlMs`: background requests on a timer, each a reply queue, for little gain.
11. The statistics service as a preset. Recommended: a preset of the operator that runs it (question 6), sending nothing until the user turns the switch on.
12. Who plans and owns the simplexmq change (D0). Recommended: you assign it in simplexmq after the first release, from the sketch in section 4: strict service requests that name an operator to avoid, with the link fetched by the agent on a fresh per-request session, refused when the route can't avoid it (~600–1,000 lines with tests). If nobody owns it: statistics can't ship; the first release doesn't need it.
13. Agents that serve only A2A (added to the draft in Revision 2, 2026-10-21, which reached master on 22 Oct; this plan's reviews didn't cover it). Recommended: roles stay MCP tool names for now, so such an agent can't be a directory; mapping A2A skills to roles is decided when a role needs it. If A2A agents should fill roles now: a skill-to-role mapping and an A2A client in the core, not estimated here.

- For default users every search's return queue is on a SimpleX Chat server, the directory's own operator, on the session that carries the user's other queues there (Flux doesn't store by default); the search review called this "can be", it is "always". And the proxy to SimpleX Directory is SimpleX Chat's own on about 4 default devices in 7, kept for every later request to the directory's server, so on those devices the operator sees both the searcher's IP address and the search. Searches could later use the simplexmq change (question 12) as a preference with fallback; until then both stay, and the alert promises nothing about either.

- The badge service could move to the draft's envelope as its own protocol name.
- `@simplex-chat/mcp`'s planned `mcp_tools` and `mcp_call` would reach the same services; no dependency either way.

## 11. Comparison with the operators design

From that design's plan of 2026-10-23 01:57 UTC and its costs.md of 06:58 UTC (shared/directory-search/several-directories/operators/; its page: https://claude.ai/artifact/YRpeaz3JcJ72onsRYy7n5G). Its numbers are its own estimates; neither plan has been built.

- **The same in both:** what users get in the first release (directories under each operator and under Your servers, SimpleX Directory preset, one search to every directory in use, a retry row per failed directory, the long-press menu); storage like chat relays with the start-up merge; older apps and remote desktops handled the same way; the one-directory search ships first; board 13's clause dropped; search linkability left to a simplexmq change; the directory answers the draft's envelope with an MCP `tools/call` of `simplex.directory.search`, the same tool contract as here.
- **What makes a directory:** there, the user puts an address in a Directories list, and "Test directory" checks that its tool list offers the search tool; here, a service whose tool list has the directory tool, found by "Test service", and other kinds of service use the same list.
- **Who builds and reads requests:** there, the apps (Swift and Kotlin), with the core checking only that a search goes to a directory in use; here, the core, with one parser, and the `protocols` profile key the draft plans.
- **Size,** both with the long-press menu (in that plan's app pull requests; here C3, after the first release): there ~4,950 lines in four pull requests (core ~1,050, directory bot ~600, iOS ~1,700, Kotlin ~1,600, CI included); here ~5,400 (core and bots ~2,500, apps ~2,900). The ~450-line gap is inside both estimates' error. Working days aren't comparable: that plan counts ~3.5 days of agent runs plus runner time; this one counts ~7 days with each app's runner checks included.
- **Statistics:** in both designs it needs the privacy policy changed and a simplexmq change so the operator receiving reports can't tie one to a device; there an operator setting (or a Privacy switch with one built-in address), here a role with a Privacy switch and the statistics service built in; ~900 lines either way.
- **Later:** there, a move to services is ~1,400 lines, or ~2,750 with the core taking over requests and the `protocols` key, and its `directories` settings key stays a release beside the new one; here, nothing to move.
- **In short:** the first releases are about the same size; if more kinds of services that users pick from a list come later, that path ends at ~6,350–7,700 lines against ~5,400 here; if they never come, that design is a little smaller and changes no profile format. That design builds and reads requests in the apps; this one in the core, sharing one protocol layer with the draft's plans for AI agents.
