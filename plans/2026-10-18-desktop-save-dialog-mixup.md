# Desktop: saving from an open Save dialog writes another file's content

## Problem

On desktop some save requests open the Save dialog only after a wait: a file tapped before it was received opens it when the download finishes (`OpenWhenReceivedEffect` → `saveFileLauncher.launch`), a file saved or shared from a linked mobile opens it once the file is fetched (`loadRemoteFile`), and the database export opens it after the archive is written. `DialogState.awaitResult` replaces the pending result and parameters on every call, while the file chooser that is already open (JFileChooser on Linux and Windows, AWT `FileDialog` on macOS) is created once and keeps its parameters. So when such a request arrives while a Save dialog for another file is open, the open dialog still shows the first file's name, but pressing Save completes the second request: the second request's callback writes the second file's content to the chosen path, and the first request never completes.

Reproduced on the master prebuild in two runs of the same bug, with text files of different size: earlier run (2026-10-18): file-A-small.txt 115 bytes; batch5 run (2026-10-25, 3 of 3 timings): file-A-small.txt 103 bytes. Steps: download the text file "file-A-small.txt" and cancel its Save dialog; tap a 40 MB file; click the text file again and keep its Save dialog open until the large file finishes; press Save. In both runs the saved "file-A-small.txt" is 40,000,000 bytes, identical to the large file.

A slot can also stay claimed with no dialog shown, and then every later request to it waits forever. Two causes, from the code:
- `awaitResult` clears the slot only after `await()` returns, so a request whose awaiting coroutine is cancelled leaves the slot claimed. This happens when a QR code view closes while its Save dialog is open: the view's coroutine scope (`rememberCoroutineScope`, `QRCode.kt:73`) cancels the coroutine waiting in `awaitResult`. For example: a peer connects through the one-time link shown in the QR code; a desktop notification is clicked, which closes all modals (`NtfManager.kt:80` sets `clearOverlays`, `App.kt:111-113` calls `ModalManager.closeAllModalsEverywhere()`); a mobile scans the "Link a mobile" QR code (`ConnectMobileView.kt:195`); or the session with a controlled mobile ends while the QR code of a group link or a security code is being saved (`RemoteHostStopped` calls `switchUIRemoteHost(null)`, which closes the center and end modals, `SimpleXAPI.kt:3822-3826`). The open slots are reached the same way when the attachment picker's `LaunchedEffect` (`ComposeView.desktop.kt:24`) leaves composition while its chooser is open.
- The chooser is shown while the slot is claimed and is created once, so a request that claims the slot before any frame shows it empty gets no dialog. Observed on master: clicking a QR code opened a folder chooser for the QR image, and after the image was saved no second Save dialog (`shareFile`, `QRCode.kt:96`) appeared, and Save of a received file afterwards did nothing, from the context menu or by tapping it. The image request resumes on the UI thread, clears the slot, writes the image and calls `shareFile`, whose request (`withLongRunningApi`, on a background thread) normally claims the slot before the next frame is rendered.

## Fix

`DialogState` takes the value its dialog returns on Cancel: `null` for the open and save slots, an empty list for the open-multiple slot. When a request is already pending in the slot, `awaitResult` returns that value at once instead of replacing the pending request, and logs a warning: it is the only trace that tells a dropped request from the user pressing Cancel. The warning goes to stdout, and is not printed when developer tools are on with a log level above Warning. The check and the claim are done under one lock, so of two requests at the same instant the dialog is opened for one, and the other is cancelled.

Inside the lock, `awaitResult` writes `params` before `request` (master writes them the other way round). The dialog is shown when `request` is set, and the chooser takes its file name once, when it opens; the composable may read `params` again on recomposition, which does not change what the open chooser uses. In the old order a dialog composed between the two writes opens with the previous request's parameters (a file name, or none) while Save completes the new request; writing `params` first removes that window.

`awaitResult` awaits its request in a `try`, and in the `finally` frees the slot under the same lock, whether the request completed or its awaiting coroutine was cancelled. The slot's request (`onResult` in master, now `request`, readable outside `DialogState`) is what each chooser is opened for: `DesktopApp.kt` composes the chooser inside `key(request)`, and the chooser's callback completes that request. A new request therefore gets a new chooser even when no frame showed the slot empty, and a chooser can complete only the request it was opened for; completing a request that has ended has no effect. `isAwaiting` and both `onResult!!` reads are removed.

A chooser leaves composition when its request ends or the slot holds another request. On Linux and Windows `onDispose` then closes the JFileChooser with `cancelSelection()`; the chooser is created when the effect starts, instead of inside the launched coroutine, so that `onDispose` can reference it. Closing a chooser whose dialog has already returned has no effect. On macOS `AwtWindow` already calls `FileDialog.dispose()` when the chooser leaves composition (see "Not fixed").

The QR code click calls `shareFile` after saving the image only on Android (`QRCode.kt:96`), where it opens the share sheet for the image saved to a temporary file, as before. On desktop `shareFile` is a second Save dialog with the image just written selected, and Save there truncates the image before copying it onto itself. Master normally did not show it: the `shareFile` request runs on `Dispatchers.Default` (`withLongRunningApi`) and usually claims the slot before the next frame, so it got no dialog (see "Problem"); when no thread picks it up before the next frame, master opens it, with that hazard. With a chooser per request it would always open. So on desktop a QR code click makes one request, as the user sees on master; when the folder chooser returns, the `finally` frees the slot, and the next save gets its own chooser. `onShare` is still called on all platforms.

The guard is in the slot, so every caller is covered: `FileChooserLauncher.launch` (open and save), `FileChooserMultipleLauncher.launch` and `saveTempImageUncompressed` (QR code save). Every callback already handles a cancel (the database export deletes its temporary archive). The request that arrives second is the one cancelled, whether it is delayed or comes from a click. A click can make a second request before the chooser is shown, because only a shown chooser blocks clicks; and a QR code click computes the QR image before it calls `awaitResult`.

## Alternatives

- A guard at the call site, in the save branch of `FileChooserLauncher.launch` (+1 line, and it would also need a lock: delayed requests run on background threads, so two of them can pass the check together). It leaves `saveTempImageUncompressed` unguarded: if a delayed request claims the Save dialog while a clicked QR code image is being computed, the QR request replaces it: pressing Save completes the QR request, and the delayed request never completes (for a database export, the progress indicator stays shown and the archive is not deleted). Every new caller would have to repeat the check.
- The same guard repeated in `saveTempImageUncompressed` (+1 line). It closes the QR path, but the check is then needed at every caller of `awaitResult`, and the open slots stay unguarded.
- Leaving the QR path open. No content is written to the wrong file, but the delayed request never completes, which is half of this bug.
- Holding `params` and the request in one state value, so that both are set by one write and the order is structural (`params` inside the request object, about 5 more changed lines). Not chosen: the diff is larger, and the write order is now stated here and reviewed.
- Freeing the slot with a plain `try/finally`, keeping one chooser per claimed slot whose callback completes whatever request the slot holds. A delayed request could then claim the freed slot while the old chooser is still open, and Save there would complete the new request, which is this bug again; and `onResult!!` would throw a `NullPointerException` when the old chooser returns while the slot is empty. Replacing `!!` with `?.` removes the exception but not the mix-up.
- Leaving the stuck slot to a separate PR. Until it lands, this PR is worse than master after a QR code view closes while its Save dialog is open: master lets a delayed request replace the cancelled one, so Save in the open dialog completes it and frees the slot, while the guard alone cancels the delayed request and every later one until the app is restarted.
- Keeping `shareFile` after a desktop QR code save: the second Save dialog would open with the image just written selected, and Save there would truncate the image before copying it onto itself.
- Skipping the copy in `copyFileToFile` (common code) when the target is the source: it changes a helper shared with Android for one desktop flow; hard links and Windows symlinks are not caught by comparing canonical paths; and it does not help the database archive (deleted after the save anyway) or encrypted received files (saved from a decrypted temporary copy).
- The same check only in desktop `shareFile`: the image is kept, but the second Save dialog still opens and its Save does nothing.
- Serialising requests with a `Mutex` instead of the guard, so a delayed request gets its own dialog after the open one closes. Now that `key(request)` gives a request made right after another its own dialog, this is about 7-10 changed lines smaller than the guard. Not chosen because it changes behaviour: a double-click on a file, or several downloads finishing while a dialog is open, would open dialogs one after another for the same file, which master never did.
- Writing the desktop QR code image to the temporary folder, as Android does, so that `shareFile` is the single Save dialog. Not chosen: the desktop flow changes from a folder chooser to a Save dialog.

## Not fixed / related

- On macOS a stale panel may stay open. From the OpenJDK sources of the macOS peer (`sun.lwawt.macosx.CFileDialog`, not checked on a Mac), `setVisible(false)` does nothing and `dispose()` does not close the native panel. Then, when the request of an open panel ends without the user closing it (a QR code view closing, as above), the panel stays open; Save or Cancel in it writes nothing, because its callback completes the ended request. A request made while it is open gets a new `FileDialog`; whether that panel is shown at once or after the old one is closed is not known (not tested; no Mac).
- Correctness still depends on `awaitResult` writing `params` before `request` (see "Fix"); holding `params` in the request object would make it structural (see "Alternatives").
- When the user chooses a folder in a Save dialog, the path is built from the file name (`File(res, input)`, `Files.desktop.kt:79-81`), which for a received file is the name the sender gave; whether core's sanitising of that name keeps the path inside the folder was not checked.
- On Linux and Windows the JFileChooser Save overwrites an existing file without asking, in every Save dialog.
- Saving a file onto itself, on master and with this PR, separate from this bug: an encrypted received file saved onto its own path in the app's files folder is overwritten by its plaintext; the database archive saved onto itself is truncated and then deleted; desktop `shareFile` of an encrypted file decrypts onto the chosen path, which may be the source.

## Effect

Desktop only: while a request is pending in a file dialog slot, a further request to the same slot is cancelled instead of replacing the request that the open dialog completes. A received or fetched file stays in the chat to be saved again; a database export has to be run again. The open dialogs have no delayed caller, so there a second request needs a second click before the chooser is shown, and that request is cancelled. A request whose awaiting coroutine is cancelled frees its slot, and on Linux and Windows its dialog is closed; a request made right after another gets its own dialog. Requests made while no request is pending behave as before, except for the order of two internal writes (`params` before `request`), and except that a request which claims the slot in the same frame the previous one ends (for example, a download finishing right after another dialog's Save) now gets its own dialog, where master showed none and left the slot claimed. On desktop the QR code click no longer makes such a second request (`shareFile`), so it shows one folder chooser, as master normally did. Android behaviour unchanged: it has no such dialog state, and its QR code click still shares the image.
