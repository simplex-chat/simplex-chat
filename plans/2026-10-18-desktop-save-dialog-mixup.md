# Desktop: saving from an open Save dialog writes another file's content

## Problem

On desktop some save requests open the Save dialog only after a wait: a file tapped before it was received opens it when the download finishes (`OpenWhenReceivedEffect` → `saveFileLauncher.launch`), a file saved or shared from a linked mobile opens it once the file is fetched (`loadRemoteFile`), and the database export opens it after the archive is written. `DialogState.awaitResult` replaces the pending result and parameters on every call, while the file chooser that is already open (JFileChooser on Linux and Windows, AWT `FileDialog` on macOS) is created once and keeps its parameters. So when such a request arrives while a Save dialog for another file is open, the open dialog still shows the first file's name, but pressing Save completes the second request: the second request's callback writes the second file's content to the chosen path, and the first request never completes.

Reproduced on the master prebuild: download a 115-byte text file and cancel its Save dialog; tap a 40 MB file; click the text file again and keep its Save dialog open until the large file finishes; press Save. The saved "file-A-small.txt" is 40,000,000 bytes, identical to the large file.

## Fix

`DialogState` takes the value its dialog returns on Cancel: `null` for the open and save slots, an empty list for the open-multiple slot. When a request is already awaiting in the slot, `awaitResult` logs a warning and returns that value at once instead of replacing the pending request. The check and the claim are done under one lock, so of two requests at the same instant the dialog is opened for one, and the other is cancelled.

Inside the lock, `awaitResult` now writes `params` before `onResult` (master writes them the other way round). The dialog is shown when `onResult` is set (`isAwaiting`), and the chooser takes its file name once, when it opens; the composable may read `params` again on recomposition, which does not change what the open chooser uses. In the old order a dialog composed between the two writes opens with the previous request's parameters (a file name, or none) while Save completes the new request; writing `params` first removes that window.

The guard is in the slot, so every caller is covered: `FileChooserLauncher.launch` (open and save), `FileChooserMultipleLauncher.launch` and `saveTempImageUncompressed` (QR code save). Every callback already handles a cancel (the database export deletes its temporary archive). The request that arrives second is the one cancelled, whether it is delayed or comes from a click. A click can make a second request before the chooser is shown, because only a shown chooser blocks clicks; and a QR code click computes the QR image before it calls `awaitResult`.

## Alternatives

- A guard at the call site, in the save branch of `FileChooserLauncher.launch` (+1 line, and it would also need a lock: delayed requests run on background threads, so two of them can pass the check together). It leaves `saveTempImageUncompressed` unguarded: if a delayed request claims the Save dialog while a clicked QR code image is being computed, the QR request replaces it: pressing Save completes the QR request, and the delayed request never completes (for a database export, the progress indicator stays shown and the archive is not deleted). Every new caller would have to repeat the check.
- The same guard repeated in `saveTempImageUncompressed` (+1 line). It closes the QR path, but the check is then needed at every caller of `awaitResult`, and the open slots stay unguarded.
- Leaving the QR path open. No content is written to the wrong file, but the delayed request never completes, which is half of this bug.
- Holding `params` and the request in one state value, so that both are set by one write and the order is structural (about 4-6 more changed lines). Not chosen: the diff is larger, and the write order is now stated here and reviewed.
- Serialising requests so a delayed request gets its own dialog after the open one closes. Better for the user, but larger, and it depends on a request made right after another getting a dialog (see "Not fixed").

## Not fixed

- If a slot is left awaiting with no dialog shown, every later request to that slot is cancelled at once, where master leaves it waiting forever. Two pre-existing causes, to be fixed separately: `awaitResult` does not clear the slot when the awaiting coroutine is cancelled, and a request made right after another, with no frame between them, may get no dialog.
- The first cause is reached when a QR code view is closed while its Save dialog is open: the view's coroutine scope (`rememberCoroutineScope`, `QRCode.kt:73`) cancels the coroutine waiting in `awaitResult`, while the Save dialog stays open. From the code (not observed in the app), three things close it without the user closing the Save dialog: a peer connecting through the one-time link shown in the QR code; clicking a desktop notification, which closes all modals (`NtfManager.kt:80` sets `clearOverlays`, `App.kt:111-113` calls `ModalManager.closeAllModalsEverywhere()`); and a mobile scanning the "Link a mobile" QR code, which is shown only while there is no session code (`ConnectMobileView.kt:193`).
- In that state this PR behaves worse than master when a delayed save request arrives. On master the delayed request replaces the pending request, so Save in the open dialog completes the delayed request: the QR code save has no file name, so on Linux and Windows the dialog is a folder chooser and Save stores the delayed request's own file under its own name (on macOS, under the name the user types), and the delayed request then clears the slot, so the slot works again. With this PR the delayed request is cancelled, Save in the open dialog completes the cancelled QR code request, and the slot stays claimed until the app is restarted, so every later request to it is cancelled.
- The second cause was observed on master: clicking a QR code opened a folder chooser for the QR image, and after the image was saved no second Save dialog (`shareFile`) appeared, and Save of a received file afterwards did nothing, from the context menu or by tapping it (recovery after a restart was not tested). The QR code click makes the `shareFile` request right after the image request. This PR does not change the trigger; later saves are cancelled at once instead of waiting forever.
- The fix for both is a separate PR, because a plain `try/finally` in `awaitResult` that clears the slot when its coroutine is cancelled is not enough: a delayed request could then claim the cleared slot while the old chooser is still open, and Save there would complete the new request. Each dialog's callback must be tied to the request it was opened for.

## Effect

Desktop only: while a request is awaiting in a file dialog slot, a further request to the same slot is cancelled instead of replacing the request that the open dialog completes. A received or fetched file stays in the chat to be saved again; a database export has to be run again. The open dialogs have no delayed caller, so there a second request needs a second click before the chooser is shown, and that request is cancelled. Requests made while no request is awaiting behave as before, except for the order of two internal writes (`params` before `onResult`). Android has no such dialog state; unchanged.
