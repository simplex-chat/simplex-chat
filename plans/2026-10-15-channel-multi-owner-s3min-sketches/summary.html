Channels with several owners

The plan lets a channel have up to six equal owners (five while its creator is one): the server that holds the channel's link takes their changes one at a time, so concurrent changes are never lost or undone. The server part and the first chat part are built; the rest waits for your review of the design.

  • For users. Today a channel has one owner, its creator. With the plan any owner can post, edit the channel, change roles, manage relays and destroy the channel; a member becomes an owner only after its security code is verified and it accepts an invitation; owners can remove each other, and the channel keeps working after the creator leaves. Up to six owners, five while the creator is one. overview
  • How. Each owner keeps a copy of the channel's link data, makes its one change and writes it back; the server takes the write only if nobody wrote since, and otherwise sends back the current data for the owner to re-apply its change. The roster, the signed list of member, moderator and admin roles, is numbered on the same server, so relays and members keep today's role protocol. overview
  • What users notice. Owner actions need that server, posting doesn't; a role change takes 1–3 seconds and can be refused for a few seconds after another owner's ("catching up, try again"); a new owner's device connects to the server directly, showing it the device's IP address, and the invitation says so. overview timing
  • Trust. Owners trust each other as the single owner is trusted today: any owner can destroy the channel or lock the others out. The design guards against dishonest relays and a server that withholds the link or serves an old copy. overview risks
  • Cost and order. About 112 hours of work, building, testing and reviewing included. The server part and the first chat part (new messages and data, needing nothing from the new server) start side by side; then the chat core moves onto the new server, with the iOS, Android and desktop apps after the core parts they need, built and tested on GitHub's runners. The riskiest part, role changes by several owners reaching every member in order, is mostly tested before any app work in the planned order. plan risk

Decided

  • An owner's write keeps the shape of today's write and adds the hash and the owner keys, for now. That leaves room for six keys: up to five owners while the creator is one, six after it leaves. overview plan
  • The server refuses today's write on a link several owners write, so a stale write, or one from an older app, can't erase the other owners' changes. Single-owner channels are unaffected. overview plan
  • A write refused because the data changed is answered with the current data, so no read follows it. overview plan
  • Each owner writes from its stored copy of the link data; it reads before a write only without a usable copy or to confirm a refusal the copy shows, and also at channel open and app start. It costs one database column; owners read the link less, and the server learns nothing new, since a refused write's data comes back over the connection the write already uses. overview copy privacy
  • The server part starts from the server code version this branch pins and adapts the design to it. overview plan

For programmers

What the pictures don't show; the plan's sections have the rest. Each link opens the cited lines of the overview or the implementation plan at the commit this page describes.

  • Wire. SMP v24, the server protocol's next version: LSWP linkId hash [keys] (fixedData, userData) answers OK, or LCUR (current) with the stored user data when the hash differs; LSET gets AUTH on a queue with several keys; not proxied. Chat protocol v23: x.grp.owner.inv, x.grp.owner.acpt, x.grp.owner.add (invite, consent, commit), x.grp.members.req and x.grp.members.page (member list), linkVersion in x.grp.info. [§4.1, §4.5]
  • Agent. Owners store and write from OwnerLinkData (encrypted fixed data, signed user data, hash); a swap returns LSRSwapped or LSRChanged with the link's data after it, directly or as the LSWAP event of an async command. [§4.2]
  • Chat. A user's command writes with writeChannelLink; background work (finishing a promotion, relays, the count, roster re-sends) runs as link syncs of agent async commands. Both continue with continueChannelLink, which re-derives what is left from the latest data and the database, at most five swaps per trigger. Link data older than the stored linkVersion is ignored, and a read only adds owners or marks revoked ones departed. [§4.4]
  • Roster. Claims come from the complete roster; roster messages from an owner who has since left are still applied in version order; a version by an owner who has left that no relay serves is skipped after a day. [§4.10]
  • Data and API. One migration, nine columns, no new table; /owner invite #<group> <member> and /_owner accept #<groupId> <chatItemId> [direct=on]; refusals as CEChannelLink errors. [§4.16]
  • Risks. The riskiest assumption is that today's roster protocol converges when versions are claimed through the link (tests in S9, S10 and S13); next, that background callbacks re-derived from the latest data are idempotent (T17, in S8). S1 first proves the swap's atomicity and that six keys fit. Trade-offs and residual risks: overview. [§8]
