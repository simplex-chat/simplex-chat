Channels with several owners

The plan lets a channel have several equal owners: the server that holds the channel's link takes their changes one at a time, so concurrent changes are never lost or undone. Nothing is built yet; please confirm the choices below.

  • For users. Today a channel has one owner, its creator. With the plan any owner can post, edit the channel, change roles, manage relays and destroy the channel; a member becomes an owner only after its security code is verified and it accepts an invitation; owners can remove each other, and the channel keeps working after the creator leaves. overview
  • How. An owner reads the channel's link, makes its one change and writes it back; the server takes the write only if nobody wrote since that read, otherwise the owner reads again and re-applies. Role changes are numbered on the same server, so relays and members keep today's role protocol. overview
  • What users notice. Owner actions need that server, posting doesn't; a role change takes 1–3 seconds and can be refused for a few seconds after another owner's ("catching up, try again"); a new owner's device connects to the server directly, showing it the device's IP address, and the invitation says so. overview timing
  • Trust. Owners trust each other as the single owner is trusted today: any owner can destroy the channel or lock the others out. The design guards against dishonest relays and a server that withholds the link or serves an old copy. overview risks
  • Cost and order. About 110 hours: the server and the messaging library first, then the chat core, with the iOS, Android and desktop apps after the core parts they need, built and tested on GitHub's runners. The riskiest part, role changes by several owners reaching every member in order, is mostly tested before any app work. plan risk

For programmers

The rest of the page is reference for the programmers who build it. S3-min is the plan's name for this design: the minimal one that keeps the features of the original, larger design except four optional parts, listed under Trade-offs.

Problem, idea and approach

Problem. Today a channel's creator is its only owner: it overwrites the link data on the link server with LSET, last writer wins, and alone numbers the roster, the signed list of member, moderator and admin roles that relays and members apply in version order [§3, §4.10]. Several owners writing this way would undo each other's changes.

Idea. The link server already orders writes to the link, so each owner change becomes a compare-and-swap: an owner reads the link data, applies its one change and writes it back with a new command, LSWP, carrying the hash of what it read. If another owner wrote in between, the server answers CONFLICT, and the owner reads again and re-applies, five attempts at most [§4.1, §4.4].

Approach. A member becomes an owner only by accepting; owners can remove each other, and any owner, the creator included, can leave. Owners are trusted as the single owner is today, and the design defends against malicious relays and a link server that withholds or serves stale data. So relays handle owner actions as today, without checking them against the link, and relays and members keep today's roster protocol [Ov: intro, Ov: Decisions, §4]. Work an owner does in the background, such as finishing a promotion, is a link sync: agent commands queued on the owner's connection to a relay, each step re-derived from the latest read, so it survives restarts [§4.4].

Terms: the link is the channel's link data on the link server; its write counter, linkVersion, goes up with every swap; the roster version numbers role changes; a link sync is an owner's background work on the link, defined above.

Sources: the overview and the implementation plan, at the commit this page describes. Each bracket links to the lines it cites: [Ov: heading] in the overview, [§4.4] in a section of the implementation plan; T8 and T17 are its tests (§7).

How owners, relays and members stay consistent
  • Reads ignore link data older than the stored linkVersion and only add owners or mark revoked ones departed: a stale read can't undo a promotion, but can make a party take a removed owner as current until its next read; that device can no longer write the link, and an honest one sends nothing [§4.4, §5].
  • Roster: an owner may claim the next roster version on the link only while it holds the complete roster at the current one (the picture Two owners change roles). An owner that sees another owner's role change above its version fetches the roster from the relays; roster messages from an owner who has since left or been removed are still applied in version order; an undelivered own roster is re-signed at the next version [§4.10].
  • Relays accept from a departed owner only its leave and roster messages up to the link's roster version. Relays and members skip an x.grp.info older than their linkVersion; relays still forward it [§4.12, §4.13].
  • Link syncs run in the main app only, at most five swaps per channel per trigger. The first current owner in the chain publishes the subscriber count, batching joins over a minute [§4.4, §4.11, §4.15].
Trade-offs

Trade-offs [Ov: Trade-offs users notice, Ov: Decisions]:

  • Owner actions need the link server, posting doesn't; a role change takes 1–3 s and can be refused for a few seconds after another owner's.
  • The link server learns when owners act and how many there are; a new owner's profile reaches every subscriber, and its member list comes from one relay, without profile pictures (a malicious relay can add made-up subscribers to it, never members with roles [§5]).
  • The link orders profile, role, owner and relay changes, leaving and destroying, each announced after its write lands; posts, moderation, blocks, subscriber removals and invitations are sent as today, outside the link [§5]. Not built: cancelling an invitation, merging two profile edits field by field, a tie-break between equal roster versions, retiring the creator's root key.
  • Older apps and servers: promotion needs every relay on chat protocol v23 and the link server on SMP v24. Older members reject a new owner's messages until they upgrade; older joiners take every owner the link lists as an owner, removed ones included, though those keys can't write the link. A channel's link writes switch to the swap at its first accepted invitation and stay as today until then; a single-owner creator also reads the link before leaving or destroying, and a failed read refuses the leave [§4.3, §4.9, §4.14, §5].
  • A promotion wins over a concurrent removal or leave of member M (decided, with nothing done for it). The link decides who is listed as an owner; what each party does depends on which message it applied first [§4.8]:

Relays, members, ownersrefuse the commit; take M as an owner at the next read; relays have dropped their connection to MM is an owner; an admin's later removal is refused, an owner's is applied and the next read makes M an owner again

The remover's device always applied the removal first. The owner-remover cells follow today's checkRole, which the plan keeps; test T8 covers only the removal-first order.

Residual risks

Residual risks [Ov: Residual risks, §5]:

  • A link server ignoring the compare-and-swap can lose writes or split roles, but can't forge.
  • A removed owner on modified software acts as an owner through a relay until the relay learns of the removal (the announcement, or its next 15-minute check), including inflated role versions that block later role changes there and at its members. A relay that learned from its check still accepts its new role events up to the link's roster version, and members apply them; with a colluding link server the removed owner can serve forged link data.
  • Any current owner can destroy the channel or lock the others out.
  • A role change no relay serves (author lost or removed first, or its only relay failed) blocks other owners' role changes while a lost author is still an owner. Once it is removed, the others wait up to a day, then one owner skips its version and carries on from its own roster, which every device then takes: role changes from that version that some devices had already applied are undone there, and so are that author's earlier changes the skipping owner never received, wherever they were applied.
  • A remover crashing after its swap sends no announcement; others learn at their next read.
  • A creator restored from a backup older than its first promotion acts as the single owner until it leaves or destroys, and its role changes can collide. A downgraded server keeps the owner keys but can lose the data of owner-changing writes since its last start, stops multi-owner writes and accepts LSET again; on an upgraded server a creator on an older app can't change the link.

Risks [§8, Ov: Not verified, size]: the riskiest assumption, which tests in S9, S10 and S13 check, is that today's roster protocol converges when versions are claimed through the link from complete rosters and departed owners' roster messages are still applied. The next is that background callbacks, re-derived from the latest read and the database, are idempotent; one that isn't would send twice or never (test T17, in S8). S1 first proves the swap's atomicity and the computed 50-owner size; the 100,000-member catch-up is an estimate. Postgres is covered by the Haskell tests, not by the app runs.

Open in plan §9, asked under Questions for you: the two design questions, which S1 builds as recommended unless you choose otherwise: LSWP sending only the user data, which leaves room for about 50 owner keys (computed from the encoders, not yet tested) instead of 6 [§4.1, Ov: Not verified, size], and refusing LSET on multi-key queues, a server behaviour change that stops stale or downgraded single-owner writes from erasing other owners. A third, decided on 26 Oct: the server design was written against an older simplexmq, which has since dropped its journal store and Postgres queue cache, so S1 builds the swap for the two stores left and updates the design's code references [§9].

API, commands and apps
  • /owner invite #<group> <member> (APIInviteGroupOwner) needs the member's security code verified (only this catches a relay substituting the member's key), relays on chat v23, the link server on SMP v24 and a chain under 50 entries [§4.6].
  • /_owner accept #<groupId> <chatItemId> [direct=on] (APIAcceptGroupOwnerInvitation): the device then talks to the link server directly, revealing its IP address; private routing asks first, and settings forbidding direct connections refuse [§4.6].
  • In multi-owner mode role changes, and removals of members, moderators and admins, claim the next roster version on the link; removing an owner and leaving write the link first; destroying deletes the link queue first. A profile edit is refused if the link's profile differs from the device's at the edit's start; the apps also refuse a save over a profile changed while editing [§4.8–§4.14].
  • Apps, iOS then Kotlin, ~380 lines each: Owner in the role picker via verification, the invitation, Remove owner, Leave, and the link and relay screens for every owner. Group-link commands are refused in channels [§4.14, §6.1].
