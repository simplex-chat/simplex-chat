# SimpleX names store: the API contract

This is the HTTP API that StoreService serves to the names webapp at simplex.domains, under `/api` on the page's own origin. It is authoritative for both implementations:
- the Haskell service (`apps/simplex-store-service`, plan [`2026-10-09-names-web-store-plan.md`](2026-10-09-names-web-store-plan.md) stages 3 and 4, tasks in [`2026-10-21-store-service-tasks.md`](2026-10-21-store-service-tasks.md));
- the webapp's mock (`simplex.domains/webapp/dev/mock/service.ts` and `dev/mock.ts`), which drives the real contracts on a local chain and is what the webapp is tested against.

It starts from what the mock implements (simplex.domains `sh/names-webapp` 2bea31b). Where the mock and the plan differed, the choice made here follows the owner's decisions of 2026-10-15, 2026-10-20, 2026-10-21 and 2026-10-22, the owner's answers of 2026-10-21 to the design questions, and the manager's rulings on the first review round. Each difference, with what must change in the mock and the page, is in [Appendix A](#appendix-a-mock-and-page-vs-plan). Error tags are indexed in [Appendix B](#appendix-b-error-tags).

The words used (owner code, commitment, intent, sponsor, sealed, phase, long poll) are defined in the spec, [Words used here](2026-10-09-name-codes.md#words-used-here).

## 1. Conventions

### Transport

- JSON bodies with `content-type: application/json`. Every answer has `cache-control: no-store` and a `Date` header. The page sets its clock from `Date`, and signs timestamps and deadlines by it.
- An error is `{"error": "<tag>", …}` with the status in Appendix B. Some tags carry more fields (`price`, `revert`).
- A rate limit answers `429 {"error": "rate_limited"}` with `Retry-After` in seconds.
- An unknown path is `404 not_found`; a known path with another method is `405 method_not_allowed` with `Allow`.
- Requests without a body (GET, cancel, retry) take none. A POST with a body that is not a JSON object is `bad_request`.

### Who may see an order

An order is disclosed (its ids, label hash, owner, `sealed`, payment address or `clientSecret`) only to a request that proves it made the order:
- holding the order's id: `GET /api/invoice/:id`, `GET /api/registration/:id`, and the requests on `/api/registration/:id/…`;
- sending every field of the order again exactly, with the owner's signature (a resend, section 5);
- an owner signature with a fresh timestamp: `find` (section 8).

Any other request that meets an existing order is refused with a tag that names nothing (`409 order_exists`). Commitments are public on chain once committed, so a commitment alone proves nothing.

### One request at a time per name and per code

The service serializes the requests that create or change an order:
- `POST /api/invoice` (a name), `POST /api/name/register`, `/reveal`, `/name`, `/spend` and `/retry` run one at a time per label hash (`/name` holds the old and the new label hash, taken in hash order; `/spend` holds the new name's);
- every reservation, release and spending of a prepaid code runs one at a time per code, and reserving is one conditional update (`unused` and not reserved → reserved by this registration) in the transaction that creates, moves or requeues the registration;
- every hold, spending and refund of a balance runs one at a time per balance (section 8), after the label hash's turn and never with a code's;
- every write to a registration is a compare-and-set on the `version` it read (section 6). A request that loses the race changes nothing and answers `409 {"error": "registration_changed", "registration": {…the current view}}`, on every endpoint that writes a registration (the reveal, `/name`, `/retry`, cancel), so the page always follows the current state.

The database backs this with unique constraints: one live registration per commitment, one live registration per owner and label hash, one registration per reserved code, one holder per balance. A registration is live while it can still lead to a registration of its name: `unpaid` with an open invoice, `queued`, `committed`, revealing or registering, and `failed` (retry is allowed). A `registered` order is not live, so the same wallet can order the name again after it lapses; a `taken` order is not live. `live` is a stored flag, and every transition that changes it does so in the same transaction.

In one transaction, rows are locked in this order: the invoice, then the registration, then a prepaid code or a balance. A late credit is its own transaction: the invoice, then the order's balance. Rows a transaction inserts are new and wait on nobody, so `/spend` may insert its invoice and order after closing a holder (which releases that holder's balance row) and before writing the balance again.

**An overdue order is closed by the next order.** When a new order from the same wallet and name meets a live order whose open invoice has passed its expiry time with no money received (the poller may not have marked it yet; a funded invoice is never closed this way, as the sweep never expires one), the new order closes it inside its own transaction, under the label hash's turn: the old invoice becomes `expired`, its registration loses `live`, and only then is the new order inserted. The provider's cancel of the old invoice is sent afterwards, best effort, as the poller would. Settlement queues a registration only while it is still live; a payment that arrives for a closed order is a late payment (it stays `unpaid`, and its confirmed money is credited to that order's balance, section 8; owner, 2026-10-22), never a second live order.

### Formats

| Field | Format |
|---|---|
| `labelHash`, `commitment`, `secret`, `:hash` | `0x` and 64 lowercase hex. Anything else is `bad_request` |
| `owner` in order bodies | an EIP-55 checksummed address. In `find`, any case |
| `signature` | `0x` and 130 lowercase hex: 65 bytes `r ‖ s ‖ v`, `v` 27 or 28, `s` at most half the curve order (low s). Else `bad_request` |
| `codeHash` | unpadded base64url SHA-256 of the canonical code: 43 characters |
| `length` | the label's length in characters, an integer |
| `duration` | seconds, an integer (section 1, Term) |
| `price`, `amount`, `amountPaid`, `fromBalance`, `/spend`'s `balance`, a balance's `amount` and `refunded` | US cents, an integer |
| `cryptoAmount…` | a decimal string |
| `revealAfter`, `revealBefore`, `expiresAt` of a registration or a name, `termStart`, `timestamp`, `deadline` | Unix seconds, integers |
| `gracePeriod` | seconds, an integer |
| `expiresAt` of an invoice, `createdAt`, `settledAt` | ISO 8601 UTC, `2026-10-21T09:15:00Z` |
| `version` | a registration's change counter, an integer |
| `terms` | 1–48 characters of `A-Za-z0-9._/-`, else `bad_request`: the terms version, with `/community` for a community name (section 1, Terms) |

### Sizes

| Limit | Value | Refused with |
|---|---|---|
| A label | 6–63 characters: `a-z 0-9 -`, each hyphen between letters or digits | `invalid_name` (length), `bad_request` (characters, at the reveal) |
| A link | one SimpleX short link: a contact address `https://<host>/a#…` or `simplex:/a#…`, a channel `https://<host>/c#…` or `simplex:/c#…`; at most 4096 bytes of UTF-8 | `invalid_link` |
| Links per key | at most one `simplex.contact` and one `simplex.channel` | `invalid_link` |
| `sealed` | at most 11095 characters | `bad_request` |
| A request body | 16384 bytes on `/api/invoice`, `/api/name/register`, `/api/registration/:id/name`, `/spend` and `/reveal`; 8192 bytes elsewhere | `bad_request` |

The mock reads every body up to 16384 bytes. A body the page builds is never near either cap. The page and the service check links against the same vectors (the webapp's `src/names.ts` cases, copied into the service's tests).

### Term

- A name is paid for `years` years. The search answer gives `years` (2 at launch, the service's setting) and, for a prepaid code, the code check gives its own `years`.
- `years` is at least 2, for the setting and for every prepaid code: the controller refuses a duration under 730 days (`MIN_REGISTRATION_DURATION`), and the free days end on 1 January 2027. The service refuses to start with `years` below 2, and the operator's commands refuse to issue a code for fewer than 2 years.
- The term starts on `termStart`, 1 January 2027 00:00 UTC, which the search answer gives. Until then the days are free.
- The contract registers for a duration from the block's time, so the page builds: `duration = years × 31536000 + max(0, termStart − now)`, with `now` by the service's clock (`Date`). A year is 365 days, as the price oracle counts it.
- The service checks it on every order, register and retarget: `duration − years × 31536000` must be within `term_slack` (1 hour) of `max(0, termStart − now)`, and never negative. Else `bad_request`.
- The end date the page shows before registration is `max(termStart, now) + years × 31536000`. Once `registered`, it shows the view's `expiresAt`, which is later by the time from the order to the register: the duration is fixed in the commitment, and the buyer gains the delay.
- Years of 365 days cross leap days: for an order before 1 January 2027, 2 years end on 31 December 2028 (`1861833600`), 5 years on 31 December 2031. The page shows these real dates, not calendar years (owner, 2026-10-21).
- A new order for the same name builds a new commitment with the current `duration`. So Get a new invoice and Order the name again send a new commitment; a resend after a lost response sends the same one.

### Prices

- Prices come from the chain. The service quotes `controller.rentPriceUSD(label, years × 31536000).base`, in attoUSD, divided by 10^16 to cents.
- The service never has the label at search, and the deployed `SimplexPriceOracle` prices by length only (`priceCentsPerYear(label.strlen())`, no premium). So it calls `rentPriceUSD` with a placeholder label of `length` letters `a`. The label never reaches the RPC node this way.
- The launch list (owner, 2026-10-21) is $100, $200 and $400 for 2 years: `setPrices` with base 5000 cents a year, 7 letters 10000 and 6 letters 20000. There are no per-name prices.
- Only the paid years are charged. The free days until `termStart` cost the buyer nothing; the sponsor's allowance pays their prorated price at registration.
- An order states the price it saw. A different chain price answers `409 {"error": "catalog_changed", "price": <cents>}`.
- An order's price is fixed when it is made (or retargeted). The reveal and the register compare no price.

### Chain reads

- A failed chain read is the RPC node not answering, answering an error, or timing out (10 s per call). It changes nothing.
- It answers `503 provider_unavailable`, except in orders, `/api/name/register`, `/name` and `/spend`, where it answers `503 name_check_unavailable`. The page reads `provider_unavailable` from `/api/invoice` and `/spend` as "this payment method is unavailable", so orders need their own tag.
- In the registration view, a failed read of `intentNonce` does not fail the view: the field is null and named in `unread` (section 6).
- A revert that is the answer is not a failure: `ownerOf` of a name nobody holds means "not held".

### Terms and community names

The buyer agrees to the terms on Check your order, and the signed order records which terms (owner, 2026-10-23).

- **The terms version** is the service's setting `[names] terms_version` (1–32 characters of `A-Za-z0-9._-`), with `[names] terms_url`, the page the checkbox links to. The available search answer carries both, as `terms: {"version", "url"}`. They change only with a restart.
- **Community names** are a list the operator keeps in the service's ini, section `[community]`, one line per name: `<label> = <what it is for>`, for example `bakers = bakers and bakeries in Portugal`. Each label must pass the label rule (section 1, Sizes) and be listed once; each text is one line of 1–200 characters with no control characters; anything else stops the service at startup, naming the line. The service keys the list by label hash, so search still never needs the label. It is read at startup; an edit takes effect on restart, for new orders and moves only (an open order keeps what it signed). The service also refuses a `[community]` section without `[names]` and any section header that appears twice in the file (the `ini` parser keeps only the last), and logs how many community names it loaded.
- **`community`**: every search answer (available, registered, being registered here, reserved) and the registration view carry `community: {"for": "<text>"}` for a listed name, else null. The page shows "Community ⓘ" with the name and the popup "This name is for <text>. Its owner agrees to use it for this community, not as the name of one person or business."
- **The signed terms.** Every order (`/api/invoice` for a name, `/api/name/register`, `/spend`) and every move (`/name`) carries `terms` and signs it: the version for a name not on the list, and the version followed by `/community` (`2026-10-23/community`) for a listed name, which records that the buyer ticked the community wording ("I agree to SimpleX name terms and will use this name for its community."). One terms document and one version serve both; the suffix is the community agreement, not another version. The service expects exactly that value for the name at the time of the request; any other value (an old version, or the wrong variant because the list changed) is `409 {"error": "terms_changed", "terms": {"version", "url"}, "community": {…} or null}`, from which the page shows the checkbox again and signs anew.
- **Stored and resent.** The registration stores the `terms` it was ordered or last moved with. `terms` is in `order_hash`, and an exact resend is answered before the terms check, so a lost answer is safe even after the version changed. A move stores the new name's `terms`; the original `order_hash` stays.
- **When the page asks** (manager's ruling, 2026-10-23): before every signature for a name the order has not agreed for (a new order, a spend, a move to a different name) the page shows the checkbox, with the community wording for a listed name. A signature for the same name again (pay again after an expired invoice, spend a balance again, a move without links) reuses the order's `terms` without asking only when they equal the current terms for that name; otherwise it asks first.
- **Signature vectors** for these messages are in Appendix C, which both implementations reproduce byte for byte.

### Codes-only mode

Before the full launch, register.simplex.domains opens to early investors with prepaid name codes, and nobody can pay for a name. The service's setting `[names] codes_only = on|off` (default `off`, read at startup) turns this on and off, with no rebuild of the page.

- **The page learns the mode from its shell.** The names build's `index.html` has `<meta name="simplex-names-mode" content="open">` in its head. With `codes_only` on, the service serves and exports the names shell with `content="codes"`, as it fills the Stripe publishable key; off, or with no `[names]`, the shell is served as built. The badges site's shell never changes.
- **The service enforces it.** With `codes_only` on, `POST /api/invoice` for a name and `POST /api/registration/:id/spend` answer `403 {"error": "codes_only"}` before they read the order, so they change nothing, reach no provider and read no chain. Every other endpoint works as before: search, link previews, code checks, `POST /api/name/register`, the registration view and its polls, `find`, the reveal, `/retry`, `/name` and record edits. Webhooks and the poller still settle invoices already open, and badge purchases are unchanged.
- **Codes for investors** come from the operators' group (`/issue name`, `/bulk name`) or from `//issue name` in the service's `--run-cli`.

### Signatures

- **EIP-712 `RegisterName`**, domain `{name: "SimplexSponsor", version: "1", chainId, verifyingContract: sponsor}`: `RegisterName(string label,address owner,uint256 duration,address resolver,bytes[] data,uint256 nonce,uint256 deadline)`.
- **EIP-712 `SetText` and `ClearRecords`**, domain `{name: "SimplexResolver", version: "1", chainId, verifyingContract: resolver}`: `SetText(bytes32 node,string key,string value,uint256 nonce,uint256 deadline)` and `ClearRecords(bytes32 node,uint256 nonce,uint256 deadline)`.
- **EIP-191** (`"\x19Ethereum Signed Message:\n" ‖ decimal byte length ‖ message`) for orders (section 5), `find`, `/name` and `/spend` (section 8). Their `timestamp` must be within 600 seconds of the service's clock, except on an exact resend.
- All are signed with the owner code's key (`m/44'/60'/0'/0/0` of the BIP-39 seed from the code's entropy). The service recovers the signer and compares it with the owner. A high `s` is refused even though recovery accepts it, since the contracts' `SignatureChecker` refuses it on chain.
- In messages, numbers are decimal; hashes and `sha256(sealed)` (the SHA-256 of `sealed`'s ASCII bytes) are lowercase `0x` hex; `terms` is as sent, just before the timestamp.

### Rate limits

Each limit counts requests per client per minute. It is taken after the route and method match and before any other check, as `limited` does today, and every request counts, whatever its outcome. Values are the service's defaults (Decided, gap 29 of the sequence doc); the mock enforces the `code` limit always (per client by `X-Forwarded-For`) and the others only when told to by `/control/search`.

| Limit | Per minute | Endpoints |
|---|---|---|
| search | 30 | `GET /api/name/:hash` |
| preview | 20 | `POST /api/link/preview` |
| code | 10 | `POST /api/code/check`, `POST /api/name/register` |
| find | 5 | `POST /api/registration/find` |
| records | 10 | `POST /api/name/records` |
| read (existing) | 60 | `GET /api/invoice/:id`, `GET /api/registration/:id`, `POST /api/registration/:id/reveal` |
| create (existing) | 5 | `POST /api/invoice`, `POST /api/invoice/:id/cancel`, `/name`, `/spend`, `/retry` |

Beyond these:
- **Link fetches** have two service-wide bounds, one for search answers (`searchFetchSlots`, 4 at a time) and one for previews (`previewFetchSlots`, 2 at a time), so previews cannot starve search. Each fetch has a 3-second timeout (`fetchTimeout`) and never waits for a slot longer than that: it gives up, and its profile is `unread` (section 2). Profiles that were read are cached 10 minutes per link; an `unread` link is fetched again on the next request. A search reads the chain within 10 s, then its profiles within one more fetch timeout, so it answers within about 13 s.
- **Record edits** have a per-name cap of 10 relayed edits per hour (section 10). Refused requests do not count.

## 2. Search

### `GET /api/name/:hash?length=N`

The page validates and lower-cases the label, then sends its keccak256 and length. The service never gets the label here.

Checks, in order: the search limit; `:hash` format (`bad_request`); `length` an integer in 6–63 (`invalid_name`). Then the chain, by hash:
- the base registrar's `nameExpires(uint256(hash))` and `GRACE_PERIOD`, and the controller's `reservedNames(hash)`;
- for a registered name, the registry's `owner(node)` and `resolver(node)`, with `node = keccak256(namehash(tld) ‖ hash)`;
- when that resolver is the default resolver contract: its `text(node, "simplex.contact")`, `text(node, "simplex.channel")` and `nonces(owner)`.

A name is registered while `nameExpires + GRACE_PERIOD` is not past the latest block. Otherwise it is reserved when `reservedNames` is not 0, and available when it is 0.

**Available:**

```json
200 {"status": "available", "price": 10000, "currency": "usd", "years": 2, "termStart": 1798761600,
     "resolver": "0x…", "sponsor": "0x…", "chainId": 1, "tld": "simplex",
     "community": null, "terms": {"version": "2026-10-23", "url": "https://…"}}
```
- `price`: cents for `years` paid years, from the chain (section 1, Prices).
- `resolver`: the default resolver contract the commitment must name. `sponsor` and `chainId`: the `RegisterName` domain. `tld`: for the node.
- `community`, `terms`: section 1, Terms and community names. Every other answer below carries `community` too.

**Being registered here:** the chain says available while a registration here is `registering` (its register sent, not mined).

```json
200 {"status": "registered", "entities": [], "tld": "simplex"}
```
No owner, records, nonce or chain id. Orders refuse this name with `name_taken`.

A name that is paid for here but not yet `registering` (`queued` to `committed`) still answers `available`, and another wallet may order it; the later of the two ends `taken` with its payment kept as a balance (section 8). Answering otherwise would tell every searcher that the name is being bought before its commitment is revealed.

**Registered, on the default resolver contract:**

```json
200 {"status": "registered",
     "entities": [
       {"type": "address", "kind": "contact", "displayName": "Alice's Bakery", "fullName": "Sourdough and pastries, Lisbon",
        "image": "data:image/jpeg;base64,…", "subscribers": null, "profile": "ok",
        "link": "https://smp8.simplex.im/a#Y8m3…", "deepLink": "simplex:/a#Y8m3…?h=smp8.simplex.im"},
       {"type": "channel", "kind": "channel", "displayName": "Bakery news", "fullName": "Daily bakes and opening hours",
        "image": null, "subscribers": 1204, "profile": "ok",
        "link": "https://smp9.simplex.im/c#Rk27…", "deepLink": "simplex:/c#Rk27…?h=smp9.simplex.im"}],
     "records": {"contact": "https://smp8.simplex.im/a#Y8m3…", "channel": "https://smp9.simplex.im/c#Rk27…"},
     "owner": "0x…", "resolver": "0x…", "recordsNonce": 0, "expiresAt": 1861833600, "gracePeriod": 7776000,
     "chainId": 1, "tld": "simplex"}
```

- `records`: the raw text records, "" when unset. A record set elsewhere may hold several links joined with `;`.
- `entities`: one per link in the records, split on `;` with spaces trimmed, that is a short link of its key's kind; other values make no entity. At most 5 per key (`maxEntitiesPerKey`), counted over the links of the key's kind, the first in the record; the rest make none. Contact entities come first.
- An entity, as the app's connection-plan alert shows a chat:
  - `type`: the record it came from, `address` (`simplex.contact`) or `channel` (`simplex.channel`);
  - `kind`: what the link opens. For a contact address, `business` when the link data says so (`business`, or the profile's `peerType` business), `bot` for `peerType` bot, else `contact`. For a channel link, `channel`;
  - `displayName`, `fullName` (may be ""), `image` (a `data:image/…` URI or null);
  - `subscribers`: a channel's member count from its link data (`publicGroupData.publicMemberCount`), else null;
  - `link`: as recorded; `deepLink`: the chat core's own `simplex:/` form of the short link, which keeps the server as `?h=` (and its port and other hosts), so the app can open it. When the chat core cannot parse the link, `deepLink` is null, `profile` is `unavailable`, and the page opens `link` as it is.
- `profile`: `ok` when the link data was read; `unread` when it could not be read now (no free slot, a timeout, a failed fetch), so searching again may fill it; `unavailable` when the service does not fetch it (section 3, the host rule). Without a profile the entity has `displayName` "", `fullName` "", `image` null, `subscribers` null, and `kind` from the link (`contact` or `channel`); the page shows the default icon.
- The service opens each link with the chat core's connect plan (`APIConnectPlan`), which reads the link data without connecting, within the search fetch bound (section 1).
- `owner`, `resolver`: the registry's `owner(node)` and `resolver(node)`. `recordsNonce`: `SimplexResolver.nonces(owner)`, for the next edit.
- `expiresAt`: the registrar's `nameExpires`; past it the name is in its grace period. `gracePeriod`: the registrar's `GRACE_PERIOD` (90 days), so the name can be registered again from `expiresAt + gracePeriod`.

**Registered, on another resolver contract or none:** the service reads no records from a contract it does not know.

```json
200 {"status": "registered", "entities": [], "records": null, "owner": "0x…", "resolver": "0x…",
     "recordsNonce": null, "expiresAt": 1861833600, "gracePeriod": 7776000, "chainId": 1, "tld": "simplex"}
```

**Reserved:** `200 {"status": "reserved"}`.

**Errors:** `400 bad_request`, `400 invalid_name`, `429 rate_limited`, `503 provider_unavailable` (any failed chain read, including the record reads: a failed read is not "no links").

## 3. Link preview

### `POST /api/link/preview {"link": "…"}`

Shows a link's chat on the Links step and in Edit links.
- Checks: the preview limit; the link is a short contact address or channel link within 4096 bytes, else `400 invalid_link`. Link validity is the shared vectors' alone; the host rule below never makes a link invalid.
- **The host rule**, for previews and for the links of search answers alike, applied by the service before it asks the chat core to fetch:
  - The hosts are the link's servers: the authority of an `https://` link, or the server hosts carried inside a `simplex:/` link. A link with several servers has every host checked; it is fetched only if all pass.
  - An IP literal is checked as it is, a name by resolving it. A private, loopback, link-local, unique-local (`fc00::/7`), shared (CGNAT, `100.64.0.0/10`), unspecified or multicast address, among a literal or any resolved address, means no fetch. A public IP literal passes: SimpleX servers may be addressed by IP.
  - A `.onion` host and a name that does not resolve mean no fetch.
  - A link not fetched under this rule is still a valid link: its profile is `unavailable`.
  - The check is best effort: the chat core resolves the host again when it connects, so DNS rebinding between the two lookups remains possible. The guard against it is in the deployment: an egress rule denies the service's outbound traffic to the private ranges above (plan, stage 6).
- The fetch runs within the preview bound of section 1 (`previewFetchSlots`, 3 seconds each, cached 10 minutes). With no free slot within the timeout, the profile is `unread`.
- `200 {"type": "address", "kind": "contact", "displayName": "…", "fullName": "…", "image": null, "subscribers": null, "profile": "ok"}`: an entity without `link` and `deepLink`, fetched as in search.
- A link whose data was not read is answered as in search, with an empty profile and `profile` `unread` or `unavailable`. The page accepts the link either way.
- Errors: `400 bad_request`, `400 invalid_link`, `429 rate_limited`.

## 4. Codes

Codes are entered only on the Check your code screen, opened from the top bar. Two kinds parse from the same field (the core `NameCode` sum type, mirrored in the page's `code.ts`):
- a **prepaid code**, `SN<length>-…`: the length in one or two ASCII digits (6–63; `SN6` to `SN9` in use), then 20 Crockford base32 characters with a Luhn mod-32 check. It pays for one name of at least that many letters, for its `years` (at least 2). The service's table, not the text, decides what it covers.
- a **name code** (owner code), `SN-` and 30 characters: the key of a name bought here. It adds that name to Your names.

The page tells the kinds apart and catches a typo (a failed check character) without a request. Nothing about codes is sent at checkout: a prepaid code applied on Check your code makes the search answer's price $0 and pays at `/api/name/register`.

### `POST /api/code/check {"code": "SN8-25X6F-6JDNM-8C59E-HDHJD"}`

Says what a prepaid code covers, without spending it.
- Checks: the code limit; the code parses as a prepaid code, else `400 code_invalid`; its hash is in the table, else `400 code_invalid`. Not 404, which the page reads as `not_found` whatever the body.
- `200 {"minLength": 8, "years": 5, "state": "unused"}`, with `state` one of `unused`, `reserved` (held by an unfinished registration, including one `failed` and waiting for Try again), `used`, `revoked`, `expired`, `unpaid`.
- The answer names no registration, even for `reserved`: a code may have changed hands, and holding it proves nothing about an order. The page links "Code in use" to an order only from its own storage.
- Errors: `400 bad_request`, `400 code_invalid`, `429 rate_limited`.

### What Check your code shows

| Answer | How the page gets it | Verdict |
|---|---|---|
| Prepaid, usable | check: `state: unused` | "Prepaid code: it pays for a name of 8 or more letters, for 5 years." The code is kept in Your names and applied to searches |
| Prepaid, reserved | check: `reserved` | "This code is being used for a name now", with a link to the order when this browser holds it |
| Prepaid, used | check: `used` | "This code was already used" |
| Prepaid, revoked | check: `revoked` | "This code is not valid: SimpleX withdrew it" |
| Prepaid, expired | check: `expired` | "This code has expired" |
| Prepaid, unpaid | check: `unpaid` | "This code is not paid for yet" |
| Prepaid, unknown | check: `400 code_invalid` | "This code is not valid: SimpleX did not issue it" |
| Name code, with its names | `find` (section 8): `200`, then each entry's `sealed` opened with the code | "Name code of alicebakery.simplex", and Add to Your names |
| Name code, no orders | `find`: `404 not_found` | "No order was found for this code" |
| Name code of another order | `find` lists an order whose `sealed` does not open with the code, or whose label does not hash to its `labelHash` | "This code does not open the order" |
| Not a code | the page: no `SN` code parses | "This is not a SimpleX names code" |
| Mistyped | the page: the check character fails | "Check it for a mistyped character" |
| Rate limited | `429` with `Retry-After` | "Too many checks just now", with the wait |
| Could not check | `503`, a network failure, or a timeout | "The code could not be checked. Try again in a moment." |

### Prepaid codes in orders

`/api/name/register` (section 5), `/name` for a code order (section 8) and `/retry` (section 9) check the code again, under the per-code serialization, and refuse one that cannot pay, with the same tags:
- `400 code_invalid`: unknown or revoked;
- `409 code_used` (spent, including by another order after the sweep released it), `409 code_reserved` (another registration holds it), `409 code_expired`, `409 payment_pending` (unpaid);
- `409 code_not_covering`: the name is shorter than the code's `minLength`.

A code still reserved by its order stays good for that order: a later revocation or expiry does not stop that order's Try again or `/name`. `code_invalid` and `code_expired` apply only to a code that has to be reserved again after its release.

A code order keeps its code reserved while `failed`, for Try again. A daily sweep releases it once the registration has been `failed` for 30 days; a later Try again or `/name` reserves it again if it is still unused, else answers the tag above. A `taken` code order releases its code at once.

## 5. Orders

### The order fields

Both kinds of order, the retarget and the spend from a balance carry:

| Field | Meaning |
|---|---|
| `labelHash`, `length` | keccak256 of the label, and its length |
| `duration` | the term in seconds (section 1, Term) |
| `owner` | the owner code's address; the retarget and the spend send none, as theirs is the order's |
| `commitment` | `makeCommitment(Registration{label, owner, duration, secret, resolver, data, reverseRecord: 0, referrer: 0})`, built by the page |
| `sealed` | the label and links encrypted under the owner code; required |
| `terms` | the terms the buyer agreed to (section 1, Terms) |
| `timestamp`, `signature` | the owner's EIP-191 signature over the order (below) |

- `secret = HMAC-SHA256(BIP-39 seed of the owner code, "simplex.domains commitment " + label)`.
- `resolver` is the search answer's.
- `data` is one `setText(node, key, link)` call for each of `simplex.contact` and `simplex.channel` that has a link, contact first, none without links. The links are chosen on the Links step, before the order, and cannot change inside it except through `/name` (section 8).
- `sealed`: the JSON `{"label", "contact", "channel"}` (each a link or ""), AES-256-GCM under `HMAC-SHA256(seed, "simplex.domains sealed")` with a random 12-byte IV, as unpadded `base64url(iv ‖ ciphertext ‖ tag)`. The service stores it unread and returns it.
- The order signature, by the owner code's key, is over `simplex.domains order <labelHash> <length> <duration> <commitment> <sha256(sealed)> <terms> <timestamp>`. It proves the owner, so nobody can place orders in another wallet's name.

### Resends and existing orders

Every order looks for an existing live order (section 1) of the same commitment, or of the same `owner` and `labelHash`, before any chain read, holding the label hash's turn (section 1):
1. **An exact resend:** a stored order, live or not, whose every field equals the request's (`labelHash`, `length`, `duration`, `owner`, `commitment`, `sealed`, `terms`, and `method` and `price` for `/api/invoice`, the code for `/api/name/register`, or the paying order's id, `price`, `balance` and `method` for `/spend`), and the signature recovers the owner. The service finds it by `order_hash`, a hash of exactly those fields in a fixed encoding tagged by the kind of order (never the timestamp or the signature). It is answered with that order as it is now: the invoice view (an expired one included), or `{"registrationId": "…"}`, in any phase. The timestamp's age is not checked on an exact resend, so a lost answer is safe however late it is resent.
2. **Anything else** that meets a live order is `409 {"error": "order_exists"}`, with no other field. The page then finds its own order with `find` (section 8), which proves the owner, and opens it there.

So one wallet never has two live orders for one name, a resend never meets its own registration as `name_taken`, and nobody learns about an order they did not make.

### `POST /api/invoice` (a paid order)

```json
{"kind": "name", "labelHash": "0x…", "length": 12, "duration": 69292800, "owner": "0x014F…9b73",
 "commitment": "0x…", "sealed": "…", "method": "btc", "price": 10000, "terms": "2026-10-23", "timestamp": 1792828800, "signature": "0x…"}
```

Checks, in order:
1. The create limit; the body cap; `kind` is `name` (a badge order is unchanged); with `codes_only` on, `403 codes_only` (section 1, Codes-only mode); formats, `sealed` present and `method` (`card`, `btc`, `xmr`), else `bad_request`; `sealed` at most 11095 characters, else `bad_request`; `length` in 6–63, else `invalid_name`.
2. The signature recovers `owner`, else `bad_request`.
3. Existing orders (above): an exact resend is answered; an overdue order of the same wallet and name is closed first (section 1); anything else meeting a live order is `409 order_exists`.
4. The timestamp within 600 seconds, else `bad_request`.
5. The duration, within the slack (section 1, Term), else `bad_request`.
6. The terms: `terms` must be the current terms for this name (section 1, Terms), else `409 terms_changed`.
7. The chain: a name registered, reserved, or being registered here is `409 name_taken`; a failed read is `503 name_check_unavailable`.
8. The price: the chain price for `years` must equal `price`, else `409 catalog_changed` with the chain's `price`.
9. The payment provider: unavailable is `503 provider_unavailable`.

`200`: the invoice view (section 6) with `registration.phase` `unpaid`. Settlement moves the registration to `queued` only while it is still live; otherwise the payment is a late payment (section 1).

Errors: `400 bad_request`, `400 invalid_name`, `403 codes_only`, `409 order_exists`, `409 terms_changed`, `409 name_taken`, `409 catalog_changed`, `429 rate_limited`, `503 name_check_unavailable`, `503 provider_unavailable`.

### `POST /api/name/register` (paid with a prepaid code)

```json
{"labelHash": "0x…", "length": 12, "duration": 163900800, "owner": "0x7a3C…e51D", "commitment": "0x…", "sealed": "…",
 "code": "SN8-25X6F-6JDNM-8C59E-HDHJD", "terms": "2026-10-23", "timestamp": 1792828800, "signature": "0x…"}
```

The duration uses the code's `years`. Checks, in order:
1. The code limit; the body cap; formats; `sealed` at most 11095 characters (`bad_request`); `length` in 6–63 (`invalid_name`).
2. The code parses as a prepaid code and is in the table, else `400 code_invalid` (a missing or non-text `code` is a format error, `bad_request`, at check 1).
3. The signature recovers `owner`, else `bad_request`.
4. Existing orders (above): an exact resend answers `200 {"registrationId": "…"}`; an overdue order of the same wallet and name is closed first (section 1); anything else meeting a live order is `409 order_exists`.
5. The timestamp within 600 seconds, and the duration within the slack for the code's years, else `bad_request`; then the terms (section 1), else `409 terms_changed`.
6. The chain: `409 name_taken`, or `503 name_check_unavailable`.
7. The code's state (section 4), then its cover: `length ≥ minLength`, else `409 code_not_covering`. Reserving it is the conditional update of section 1, in the transaction that creates the registration.

`200 {"registrationId": "…"}`: the code is reserved for the registration, which is `queued`. The page opens `?registration=<id>`.

### `POST /api/invoice/:id/cancel`

As for badges, with the name's view:
- `200` the invoice view, now `expired`. The service cancels at the provider first and expires its record only after the provider accepted, so a cancel never answers `open`;
- `409 not_open`, `409 funded` (the service has read a payment), `404 not_found`, `503 provider_unavailable` (also when Stripe refuses to cancel an intent already processing).

A cancel that lost to settlement answers `200` with `status: paid`; the page re-reads and opens the registration.

### Repeats

| Request | A repeat of the same body |
|---|---|
| `POST /api/invoice` | answered with the same order, in any phase |
| `POST /api/name/register` | answered with the same `registrationId`, in any phase |
| `POST /api/invoice/:id/cancel` | `409 not_open` once cancelled |
| `/reveal` | `200 {}` once accepted, in that or any later phase |
| `/name` | a body whose fields equal the registration's current ones answers the view unchanged, and counts no move |
| `/spend` | answered with the same order, in any phase: its invoice view, or its `registrationId` when it has no invoice |
| `/retry` | `400 bad_request` once out of `failed`: the page re-reads the view |
| `POST /api/name/records` | the same answer for an edit that was sent: it waits for the same transaction, or repeats its outcome; a refused one is checked anew |

## 6. Following an order

### The registration view

```json
{"id": "t2Jk8RmQ4vXw9NcP3yLb6g", "version": 7, "moves": 0, "linksRefused": false, "phase": "committed", "labelHash": "0x…", "label": null, "owner": "0x…",
 "commitment": "0x…", "sealed": "…", "resolver": "0x…", "sponsor": "0x…", "chainId": 1, "tld": "simplex",
 "years": 2, "duration": 69292800, "price": 10000, "fromBalance": 0, "balance": null, "latePayment": null, "commitTx": "0x…", "registerTx": null,
 "revealAfter": 1792828800, "revealBefore": 1792915140, "intentNonce": 0, "unread": [], "expiresAt": null, "error": null, "community": null, "terms": "2026-10-23"}
```

- `id`: a random 128-bit token in base64url. Whoever holds it can follow the registration and send its reveal and retry.
- `version`: increases with every change the service makes to the registration (phase, label, intent, transactions, reveal times, error). The long polls hold on it. A change of the order's balance is not a change of the registration: it leaves `version` as it is (section 8, Balances).
- `label`: null until the reveal is accepted.
- `years`, `duration`: the term paid for; `duration` rebuilds the commitment on another browser.
- `price`: what the order is worth in cents: the price paid, any part from a balance included, or after `/name` the new name's price, which caps a further move. 0 for a code. A paid order that ends `taken` keeps it as its balance.
- `fromBalance`: the cents paid from another order's balance when the order was made (`/spend`, section 8); 0 when none. A move does not change it, so after a move to a cheaper name it can exceed `price`.
- `balance`: this order's balance (section 8): null until its first credit, then always an object, with `amount` 0 once spent or refunded: `{"amount": 10000, "held": false, "heldUntil": null, "refunded": 0}`. `amount`: the cents left to spend. `held`: an order's invoice holds the balance. `heldUntil`: that invoice's `expiresAt` while no money has reached it, so the hold ends then unless paid; null when not held, and null while held by an invoice that money reached (it holds until its payment settles or the provider closes it, whatever the time; the page shows "in use by a payment being confirmed" and reads the view again). A holder whose invoice is past its expiry time with no money received reads as none (`held` false), as its invoice reads `expired`. `refunded`: the cents support refunded from it, over all its refunds. The holder is not named: whoever holds this order's link gets no other order's id from it. The page knows the holder from its own records (the order it made by `/spend`), or from `find`'s `heldBy` (section 8).
- `latePayment`: null, or `{"waiting": "confirming" | "crediting" | "support"}` while money on this closed `unpaid` order is not all credited to its balance (section 8, late payments). `confirming`: money received, not yet confirmed. `crediting`: confirmed, the credit not yet made (the poller's next pass, or a rate read that is failing for now). In both the page reads the view again. `support`: the credit will not come by itself (an invoice made under `HighSpeed`, an amount that could not be counted in units, a current rate below the floor, or unconfirmed money past the read window, once alerted); the page stops reading and tells the buyer to write to support with the reference. It turns null once all is credited, whatever it said before.
- `community`: the community entry for `labelHash`, as in search (section 1, Terms and community names), else null.
- `terms`: the terms this order signed when it was made or last moved (section 1), null for an order stored without them. The page compares it with the current terms before signing again for the same name.
- `commitTx`, `registerTx`: among the hashes sent since they were last cleared, the one mined with status 1, else the latest sent. Null when none, or when it was judged mined from chain state with no hash known.
- `revealAfter`, `revealBefore`: the commit's block time plus the controller's `minCommitmentAge` and `maxCommitmentAge`.
- `intentNonce`: `SimplexSponsor.nonces(owner)`, read only in `committed`, null otherwise.
- `unread`: the fields left null because their chain read failed (`intentNonce`). The view itself does not fail. The page reads the view again without `seenVersion` (a failed read changes no version), after 5 seconds, then 15, then every 30 seconds while `unread` is not empty.
- `moves`: how many times `/name` has moved this order; at most `max_order_moves` (3).
- `linksRefused`: true once a reveal was refused for its links (section 7), so every browser, not only the one that revealed, offers `/name` with corrected links; false again after a successful `/name`.
- `expiresAt`: the name's `nameExpires`, once `registered`.
- `error`: null, or one sentence for the buyer. It never holds the RPC URL or a raw revert.

### The name invoice view

The badge invoice's fields, with `invoiceId`, `kind: "name"` and the registration, without `badgeType` and `months`:

```json
{"invoiceId": "q7ZpL2dN9xWc4KfR8tYb1A", "status": "open", "amount": 10000, "currency": "usd",
 "expiresAt": "2026-10-21T10:15:00Z", "kind": "name", "registration": {…},
 "address": "bc1q…", "cryptoAmount": "0.00156", "cryptoCurrency": "btc", "requiredConfirmations": 1}
```
- Card: `clientSecret` instead of the crypto fields.
- For an order paid partly from a balance (`/spend`), `amount` is the difference only; the registration's `price` and `fromBalance` give the whole.
- After a payment is read: `amountPaid`, `cryptoAmountPaid`, `cryptoAmountDue`, `paidInFull`, and `settledAt` once `paid`.
- `cryptoAmountDue` is never negative: BTCPay's due goes below 0 on an overpaid invoice, which reads `"0"` (owner, 2026-10-27).
- `paidInFull` is the provider's verdict that the whole amount arrived, on a closed invoice too: an `expired` invoice (expired or cancelled at BTCPay) reads true once BTCPay's `additionalStatus` is `PaidLate` or `PaidOver`, or its due is 0 or less (owner, 2026-10-27). BTCPay never settles an invoice it has closed, so a late payment of the whole amount keeps `status: "expired"` with `paidInFull: true`.
- `status`: `open`, `paid` or `expired` (a cancel leaves `expired`).

### `GET /api/invoice/:id?wait=<status>&seenVersion=<version>&seenPaid=<cryptoAmountPaid>&seenFull=0|1`

The long poll for a paid order.
- Without `wait`, it answers at once.
- With `wait`, it holds while the status is `wait`, the payment marks are `seenPaid` and `seenFull` (each compared only when sent), and the registration's `version` is `seenVersion` (when sent). It answers on any change, or unchanged after at most 30 seconds (the mock: 20).
- An invoice that reads `paid` while its registration is `unpaid` (paid after it closed) is answered at once and never held: there is nothing more to wait for. Its confirmed money is credited to the order's balance (section 8) by the poller, which can come a pass later than the paid status, and leaves `version` unchanged: the page reads the view again until the balance shows it.
- An open invoice past its expiry with no money received reads `expired`; a funded one stays `open` until it settles.

### `GET /api/registration/:id?seenVersion=<version>`

The long poll for any registration, and the only one for a code order. It holds while the `version` is `seenVersion`, up to 30 seconds. A `committed` registration with no reveal past `revealBefore` reads `failed` ("The name was not signed in time").

Both take the read limit. Errors: `404 not_found`, `429 rate_limited`.

### Phases

| Phase | Meaning | Next |
|---|---|---|
| `unpaid` | its invoice not settled while open | `queued` at settlement of an open invoice |
| `queued` | paid, or its code reserved | `committing` |
| `committing` | the commit sent | `committed` once mined, or once `commitments(commitment)` is live |
| `committed` | waiting for `revealAfter` and the page's reveal | `registering` after the reveal; back to `committed` with `label` null when the sponsor nonce moved (`InvalidNonce`); `queued` after `/name`, only once a reveal was refused for its links; `failed` past `revealBefore` |
| `registering` | the register sent | `registered`, `taken` or `failed` |
| `registered` | the name is the owner's, `confirmations` blocks after the receipt | final |
| `taken` | someone registered the name first | final. A paid order's `price` becomes its balance in the same write (section 8); a code order's code is released (section 4) |
| `failed` | the service's retries gave up once none of its register transactions can still be mined (each mined, or its nonce taken by another mined transaction), or the commitment lapsed | `queued` or `registered` after `/retry`; `queued` after `/name`. A code order keeps its code reserved for 30 days (section 4) |

The page follows `failed` too, since another browser can move it on. A `taken` order changes no more; its balance is read from its view.

## 7. The reveal

### `POST /api/registration/:id/reveal`

```json
{"label": "alicebakery", "secret": "0x…", "records": {"contact": ["https://smp8.simplex.im/a#…"], "channel": []},
 "nonce": 0, "deadline": 1792915140, "signature": "0x…"}
```

Gives the service the name, the links and the owner's intent, once `revealAfter` has passed. The page sends it automatically while open, or when the order link is reopened (on another browser, with the name code).
- `records`: at most one link per key, as chosen before the order.
- `nonce`: the view's `intentNonce`. `deadline`: the view's `revealBefore`, after which the commitment lapses anyway.

It runs one at a time per label hash with orders, `/name` and `/retry` (section 1).

Checks:
1. The read limit; the signature's format and low `s` (`bad_request`).
2. With `label` already set: the same label and signature answer `200 {}`; anything else is `bad_request`.
3. The phase is `committed`, else `bad_request`.
4. The label is valid, hashes to `labelHash` and has `length`; at most one link per key.
5. The service rebuilds `data` from the sent links and the commitment from the label, the owner, the stored `duration`, the secret and the default resolver; it must equal the stored commitment, else `bad_request`.
6. The deadline is not past and not before the registration's `revealBefore` (an earlier one would expire before the worker can register); the intent's signer is the owner; `nonce` equals `SimplexSponsor.nonces(owner)` on chain; else `bad_request`.
7. Each link is a short link of its key's kind within the bound, else `invalid_link`.

`200 {}`: the registration keeps `committed` with its label set, and the worker registers. The write is a compare-and-set on the `version` the reveal read; a lost race writes nothing and answers `409 registration_changed` with the current view (section 1), from which the page signs again or follows the new state. A failed chain read is `503 provider_unavailable`. `404 not_found` for an unknown id.

A failed check changes nothing, with one exception: a reveal refused at check 7 records the refusal (`links_refused_at`) on the registration, as a compare-and-set write that bumps `version` and wakes the polls. It can only be recorded after checks 5 and 6 have passed, so the refused links are provably the committed ones and the owner signed them; nobody can trigger it on purpose with links that were never committed. Such links cannot be fixed by revealing again, since they are in the commitment; the page then offers `/name` with the same name and corrected links (section 8).

## 8. Owner-signed requests

These need the owner code, so a link alone cannot use them. Each takes its limit (find; create for `/name` and `/spend`) and answers `404 not_found` for an unknown id.

### `POST /api/registration/find {"owner": "0x…", "timestamp": 1792828800, "signature": "0x…"}`

Finds a name code's orders. Used by Check your code (the name code's verdict and Add to Your names), by an order link opened where the code is not stored, and after `409 order_exists`.
- Message: `simplex.domains find <owner as lowercase 0x hex> <timestamp>`.
- `200 {"registrations": [{"registrationId": "…", "invoiceId": "…", "phase": "registered", "createdAt": "2026-10-21T09:15:00Z", "labelHash": "0x…", "sealed": "…", "balanceSource": null, "heldBy": null}]}`, newest first, one per registration of that owner, retargeted ones included: the 50 newest, and after them every older one holding a balance above 0, since a balance never expires. `invoiceId` is null for an order without an invoice: a code order, or one paid wholly from a balance. Balances are read from each order's view, not from `find`. `balanceSource`: the id of the order whose balance paid this one when it was made, else null. `heldBy`: the id of the order whose invoice holds this order's balance, else null, read as the view's `held` (an overdue holder with no money reads null). `find` proves the owner, so these ids go to nobody holding only a link; a browser that restored the name code learns from them which order a balance paid and which holds it. `labelHash` and `sealed` let the page name every order with one request: it opens `sealed` with the code and checks the label's hash.
- Orders are signed by their owner (section 5), so only the owner code's own orders are listed.
- `404 not_found` when the owner has none. `400 bad_request` for a wrong signer or a stale timestamp. `429 rate_limited` (find limit).

### `POST /api/registration/:id/name` (another name, or other links)

```json
{"labelHash": "0x…", "length": 9, "duration": 69292800, "commitment": "0x…", "sealed": "…", "terms": "2026-10-23", "timestamp": 1792828800, "signature": "0x…"}
```

- Message: `simplex.domains name <registrationId> <labelHash> <length> <duration> <commitment> <sha256(sealed)> <terms> <timestamp>`. An `owner` in the body is ignored. `terms` are the new name's (section 1, Terms): a move reaches a name the buyer has not agreed for, and a community name needs the community wording.
- A body whose fields equal the registration's current ones, `terms` included, is a repeat: it answers the view unchanged and counts no move. A body that differs only in `terms` is a move, checked like any other.
- Allowed only (manager's ruling, 2026-10-21; `taken` removed by the owner's decisions of 2026-10-22, which keep a taken order's payment as its balance): for any registration in `failed`; and for any registration in `committed` whose reveal was refused for its links (`invalid_link`, recorded by the reveal). Never from a `committed` registration that has had no such refusal, nor from `taken`. Else `bad_request`. The new name may be the same name with other links.
- From `failed`, `/name` first runs `/retry`'s check 1 (section 9) on the current name: a register that went through makes the order `registered`, and `/name` answers `409 registration_changed` with that view, so one payment never registers two names. A failed chain read in that check answers `503 name_check_unavailable`.
- At most `max_order_moves` (3) successful moves per order over its life, counted on success; past that, `409 {"error": "move_limit", "registration": {…the current view}}`. The order stays as it is (`failed`, or `committed` with its links refused); the page shows its state with a line to contact SimpleX support and the order's reference, and support settles it by hand, refunding a paid order.
- The order checks run on the new fields: formats, `invalid_name`, existing live orders for the new commitment or this owner and the new hash, other than this registration (`409 order_exists`), the duration for the registration's `years`, the terms (`409 terms_changed`), `name_taken`, `name_check_unavailable`.
- A paid order (by invoice, from a balance, or both): the new name's chain price for the registration's `years` must be at most its `price`, else `409 {"error": "price_too_high", "price": <cents>}`. A cheaper name lowers `price` to its own and adds the difference to the order's balance (Balances, below), in the move's transaction (manager's ruling, 2026-10-22), which the page says before the buyer chooses.
- A code order: the code is checked again and reserved again under the per-code serialization, as `/retry` does: still reserved by this order, it is kept, even if revoked or expired since (as `/retry` does); released and still unused, it is reserved again; spent elsewhere after the sweep released it is `409 code_used`; held by another order `409 code_reserved`; released and then revoked `400 code_invalid`, or expired `409 code_expired`. The new name must be covered by it (`409 code_not_covering`).
- `200` the registration view: the new hash, length, duration, commitment and sealed, `price` the new name's (a paid order), `moves` one more, phase `queued`, with the label, intent, transactions, reveal times and the recorded link refusal cleared (`linksRefused` false). An old commitment already on chain is left to lapse.

### Balances

A paid order whose name someone registered first keeps what it is worth as a balance, which buys another name (owner, 2026-10-22). There is no code for a taken order.

- **What it is:** US cents, held per order and owned by that order's owner code. Balances are never merged, across orders or wallets: one order's balance pays for one new order at a time. A balance never expires.
- **Credited:** with the order's `price`, in the write that makes a paid order `taken` (paid by invoice, from a balance, or both), so a `taken` order with a payment always has a balance. A move to a cheaper name adds the difference (`/name`, above). A code order gets none: codes carry no money, and its code is released (section 4). A late payment (section 1) adds its money to the closed order's own balance (owner, 2026-10-22). It covers money that arrives on any name invoice after it closed (a difference invoice included), and money received while the invoice was open that it still holds when the provider closes it or a cancel meets it.
  - *Overpayment* (owner, 2026-10-27): on any name invoice that settles, one paid in full in time included, the confirmed crypto above what the invoice asks (BTCPay's payment method `amount` in atomic units, which counts any network fee BTCPay added) is credited to the order's balance by the same credit steps below (its share and rate, numbered with the invoice's other credits, unique), logged at info as an overpayment, and alerted as late money is when it is not credited. An overpaid closed order's late payment is all late money, so the share of all of it is credited.
  - *Only confirmed money is credited.* Stripe: the succeeded amount. BTCPay: when the invoice reads `Settled`, or every payment of its payment method reads `Settled`, all of `paymentMethodPaid`; otherwise the sum of the `Settled` payments' `value`, capped at `paymentMethodPaid`, so the credited crypto never exceeds the received and reaches it exactly once everything settles. Crypto is counted in integer atomic units (satoshi for BTC, piconero for XMR); an amount with a non-zero digit past its unit (trailing zeros are accepted) cannot be counted: that money is not credited and reaches the alert, while the rest of the read, and every badge or on-time order, goes on as before. BTCPay settles a payment at the invoice's own speed policy (`checkout.speedPolicy`, fixed when the invoice was made; a missing or unknown policy counts as `HighSpeed`); a late credit needs at least one confirmation, so money on an invoice made under `HighSpeed` (which settles at zero confirmations) is never credited automatically, whatever the configuration says later, and goes to the alert below.
  - *The price share, at the lower rate* (owner, 2026-10-22 and 2026-10-27): new confirmed crypto is credited as its share of the invoice's `amount` (the price, or the difference of a `/spend` order), at the lower of the invoice's rate and the provider's current rate for the coin against US dollars, the service's currency (BTCPay's store rates, through the configured provider): `floor(amount × units ÷ invoiced units × min(1, current rate ÷ invoice rate))` cents, computed exactly, for BTC and XMR alike. The invoiced units are BTCPay's payment method `amount` in atomic units, network fee included, so the fee BTCPay adds (to every Monero invoice, and to a Bitcoin invoice after a part payment) is never credited: a full late payment credits at most the `amount`, and an overpaid one the share of all it received. The rates and the cents are stored with each credit. Money on an invoice with no invoice rate or no invoiced units recorded is not credited and is logged as an error. A failed rate read credits nothing yet, and the credit is tried again, never at a guessed rate: a failed read is an error, a missing pair, a rate with errors, a rate at or below 0, A rate below half the invoice's (`minCurrentRateFraction`, an owner-visible constant) is not used either: it is logged as an error, as it may be a glitch or a real fall, and the credit waits.
  - *Once:* each credit adds only the confirmed crypto (or, for Stripe, cents) not yet credited from that invoice, under the invoice's lock, with each credit numbered per invoice and unique, so a repeated, growing or reorganised report, or a second instance, never credits twice, and an unconfirmed payment that is replaced or dropped never credits.
  - *Which invoices:* a name invoice whose order is `unpaid` and not live, whatever the invoice's own status (a late `Settled` invoice reads `paid` while its order stays `unpaid`).
  - *When:* after the settlement that recorded the payment commits, by the poller, and again by the poller's pass (at its idle cadence) for any such invoice whose confirmed money is not all credited, so a crash or a failed rate read loses nothing. A cancel by the buyer reads no rate: its late money is credited by the poller. The rate read never runs under the invoice's lock, happens only when crypto is due, and is made once per currency pair per pass.
  - *Pending and the alert:* money received but not confirmed (a mempool payment, Monero confirming with a zero figure) is pending and logged at info. The operator is alerted once per invoice, and again only when more money arrives, when money on a closed invoice is still not all credited and its payment was first seen longer ago than the poller's read window (`settleWindow`, about 72 hours). The alert names the crypto received, confirmed and credited (cents for Stripe), and its reason: unconfirmed money ("refund by hand only a transaction confirmed on chain that BTCPay no longer monitors; one still `Processing` there waits"), confirmed money waiting on a failing rate read ("do not refund; fix the rate read"), confirmed money waiting because the current rate is below the floor (naming both rates: "the coin's price fell by more than half since the invoice; it is never credited by itself; refund by hand only a transaction confirmed on chain" — the floor stops all automatic credit for that invoice for good, so a later price recovery cannot credit money support already refunded), or money that could not be counted in units ("check it at the provider"), money on an invoice made under `HighSpeed` ("the invoice was made under HighSpeed, so its money is never credited by itself; refund by hand only a transaction confirmed on chain"), Monero money whose invoice shows no confirmation threshold of at least 1 (`additionalData.invoiceSettledConfirmationThreshold` 0 or missing: "the Monero plugin shows no confirmation of this money, so it is never credited by itself; refund by hand only a transaction confirmed on chain"; BTCPay does not send a payment's own confirmation count), or card money confirmed but not credited past the window ("confirmed, the credit waits on the poller's credit pass; do not refund; check the service log"). Only one instance logs it, by a conditional write of the alert's mark. The view's `latePayment` (section 6) tells the page which of these it is waiting on.
- **Spent:** only by `/spend` (below), signed by the owner, for a new order of the same owner. When the balance covers the new name's price, the price is spent at once and the rest stays as balance. When it does not, all of it pays, and an invoice is made for the difference.
- **Held:** while that invoice is open, the new order holds the balance: no other spend and no refund takes it. Settlement queues the new order and spends what it held, in one transaction. Whatever closes the invoice unpaid (a cancel, its expiry, the poller's sweep, a next order closing it as overdue, section 1) releases the hold in the transaction that closes the order. A payment that arrives after that is a late payment (section 1): it is credited to the closed order's own balance, and the released balance is not touched. A hold by an order whose invoice is past its expiry time with no money received reads as free (`held` false), and the next `/spend` of that balance closes that order first, in its own transaction, as section 1 closes an overdue order (below). A refund does not: it waits for the poller's sweep to close the holder.
- **Refunded:** only by support, when the buyer writes with the order's reference (its invoice id, or its registration id for an order without an invoice). The operator command `//refund <reference> <cents>` (task plan, T26) sets the balance to 0 and adds the cents to `refunded`, which counts every refund of the balance (one can be credited again later, by a late payment or a move); support then pays them back by hand, by the methods that paid them, which the command lists back through every balance the money came from. A held balance is never refunded, overdue holder or not: the command names the holder and its invoice's expiry, and support runs it again once the poller has closed the holder. There is no refund endpoint, no automatic refund, and no refund address given to the service.
- **Concurrency:** each hold, spending and refund is one conditional write on the balance row (its `amount` as read, and no holder, or this holder), in the balance's turn (section 1). A writer outside the turn (settlement, the poller, a second process running the operator command) can only make the write refuse, never spend a balance twice. Every write is in the transaction of the order change it belongs to, so a restart finds both or neither.
- **Closing a holder** of another name: `/spend` holds the new name's turn, not the holder's. The close is the compare-and-set on the holder's `version` and the conditional expiry of its unfunded invoice (section 1), so it is safe without that turn. A holder no longer live when the transaction runs (cancelled, swept, or closed by its own name's next order meanwhile) is skipped, and the hold write decides; a holder still live that cannot be closed (its money arrived meanwhile) answers `409 balance_changed` with the current balance.
- **Seen in** the view's `balance` (section 6). A balance change leaves the order's `version` unchanged: the page reads the view again, without `seenVersion`, to see it.

### `POST /api/registration/:id/spend` (another name, paid from this order's balance)

```json
{"labelHash": "0x…", "length": 9, "duration": 69292800, "commitment": "0x…", "sealed": "…",
 "price": 20000, "balance": 10000, "method": "btc", "terms": "2026-10-23", "timestamp": 1792828800, "signature": "0x…"}
```

- `:id`: the order whose balance pays. Its owner is the new order's owner, so the same name code owns the new name; an `owner` in the body is ignored.
- Message: `simplex.domains spend <registrationId> <labelHash> <length> <duration> <commitment> <sha256(sealed)> <terms> <timestamp>`.
- The order fields are built as in section 5, for the service's `years`. `price`: the new name's price from the search answer. `balance`: the `amount` of the balance as the page read it. `method`: `card`, `btc` or `xmr`, present exactly when `price` is more than `balance`.

It runs under the new name's label hash turn, then the balance's turn. Checks, in order:
1. The create limit; with `codes_only` on, `403 codes_only` (section 1, Codes-only mode), before the body is read; the body cap; formats, `sealed` present and at most 11095 characters, `price` and `balance` positive integers, and `method` present exactly when `price > balance`, else `bad_request`; `length` in 6–63, else `invalid_name`.
2. The order at `:id`, else `404 not_found`.
3. The signature recovers that order's owner, else `bad_request`.
4. Existing orders (section 5): an exact resend, by `order_hash` over the order fields, the owner, `:id`, `price`, `balance` and `method`, is answered with that order as it is now, in any phase; an overdue order of the same wallet and name is closed first (section 1); anything else meeting a live order is `409 order_exists`.
5. The timestamp within 600 seconds, and the duration within the slack for the service's `years`, else `bad_request`; then the terms (section 1), else `409 terms_changed`.
6. The balance: its `amount` equals `balance` and no open order holds it (an overdue holder counts as none), else `409 {"error": "balance_changed", "balance": {…the current balance, or null}}`.
7. The chain: `409 name_taken`, or `503 name_check_unavailable`.
8. The price: the chain price for `years` must equal `price`, else `409 catalog_changed` with the chain's `price`.
9. For a difference, the payment provider: unavailable is `503 provider_unavailable`. A card difference below the card provider's minimum charge (`minCardChargeCents`, 50) is `400 bad_request`; the page offers only Bitcoin and Monero for such a difference.

Answers:
- `price ≤ balance`: `200 {"registrationId": "…"}`. In one transaction, an overdue holder is closed, the new order is written `queued`, with `price` its name's and `fromBalance` equal to it, and `price` is spent from the balance; the rest stays. The page opens `?registration=<id>`.
- `price > balance`: `200` the name invoice view of section 6, its `amount` the difference `price − balance`, its registration `unpaid` with `fromBalance` equal to `balance`. In one transaction, an overdue holder is closed, and the invoice, the new order and its hold are written.
- When the write refuses (another process changed the balance, or a holder still live could not be closed), the answer is `409 balance_changed`, and an invoice made at the provider is cancelled there, as for an order that lost (section 5).
- A paid order made this way is followed, retried, moved and ends like any paid order; ending `taken`, it gets a balance of its own, its whole `price`.

Errors: `400 bad_request`, `400 invalid_name`, `403 codes_only`, `404 not_found`, `409 order_exists`, `409 terms_changed`, `409 balance_changed`, `409 name_taken`, `409 catalog_changed`, `429 rate_limited`, `503 name_check_unavailable`, `503 provider_unavailable`.

## 9. Try again

### `POST /api/registration/:id/retry`

Only from `failed`, and not when `linksRefused` is set (its commitment fixes the refused links, so a new commit could never register; the page offers `/name` instead), else `400 bad_request`. In order:
1. A register that went through with only its confirmation lost (a mined register with status 1, or `ownerOf` is the owner) makes it `registered`. A code order's code is spent in the same write when it is still unused or held by this order; a code released and then spent, revoked or expired meanwhile leaves the order `registered` and alerts the operator, since the name was already paid with it.
2. A code order whose code was released by the 30-day sweep and is now used, revoked, expired or held elsewhere answers that code error (`409 code_used`, `400 code_invalid`, `409 code_expired`, `409 code_reserved`); it stays `failed`.
3. Otherwise it is `queued` again at no charge, re-reserving a released code. When the sponsor nonce moved since the intent, or a new commit is needed (the stored intent's deadline is the old `revealBefore`, so it cannot serve the new window), the label and intent are cleared, so the page reveals and signs again.

`200` the registration view. `503 provider_unavailable` on a failed chain read. Create limit.

## 10. Editing links

### `POST /api/name/records`

```json
{"labelHash": "0x…", "key": "simplex.channel", "value": "https://smp9.simplex.im/c#…", "nonce": 0, "deadline": 1792832400, "signature": "0x…"}
{"labelHash": "0x…", "clear": true, "nonce": 1, "deadline": 1792832400, "signature": "0x…"}
```

Changes one record of a registered name; the service relays `setTextWithSig` (or `clearRecordsWithSig`) and pays the gas. Edit links in Your names sends one request per changed key, one at a time.
- `key`: `simplex.contact` or `simplex.channel`. `value`: one short link of that kind, or "" to remove it. The whole record is replaced.
- `nonce`: `recordsNonce` from the search answer, one counter for all of the owner's edits. `deadline`: signing time plus one hour.
- The signature is `SetText` (or `ClearRecords`) with the name's key.

Checks, in order:
1. The records limit; formats and the key; the link (`invalid_link`); the signature's format and low `s`; the signer recovered.
2. An identical repeat of an edit that was sent (the same signed body): answered from that edit, as below. Only sent edits are stored; a request refused before sending leaves nothing, so its repeat is checked anew.
3. The deadline after the latest block's time; the signer is the registry's `owner(node)`; the name's resolver is the default `SimplexResolver`; the nonce equals `SimplexResolver.nonces(owner)`. Else `bad_request`.
4. The per-name cap: 10 relayed edits in the last hour, else `429 rate_limited` with the real wait. Only edits that were sent count, so nobody but the owner can use up a name's cap.

Answers:
- `200 {"tx": "0x…"}` once mined; `{"tx": null}` when it was found applied with the applying transaction unknown (another relayer's, or ours with its receipt pruned).
- Whether an edit was **applied** is decided from its own transactions first: one of its sent hashes with a receipt of status 1 means applied, answered with that hash. Only when no receipt is known (pruned, or relayed by someone else) is it judged by chain state: the owner's nonce moved past its nonce and the record holds its value (both keys "" for a clear) means applied, `{"tx": null}`; the nonce moved but the record holds another value means `record_reverted` with `InvalidNonce`. A later edit of the same key can make this second judgment wrong; the page's next nonce re-read corrects what it shows.
- `409 {"error": "record_reverted", "revert": "SignatureExpired"}`: reverted, with the revert's name or null. The nonce is free again for a new body.
- `504 edit_pending`: not mined within 90 seconds, or the chain stopped answering after the send. The edit goes on; an identical repeat waits for it again. The page says the edit may still land and re-reads the name later.
- `503 provider_unavailable`: the chain failed before anything was sent. Nothing is stored; the page may send it again.
- `400 bad_request`, `400 invalid_link`, `429 rate_limited`.

After `{tx}` the page signs the next edit with the next nonce; after `record_reverted`, with the same one; after any `bad_request`, it re-reads `recordsNonce`.
