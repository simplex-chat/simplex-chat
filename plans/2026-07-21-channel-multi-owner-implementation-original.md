# Channel multi-owner — implementation plan

Companion to the design overview (`2026-07-15-channel-multi-owner.md`) — read that first for *why*. This covers *what to build*: data model, migrations, types, protocol events, commands, and sequencing. It is a map for implementing agents, not an exhaustive edit list; trivial wiring (JSON instances, `CMEventTag` cases, view strings) is implied.

The sequencer frame (overview §1) drives everything: link data and owner keys are sequenced by the SMP server via **hash-CAS** (the server keys on a content hash, not a version counter); the roster has no sequencer and converges by a deterministic blob tie-break plus owner-side auto-retry; the subscriber count is cosmetic and any owner corrects it on channel open. Each owner has **one key** — its member key is its `OwnerAuth.ownerKey`, its link-data signing key (the creator's link-data writes stay root-signed) and its link-queue recipient key — so the published owners chain is also the queue's key map.

## Sequencing

Two repos, in order. **simplexmq first** (the relay version bump, hash-CAS on the SMP link queue, the foreign-link write path, the creator's key rotation, forgetting a connection without `DEL`), then **simplex-chat** (data model, events, logic, apps). Multi-owner is gated on the link queue's server negotiating the new SMP relay version; below it, promotion is blocked, not degraded. Relays must accept channels with several owners a release before promotion is enabled (Part 8).

## Part 1 — simplexmq

### 1.1 SMP server — hash-CAS on the link queue

- **Version bump.** New `VersionSMP` `linkCasSMPVersion = 24`; bump **both** `currentClientSMPRelayVersion` and `currentServerSMPRelayVersion` 23 → 24 (`Transport.hs:228-232`). The negotiated session version is the *min* of the two peers' relay ranges, so the client constant must also advance for a client to perceive and exercise v24. `proxiedSMPRelayVersion` stays at 23 (`:241-242`): recipient commands are not proxied. This is the SMP *relay* version (`VersionSMP`, gating `Command`/`BrokerMsg` encoding) — **not** `currentSMPClientVersion`, which rides the client↔client envelope and gates nothing server-facing.
- **The CAS token is a content hash, not a counter.** For link data it is SHA-256 of the stored *encrypted* user-data bytes (nonce + ciphertext, exactly as uploaded — the only thing the server can key on, since it cannot read the content); for `recipientKeys` it is SHA-256 of the encoding of the sorted key set. The server stores `recipientKeys` sorted, so it and the owners hash the same bytes. No server version counters.
- **The CAS is atomic in both queue stores** (the journal message store uses one or the other, `MsgStore/Journal.hs:107-117`). STM store: compare inside the existing STM transaction (`addQueueLinkData`, `QueueStore/STM.hs:168-188`; `updateKeys`, `:200-206`). Postgres store, with or without its cache: an `UPDATE … WHERE` predicate for both — link data `… AND sha256(user_data) = ?` (the blob is not loaded on the normal path: `rowToQueueRec` uses empty placeholders, `QueueStore/Postgres.hs:726-730`), keys `… AND recipient_keys = ?` against the value just read — because the Postgres message store runs with no cache and a no-op queue lock (`MsgStore/Postgres.hs:84`, `:100`), so each command holds its own copy and an in-memory compare would let two concurrent writes both pass. A 0-row update reads and returns the current value.
- **Two new recipient commands** (`Command Recipient`, gated ≥ v24; new tags rather than extending `LSET`/`RKEY`, so version-gating is clean):
  - **`LSETH expectedHash linkId userData`** — hash-CAS on the user data only; the server keeps the stored fixed data. (`LSET` must resend the fixed data byte-identical, `QueueStore/STM.hs:178`, `QueueStore/Postgres.hs:319`, which a promoted owner cannot reproduce: encryption uses a fresh nonce and the read path keeps only the decrypted data.) If `hash(stored) == expectedHash`: store, reply `OK`. Else reply the current encrypted user data. The link-id check stays as in the `LSET` handler (`Server.hs:1575-1579`).
  - **`RKEYH expectedHash keys`** — hash-CAS replace of the key set (as `RKEY`, `Server.hs:1574`). Accept: store sorted, reply `OK`. Else reply the current set.
- **One new `BrokerMsg`** for a rejection, carrying the current value (user data or key set); success is the existing `OK`, and the writer computes the new hash itself. Returning current state on rejection is what removes the writer's pre-read.
- **Auth unchanged:** both are recipient commands, so any key in `recipientKeys` authorises them (`Server.hs:1289-1290`, `:1333-1334`) — this is what lets a promoted owner write. `recipientKeys` stays `NonEmpty` (the parser rejects a zero-length set), so an `RKEYH` can never empty the set; the server has no notion of owner/revocation, so "≥ 1 *live* owner" is a client-side concern (Part 5).
- **Tests** (`tests/ServerTests.hs`, for each queue store): two concurrent `RKEYH` adds both land after one retry; of two concurrent `LSETH`, one is rejected with the winner's blob; `LSETH` cannot change the fixed data; the new commands' AUTH timing matches the existing "Timing of AUTH error" tests.

### 1.2 SMP agent — hash-CAS APIs, foreign-link write, key rotation, local forget

- **Stateless hash-CAS APIs.** Chat keeps the hashes; the agent takes the expected hash and returns either `OK` with the new hash (computed from the exact ciphertext it uploaded — never by re-encrypting, since encryption uses a fresh nonce) or, on conflict, the decrypted current data with its hash. The agent never re-merges (merge policy is chat's). No new agent-store columns.
  - `setConnShortLinkCAS` — synchronous, on the device's own link queue.
  - **An async variant** of the agent's `LSET` command (`setConnShortLinkAsync`, processed at `Agent.hs:2255-2258`), because the creator's link writes mostly run asynchronously: on success the `LINK` event carries the expected hash the command was issued with and the new hash; on conflict a new event returns the expected hash, the decrypted current data and its hash, and chat reconciles and re-enqueues. (The expected hash is the `baseHash` the announcing event needs, overview §2; reading it from chat's state when the event arrives would be wrong after an intervening reconcile.)
  - `updateRcvKeysCAS` — `RKEYH` on the own queue.
  - A local read of the own link queue's recipient id, which the creator puts in the promotion `inv` (today it is reachable only through `getConnectionQueueInfo`, a `QUE` round-trip to the server).
  - A read of whether the link queue's server session supports v24 (connecting if needed; for the own queue and, with the server from the channel link, for a promoted owner), which the inviter checks before sending `inv`. Below v24 the CAS calls fail with `TEVersion`, as the client already gates version-dependent commands on `thVersion` (`directResolveName`, `Client.hs:1078-1084`); a sole live owner then writes with today's `setConnShortLink`/`setConnShortLinkAsync` (blind `LSET`), and with two or more live owners the write fails and is surfaced (Part 8).
- **Foreign-link path** — a promoted owner does not own the link queue. `setForeignLinkData`, `updateForeignRcvKeys` and `deleteForeignLinkQueue` (`DEL`, for destroying the channel) take **explicit credentials**: `SMPServer`, the link-queue recipient id (`linkRcvId`, delivered in the promotion `inv`; it is *not* derivable from the public short link, which yields only the sender-side `linkId`), the `LinkKey`, `rootPubKey`, the owner's member private key (it signs the user data and authorises the commands), and the expected hash. Validation builds the link credentials in memory with the root key set, so `validateOwners` checks that the signing key is a chain key (`Agent/Protocol.hs:1991-2001`) — no `rcv_queues` row and no stored `linkRootSigKey` (`AgentStore.hs:2903` keeps `Nothing` for the creator, whose signing key is the root). Prefer this over materialising a fake `RcvQueue`/`ContactConnection`, which would need an `rcvDhSecret` the owner must not have and risks it subscribing to the creator's queue. Reads use the existing `getConnShortLink`. Foreign calls are **synchronous**: an agent async command delivers its result to a connection, and a promoted owner has no link connection to receive it. They run on a transport session of their own, one per link (the default session is shared per user and server, `mkTSession`, `Agent/Client.hs:1442-1443`), so the link server cannot tie them to the owner's other queues.
- **Creator key rotation** — `setConnRcvAuthKey connId privKey` replaces the own queue's recipient key with the given one in three resumable steps: `RKEYH` adding the new key, persisting it as the queue's `rcv_private_key`, `RKEYH` dropping the old key. A rejected step returns the current set, from which the next step is decided.
- **Forget a connection without `DEL`** — a new local-only deletion; today every agent deletion path sends `DEL` (`deleteConnectionsAsync_`, `Agent.hs:1022-1030`).
- **`Crypto/ShortLink.hs`:** extract `mkOwnerAuth :: OwnerId -> PublicKeyEd25519 -> PrivateKeyEd25519 -> OwnerAuth` (an existing owner key — the promotee's member key — signed by the signer's private key); redefine `newOwnerAuth` on it; export (kills the formula duplicated in chat at `Internal.hs:1680`). The creator signs a new owner with the **root** private key (as `Commands.hs:2757` already does for itself), keeping the chain flat; a non-creator owner signs with its **own member** key (delegation). `validateLinkOwners` is **unchanged** — it accepts "signed by root or an earlier entry", which holds as long as chat writes the owners list in insertion (signer) order (Part 2), so no order-independence change is needed.
- **Tests** (agent): a conflict is returned on the sync and the async path, with the expected hash; a foreign-link write signed by a non-creator owner's key is accepted by a reader; a foreign `DEL` by a non-creator owner deletes the queue; the rotation completes after a crash between each pair of steps.

## Part 2 — simplex-chat: data model & migration

One migration `M20260721_channel_multi_owner` (register in `Migrations.hs` + `.cabal`, both SQLite and Postgres; `chat_schema.sql` regenerates from tests). All new columns nullable / defaulted, so `ALTER TABLE ADD COLUMN` is safe on the STRICT tables and remote-desktop JSON stays forward-compatible.

### `group_members` (columns)
| column | on which rows | purpose |
|---|---|---|
| `owner_auth_sig BLOB` | owners | chain entry signature (with the existing `member_pub_key` = the entry's `ownerKey`, this is the full `OwnerAuth`) |
| `owner_auth_index INTEGER` | owners | **insertion (signer) order** in the chain — a new entry is appended after the entry that signed it; load-bearing for `validateLinkOwners`, *not* a memberId sort |
| `roster_key_version INTEGER` | any member (on an owner's device) | made-at version of the change that set the member's current role; `NULL` for an empty key, which only an event above `groups.roster_key_floor` beats (Part 6) |
| `roster_key_author BLOB` | ″ | that change's author `memberId` (with the version, the member's roster key; a removal's key lives on its `group_revoked_owners` row) |
| `roster_key_prev_version INTEGER`, `roster_key_prev_author BLOB` | ″ | that change's own `prevKey`, which a retry of it carries (Part 6) |
| `roster_key_resent INTEGER` | ″ | whether this owner has already re-sent the current key; cleared when the key changes (Part 6) |
| `roster_key_reported INTEGER` | ″ | one bit per relay-reported trigger: whether (5), and whether (7), has already re-sent the current key — separate bits, so one trigger's re-send never uses up the other's; separate from `roster_key_resent`, which (1)–(3) and (6) skip on; cleared when the key changes (Part 6) |
| `relay_subscriber_count INTEGER` | relays | latest absolute count that relay reported |
| `relay_subscriber_count_ts TEXT` | relays | the relay's own timestamp for that reading (the freshness token; cleared with the count on `GSMemRemoved`/`GSMemLeft`) |
| `promote_invitation_id BLOB` | the promotee (invitee row on O1; own membership on M) | pending promotion |
| `promote_role TEXT` | ″ | offered role |
| `promote_status TEXT` | ″ | invited / accepted / key_added / entry_published / rejected / cancelled / expired — the step reached drives resume and the undo on cancel (Part 5); `entry_published` is set *before* the chain's `LSETH` is issued, so from it on the entry may be live |
| `promote_link_rcv_id BLOB` | M's own row | link-queue recipient id (from `inv`) |

`MemberRoleProposal` (Part 3) is *derived* from `promote_*`, not a stored column. Member cleanup (`getRemovedMembersToCleanup`, `Store/Groups.hs:1375-1382`) skips a row whose `promote_status` is `accepted`, `key_added` or `entry_published`, so a chain interrupted by the member's removal can still be resumed and undone.

In channels a relay's removal keeps its member row (status `GSMemRemoved`) and relay row (`RSInactive`), as a relay's own leave already does (`updateMemberRecordDeleted`, `Internal.hs:2218-2230`), instead of deleting both on either removal path (`deleteOrUpdateMemberRecordIO` and `fullyDeleteMemberRecordIO`, `Internal.hs:2192-2216`; `group_relays` cascades, `chat_schema.sql:839`): the next link write subtracts it (Part 6). `APIAddGroupRelays` then checks for duplicates only among relays whose member row is current (today any `group_relays` row, `Commands.hs:2782-2789`), so a removed relay can be added again; `group_relays` has no uniqueness on the chat relay, so the new invitation gets a row of its own.

### `groups` (columns)
| column | purpose |
|---|---|
| `link_data_hash BLOB` | the hash this device holds for the published link data — the value it CASes on (from its accepted writes, rejections, and events whose base hash matched) |
| `key_set_hash BLOB` | last known key-set hash |
| `published_relays BLOB` | the last published relay list this device knows (from reconcile, accepted writes, and adopted events); a write's relay list is this plus the owner's own in-progress additions minus every relay whose member row on this device is removed or left (Part 6). `NULL` until first filled: a promoted owner reads the link data to fill it before its first write |
| `link_data_version INTEGER` | on every member and relay: the `linkDataVersion` it holds, from accepted writes, applied events and link-data refresh — on a relay only from an applied `XGrpInfo`, since a relay never applies the profile from link data (Part 6) and would otherwise drop the event that carries it; an `XGrpInfo` below it is ignored (Part 4) |
| `subscriber_count_ts TEXT` | the published `subscriberCountTs` this device holds, beside the existing `public_member_count`; non-count writes carry both unchanged (Part 6) |
| `roster_key_floor INTEGER` | on an owner: the roster version it held when it started keeping per-member keys (at the migration, or at its promotion); an empty key loses only to an event above it (Part 6) |
| `roster_blob_sent_version INTEGER` | on an owner: the version of the last roster blob it sent (a change, retry, relay setup or departure re-send); drives the equal-version re-send trigger (Part 6) |
| `stored_roster_owner_id BLOB` | cross-device author `memberId` of the **stored roster blob**, written beside `stored_roster_version` only by `setGroupLiveRoster`; the tie-break key (supersedes the device-local `roster_sending_owner_gm_id` for comparison) |
| `link_rcv_id BLOB` | for this user as a non-creator owner: the link queue's recipient id. With the server and `LinkKey` from the channel link and the existing `root_pub_key` and `member_priv_key` columns, it completes the foreign-link credentials (the creator keeps `GroupKeys` unchanged) |

Do **not** add a `roster_version_owner_id` on the gate `roster_version` — the delta path (`setGroupRosterVersion`) must advance the gate *without* writing any blob author, or a delta would corrupt the blob tie-break (Part 6).

### `group_roster_catchup` (new table)
`(group_id, relay_group_member_id, roster_version)` — on an owner, per relay, the highest roster version that relay has served it as catch-up (Part 6).

### `group_roster_latest_events` (new table)
`(group_id, member_id, roster_version, author_member_id, shared_msg_id, msg_body, msg_chat_binding, msg_signatures, broker_ts)` — on a relay, for each member, a copy of the latest owner's `x.grp.mem.role` or `x.grp.mem.del` carrying a roster version that it applied, kept in the table itself as `groups.roster_msg_*` keeps the stored roster's signed header (`chat_schema.sql:205-210`), so neither message cleanup and chat-item TTL (`Store/Messages.hs:392-394`, `:3621-3623`) nor member cleanup removes it. Served to owners as catch-up and passed back to a blob's author (Part 6).

### `group_revoked_owners` (new table)
`(group_id, member_id, member_key, key_drop_enforced, removal_step, roster_key_version, roster_key_author, roster_key_prev_version, roster_key_prev_author, with_messages, revoked_version, revoked_leave, roster_bound, hold_running_left)` — on every member's and relay's device, one row per removed memberId: every revoked owner, and every member removed by an applied `x.grp.mem.del` or by an owner-signed one whose target this device does not know (a removal can arrive before the promotion it revokes, through a different relay — overview §6). It lives outside `group_members` because member cleanup deletes a removed channel member's row a day after removal when it has no chat items (`deleteOrUpdateMemberRecordIO`, `Internal.hs:2192-2203`; `cleanupRemovedMembers`, `Commands.hs:5960-5966`; `getRemovedMembersToCleanup`, `Store/Groups.hs:1375-1382`). Rows come from `revokedOwners` at join and at relay invite, from link-data refresh, and from removal and owner leave events; they are never deleted.
- `member_id` — the replay record: `x.grp.owner.add` and `x.grp.mem.role` for it are ignored, a relay refuses any join onto it, and promotion refuses it (Parts 4–6).
- `member_key` — the key the heal drops (`NULL` when this device never knew it).
- `key_drop_enforced` — false when the revocation was first seen in the link data and the key drop is not yet confirmed; true once confirmed, or for a row from an event (a removal or leave event is sent after the key drop). Drives the heal (Part 6).
- `removal_step` — for a removal or leave this device runs: revoking / revoked / key_dropped / announced. The row is written with `revoking` before the first `LSETH`, so a crash at any point is re-driven at chat start through the announcement (Part 5).
- `roster_key_version`, `roster_key_author`, `with_messages` — on an owner's device, the key of a roster removal (made-at version and author) and its `withMessages` flag, kept here because the removed member's row is cleaned up; a removal beats any role change of that member, and a re-sent removal carries the flag (Part 6). A removal that carries no roster version — every removal in a call that removes no roster member (`Commands.hs:3136-3139`; a call that removes one stamps its version on every removal it sends, `:3196`) — has no key and is never re-sent; its record makes it stick on every device that saw it. A joiner records only `revokedOwners`, so if such a removal of S races another owner's promotion of S, a later joiner sees S at the promoted role from the relay's stored blob until the promoter's next roster change (cosmetic: S's connections are gone).
- `revoked_version`, `revoked_leave` — for a revoked owner, its `revokedOwners` entry's `rosterVersion` and `leave` as this device first saw or wrote them — from the link data, from this device's own revocation write, or from the departure event's `revokedVersion` (Part 4) — republished unchanged in its link writes; `NULL` only for a removed non-owner, which `revokedOwners` does not list. A row first created by the removal of a non-owner that raced the promotion it revokes takes the entry's values when the entry is first seen.
- `roster_bound`, `hold_running_left` — on an owner's device, for an owner that left and whose leave this device learned of from link data before processing its `x.grp.leave`: the roster version published with the leave (`revokedOwners`, below), and the running time left in the hold during which this device still applies that owner's held role and removal events (Part 6); `NULL` once the hold ends, when adoption runs.

### `group_departure_notices` (new table)
`(group_id, member_id, relay_group_member_id)` — on an owner, the relays that have reported applying a departed owner's departure (`x.grp.owner.departed`, Part 4), recorded whenever a report arrives; a hold ends when every relay that was current and connected to this owner at its start, and not since removed or left, has reported (Part 6).

An owner's own roster changes are the member keys whose author is this owner — no separate record.

### No pending-edit record for whole-value fields
Profile/prefs edits are synchronous and write-then-commit (Part 6), so nothing is stored while they are in flight. Owners and revoked owners merge as a union keyed by memberId; a relay this owner is adding is durable in its relay row, and a removed or departed relay in its kept member row.

### Published link data (not DB — chat's `GroupShortLinkData` JSON)
`GroupShortLinkData` (`Protocol.hs:1621`), carried in `UserContactData.userData`, gains optional fields — simplexmq's `UserContactData` encoding is unchanged: `linkDataVersion` (advisory ordering — recipients drop an older profile event; correctness rests on the server hash-CAS and reconcile, so a corrupted value only degrades live-event ordering, never stored state), `revokedOwners :: [RevokedOwner]` (`{memberId, rosterVersion, leave}` — the roster version its writer held when writing the entry, and whether the entry is the owner's own leave, whose held changes that version bounds, Part 6; a memberId appears once, and the merge keeps the first entry this device saw for that memberId), and `subscriberCountTs` beside `publicMemberCount` in `PublicGroupData` (`:1616`). `group_revoked_owners` locally holds `revokedOwners`, besides the other removed memberIds it records.

## Part 3 — new Haskell types

- **`MemberRoleProposal = MRProposed GroupMemberRole | MRRejected GroupMemberRole`** (`Types.hs`); `GroupMember` gains `memberRoleProposal :: Maybe MemberRoleProposal` (derived from `promote_*`) and the app-facing `promotionPending :: Bool`.
- **`PromotionRoleData`** for the wire: a role-tagged sum with an opaque fallback — `PRDOwnerInv { linkRcvId }` / `PRDUnknown` (decode an unrecognised tag to `PRDUnknown`, do **not** error — `omittedField` only covers an *absent* field, not a present unknown one).
- **`ForeignLinkKeys`** — the input to the Part 1.2 foreign-link APIs: `SMPServer`/`linkRcvId`/`LinkKey`/`rootPubKey`/member private key, assembled from `groups` columns, plus the expected hash.
- **`GroupLinkWriter = GLWOwn Connection GroupLink | GLWForeign ForeignLinkKeys`** — resolved once per link write (Part 6), from the keys: `GRKPrivate` (the creator, holding the root private key) → `GLWOwn`; otherwise a stored `link_rcv_id` → `GLWForeign`; neither → not a link writer. Never from whether a group link row exists (Part 5 refuses creating one for a channel).
- Reuse: `OwnerAuth` (simplexmq), `MemberId`, `MemberKey`, `VersionRoster`.

## Part 4 — new protocol events (`ChatMsgEvent`, `Protocol.hs`)

All `requiresSignature`. Wire is JSON with optional-field forward-compat (`.=?` / `opt`).

| event | dir | fields | delivery |
|---|---|---|---|
| `x.grp.promote.inv` | O1→M | `invitationId, memberId, memberRole, roleData?` (`memberId` = M; `roleData` = `PRDOwnerInv{linkRcvId}`) | M's support scope (`DJSMemberSupport` of `memberId`) |
| `x.grp.promote.acpt` | M→O1 | `invitationId, memberKey, roleData?` (none for owner) | M's support scope (the sender's) |
| `x.grp.promote.reject` | M→O1 | `invitationId` | M's support scope (the sender's) |
| `x.grp.promote.cancel` | O1→M | `invitationId, memberId` | M's support scope (`DJSMemberSupport` of `memberId`) |
| `x.grp.owner.add` | owner→all | `memberId, ownerAuth, profile` (+ the link-data hash fields below) | `DJSGroup` — all members and relays |
| `x.grp.relay.count` | relay→owners | `count, ts` (the relay's own clock) | sent directly to owners, as the relay sends the join announcement (`introduceInChannel`, `Internal.hs:1320-1326`) — not a `DJSGroup` job, which would fan out to every member |
| `x.grp.owner.sync` | owner→relay | — | sent directly to each relay by a promoted owner that completed from link data (Part 6); the relay answers a current owner with its member catch-up and count reading, below |
| `x.grp.roster.dropped` | relay→owner | `sharedMsgId, version, proof` (`proof` = the owner-signed role or removal event, or roster header, that set the relay's gate to `version`) | sent directly to the owner whose role or removal event the relay's gate dropped; never forwarded, and ignored when it arrives as a forward (Part 6) |
| `x.grp.owner.departed` | relay→owner | `memberId` (the departed owner) | sent directly to every current owner when the relay applies that owner's departure, after its kept copies of that owner's events; never forwarded (Part 6) |

`memberKey` in `acpt` is M's existing key; O1 checks it **equals the key it already holds for M** and adds the key it holds (a consistency check, distinct from the advisory OOB verification in Part 7). Support-scope delivery also reaches moderators, admins and owners (`Subscriber.hs:4424-4438`), so every recipient other than `memberId` ignores `inv` and `cancel`; M accepts them only signed by a current owner, and `cancel` only from the `inv`'s signer; O1 matches `acpt` and `reject` only from M's own member row.

**`x.grp.owner.add` is the promotion commit.** A member or relay applies it only if its sender (the message signer) is a current owner, `memberId` is not in `group_revoked_owners` and its member row (if any) is not removed or left, `ownerAuth` validates — signed by the stored root key (`root_pub_key`) or by a current, non-revoked owner's key — and `ownerAuth.ownerId` is `memberId`; it then sets the member's `member_pub_key` to `ownerAuth.ownerKey` (logging a warning when a relay-asserted key differs), creates the member if unknown with `profile` (or updates a placeholder profile with it — relays introduce owners only to later joiners, `Internal.hs:1320-1332`), and sets its role to owner. M, receiving it for itself, completes its promotion only as Part 6 describes. It is a new event rather than `x.grp.mem.role … GROwner`, which would apply the role to a relay-asserted key (`Subscriber.hs:3465-3468`) and never create an unknown owner (`:3458`); clients that predate it ignore it and keep rejecting the new owner's admin messages (Part 8). The sender check stops a removed owner reinstating itself with its own still-valid root-signed entry; the removal record stops a relay re-delivering an old add, and a removal that arrived before the add it revokes (Part 2). `group_revoked_owners` survives member cleanup (Part 2), and a removed memberId is never promoted again (Part 5), so no version gate is needed — which would also drop adds that relays merely reordered. Whenever a relay starts treating a memberId as an owner — applying `x.grp.owner.add`, applying the chain in its periodic link check, or accepting that owner's join — and when a current owner sends it `x.grp.owner.sync`, it sends that owner `XGrpMemNew` for each of its current members, batched (relays announce joiners only to the owners and moderators of that moment, `Internal.hs:1323-1326`, so a promoted owner would otherwise hold no row or key for earlier subscribers; the keys are relay-asserted, as the creator's are today), and then its current `x.grp.relay.count` reading, which M also takes as that relay's confirmation that it treats M as an owner (overview §6). A device stores `x.grp.relay.count` from a relay member whatever its own role, since the reading can arrive before the forwarded commit.

`x.grp.mem.role` and `x.grp.mem.del` gain an optional `retryOf :: {version :: VersionRoster, author :: MemberId}`, the key of the change a re-send carries (absent on an original, whose key is its own version and signer, Part 6), and an optional `prevKey` of the same shape, the key the change replaced on its author's device — the sender's own previous key on an original, the original change's stored `prevKey` on a retry (used only to decide whether to surface an override); members and relays apply a retry through the gate like any change, and owners order it by that key. A relay whose gate drops an owner's role or removal event sends it unchanged to its other current owners (directly, as it sends `x.grp.relay.count`, the events of one received message batched in one message, `encodeBinaryBatch`, `Internal.hs:2899-2903`), so every owner hears every owner's roster change, and sends the sending owner `x.grp.roster.dropped` with its gate and that gate's signed proof (table above; Part 6). `XGrpRosterRequest` from an owner asks a relay for catch-up — its kept latest role and removal events above the requested version — instead of the blob a member's request gets; from a relay, carrying the relay's gate and, as a new optional field, the same signed proof, it asks an owner to re-send its blob (Part 6).

Additive: `linkDataVersion`, `linkDataBaseHash` and `linkDataHash` become optional fields on the events that announce link-data writes — `XGrpInfo`, `XGrpRelayNew`, `x.grp.owner.add`, and `x.grp.mem.del` of an owner — present only when the event describes its write's entire change (a write that activates several relays at once carries none). `x.grp.mem.del` of an owner and an owner's `x.grp.leave` also carry, as optional `revokedVersion`, the `rosterVersion` of the `revokedOwners` entry their write published; a receiver stores it as `revoked_version`, with `revoked_leave` set for a leave (Part 2), so it can republish the entry and bound trigger (7) without reading the link data. Order: write first (`LSETH`), then broadcast. A receiving owner adopts `linkDataHash` into `link_data_hash` only when `linkDataBaseHash` equals the value it holds (overview §2); otherwise it applies the content and keeps its hash. Every recipient ignores an `XGrpInfo` whose `linkDataVersion` is below its `link_data_version` — the profile is a whole value, so an older one arriving late through another relay would revert a newer one (`xGrpInfo` applies any differing profile, `Subscriber.hs:3848-3849`); the other announcing events compose (relay and owner additions, removals) and are not version-gated.

The chat version these events and the relay behaviour gate on is `multiOwnerVersion = VersionChat 23`, with `currentChatVersion` raised from 22 (`Protocol.hs:96-97`).

The roster tie-break needs **no wire field** — the author is the message signer (`withAuthor`), already available at the completion gate; store its cross-device `memberId` in `stored_roster_owner_id` at completion and compare there.

The new owner events (`x.grp.promote.*`, `x.grp.owner.add`) are added to the relay forwarding set (`isForwardedGroupMsg`, `Protocol.hs:528`), the relay's dispatch (`processEvent`) and, since members and owners receive them as relay forwards, `processForwardedMsg` under `withAuthor` (`Subscriber.hs:4041-4064`, whose catch-all rejects unknown events) — or relays and members drop them. The direct-only events — `x.grp.relay.count`, `x.grp.owner.sync`, `x.grp.roster.dropped`, `x.grp.owner.departed` — are not forwarded and are ignored when they arrive as a forward.

## Part 5 — commands (`ChatCommand`, `Controller.hs`)

- **`APIAcceptRolePromotion GroupId`** — M marks accepted, then sends `acpt` (a crash between them leaves an accepted record, which the chain may still commit); the async chain (overview §6) then runs on O1. M holds at most one pending promotion: an `inv` received while one is pending is answered with `reject` automatically. Before acceptance M's record clears on `cancel`, when the inviter is revoked, and on its own TTL. After acceptance it holds `promote_link_rcv_id`, which completing needs (Part 6), so only `cancel` clears it; when the inviter is revoked, M settles it from the link data on its next refresh — an entry for M completes the promotion, none clears the record.
- **`APIRejectRolePromotion GroupId`** — sends `reject`, clears.
- **`APICancelRolePromotion GroupId GroupMemberId`** — O1 sends `cancel`. If the chain already added M's key (`promote_status` `key_added`), it drops the key with `RKEYH`; from `entry_published` on — set before the chain's `LSETH` is issued, so the entry may be live or still queued in the agent — it revokes M instead (the removal chain below, revocation first), which also removes M from the channel — a revocation is applied as a removal everywhere (Part 6), and the Cancel confirmation says so from that step on; then clears the proposal. The same undo runs when the chain stops because M left or was removed (below). The inviter's record expires only while `invited` (its expiry sends `cancel` to M), and M's only before it accepts — after acceptance the chain runs to completion or to an explicit cancel. Both TTLs are fixed in `ChatConfig` and checked at chat start (with the re-drive of pending records, under the group lock) and by a per-user step in the periodic cleanup manager (`cleanupUser`, `Commands.hs:5922-5933`) — not by the relay-request pattern, whose TTL is checked only on a temporary error inside its own worker (`retryTmpError`, `Subscriber.hs:4554-4559`), which an invitation waiting on a person never reaches.
- Route **`APIMembersRole … GROwner`** on a channel into the invite flow — single-target (reject a multi-member owner promotion, as the existing guards do: channel owner-role guard `Commands.hs:2994-2995`, multi-member admin guard `:2990-2991`). Before sending `inv` the inviter checks that the link queue's server session supports v24 (Part 1.2). Before any key change the chain refuses a memberId in `revokedOwners` or in `group_revoked_owners` (its key would be added but its entry never written, since the merge excludes revoked memberIds) and checks that the link data still fits with M's entry added (user data is padded to 13,784 bytes, `ShortLink.hs:46`), refusing the promotion with a clear error otherwise. Before each step it re-checks that M is still a current member without a `group_revoked_owners` row and that the inviter is not revoked, and undoes otherwise (above); each chain `LSETH` attempt re-checks the fit and the inviter's revocation on the blob it replaces, and on a misfit undoes by dropping M's key. M's entry is added to the local chain only by that `LSETH`, so no unrelated write (a count publish, a relay ack) publishes it early. The creator's first promotion then rotates its link-queue key to its member key (Part 1.2).
- **`APIMembersRole`** whose target is a current owner, to any other role, is refused in channels — removal is the only way to drop an owner (today only `newRole == GROwner` is blocked, `Commands.hs:2995`); receivers likewise ignore `x.grp.mem.role` whose target is a current owner or a memberId in `group_revoked_owners`.
- Route owner **removal** (`APIRemoveMembers` of an owner) into the removal flow (overview §7): an async command that first writes its `group_revoked_owners` row with `removal_step` `revoking`, then writes the revocation (`LSETH` adding the target to `revokedOwners`, with the remover's roster gate as its `rosterVersion`), **then** drops the key (`RKEYH`; the target's key is its chain entry's `ownerKey`), **then** sends `x.grp.mem.del`. Each `RKEYH`/`LSETH` payload is built by applying the delta to the server's *current* set/blob (the believed one, or the one returned on a conflict) — never rebuilt from the chain, which could drop a concurrently-added owner's key whose chain entry is not yet published. Refuse removing/leaving the last *live* owner, checked on the blob each revocation `LSETH` attempt replaces — the believed one, then the one each conflict returns: the actor must not be in its `revokedOwners`, and an owner outside `revokedOwners` must remain after the change; otherwise stop before any key change and surface it (overview §3). A crash between the steps is resumed from `removal_step` at chat start; another owner's reconcile heals the key drop if this device never comes back (Part 6).
- **Leave** (`APILeaveGroup`, `Commands.hs:3233-3253`) by an owner while another live owner remains: the same record and precondition; roster changes are refused once its leave record exists, but re-sends it has pending still go out (they carry earlier changes); then, once its earlier messages to every current relay are on the relay's queue server (their `msg_deliveries` marked by `SENT`, `sentMsgDeliveryEvent`, `Subscriber.hs:1189-1192`, `:1835-1837` — accepted by the server, not yet processed by the relay; and no `pending_group_messages` remain for any current relay — in channels an owner's message to a relay whose connection is inactive (`QUOTA`, `Subscriber.hs:1749-1762`) is stored as pending, as in other groups (`MSAPending`, `Internal.hs:2851`), and sent when the connection continues (`Subscriber.hs:1197-1199`); today `memberSendAction` drops it (`Internal.hs:2840-2846`, `readyMemberConn` `:2877-2885`), so a role change made while the relay was backlogged never reached it; within a bound, as a relay's queue server may be down), revoke itself (`LSETH`, an entry with its own roster gate as `rosterVersion` and `leave` set, keeping its own chain entry — a non-creator's write is validated with its own key, which must still be a chain key, pinned `Agent/Protocol.hs:1996-2001`; `revokedOwners` marks it revoked, and the next other owner's write drops it), drop its own key (`RKEYH`), then `x.grp.leave`; after its own key is dropped, an `AUTH` error on that key counts as done, so a resumed leave goes on to the announcement. The creator then forgets its link connection without `DEL` (Part 1.2) instead of `deleteGroupLinkIfExists` (`Internal.hs:1739-1748`), which would `DEL` the shared queue. The same applies where an owner processes its own removal (`Subscriber.hs:3736`; a relay processing its own removal there keeps deleting its own relay link) and where an owner that is no longer current deletes the chat (`Commands.hs:1400`). Destroying the channel still deletes the queue: the creator through its link connection as today, and a non-creator owner, which has none, with `deleteForeignLinkQueue` (Part 1.2) — only in the branch where a current, non-revoked owner sends `x.grp.del` (`doSendDel`, `APIDeleteChat`, `Commands.hs:1394-1400`). `deleteGroupLinkIfExists` at `:1400` runs regardless of `doSendDel`, so the foreign `DEL` must not join it there: a removed owner whose key a crash left live would otherwise destroy the channel by deleting its chat.
- **`APICreateGroupLink`, `APIAddGroupShortLink` and `APIDeleteGroupLink`** are refused for channels (`Commands.hs:3349-3384`): a channel's link is created with the channel, the apps would otherwise create a direct group link for a promoted owner that opens the link screen (`GroupLinkView.swift:164-166`), and `APIDeleteGroupLink` sends `DEL` on the shared queue (`deleteGroupLink'`, `Internal.hs:1733-1737`) — destroying the channel goes through `APIDeleteChat`.

The promotion, removal and leave chains are async commands resumable from their durable records (the `promote_*` columns / `group_revoked_owners.removal_step`) — no new durable-worker type.

## Part 6 — key logic changes (anchors)

- **One writer for every link write.** Each link-write site resolves a `GroupLinkWriter` once, from the keys (Part 3): the creator's own link connection and group link, or a promoted owner's `ForeignLinkKeys`. The `GroupLink` that `CRGroupRelaysAdded` and `CEvtGroupLinkDataUpdated` carry (`Controller.hs:862`, `:1035`) becomes optional, absent only for a promoted owner, and both apps decode it as optional — an older remote-desktop app fails to decode only those responses, which exist only for a promoted owner. Today every site needs the creator's group link row or link connection — `setGroupLinkData'` silently skips the write without one (`Internal.hs:1581-1586`, used by the profile edit at `Commands.hs:4190`), and `setGroupLinkData`/`setGroupLinkDataAsync` (`:1588-1604`), `updatePublicGroupData` (`:1624`), relay add (`Commands.hs:2790`) and relay connect/ack (`Subscriber.hs:946-947`, `:3663-3665`) throw. Foreign writes are synchronous (Part 1.2); a caller that is asynchronous today runs them in a thread, and its intent is already durable (relay rows, promotion records, `group_revoked_owners.removal_step`), so reconcile at chat start re-drives an interrupted one. The body of the `LINK` handler (`Subscriber.hs:1431-1481`: relay activation to `RSActive`, `XGrpRelayNew` to other relays, `CEvtGroupLinkDataUpdated`) becomes a function of the written data and the resolved writer — not a re-read of the group link (`Subscriber.hs:1439`), which a promoted owner has no row for — called from the `LINK` event and after a foreign write returns `OK`, which produces no `LINK` event.
- **`groupLinkData`** (`Internal.hs:1670`, self-only owners at `:1676-1682`) → build the write from local state via the **reconcile** routine; delete the `GRKPrivate` singleton / `[]` fallback; read the stored chain (insertion order). The creator's own entry, computed on every write today (`Internal.hs:1676-1682`), is stored on its membership row at channel creation and filled on first start after the migration (it holds the root key); a write whose chain lacks an entry for a current, non-revoked owner is refused. The relay list is `published_relays` (read from the link data first when it is still `NULL`) plus this owner's in-progress additions minus every relay whose member row on this device is removed or left (Part 2 keeps removed relays' rows), and a write whose relay list is empty is refused unless this owner is removing the last relay — not only its own `group_relays` rows (`getPublishableGroupRelays`, `Store/Groups.hs:1528-1545`), which reference its own chat relays (`chat_schema.sql:840`) and are empty for a promoted owner. The count fields are the published `(publicMemberCount, subscriberCountTs)`, unchanged, except in the gated count publish.
- **Reconcile** = merge published link data into local, by field kind: owners and revoked owners merge as an idempotent union keyed by memberId, minus revoked entries no current entry depends on (dropped, below), and a published entry fills `owner_auth_sig`/`owner_auth_index` on a local owner row that lacks them (rows created before the migration store only the key); relays: `published_relays` is replaced by the published list, and this owner's in-progress relay rows (being added and not yet published) and its removed or departed relays' member rows are kept; profile/prefs adopt the published value. A chain owner for which this device holds a `group_revoked_owners` row — a removal that raced that member's promotion — is revoked by this owner through the removal flow (Part 5): the removal wins. Subscribers' link-data refresh (`updateGroupFromLinkData`, `Internal.hs:1634-1654`, today profile and count only; called only from `Commands.hs:1966`, `:4624`, `:4651`) also applies the chain: validated entries as owners (keys from `ownerKey`), `revokedOwners` into `group_revoked_owners`. A revocation this device has not yet applied is applied as `x.grp.mem.del` of that owner would be (`xGrpMemDel`, `Subscriber.hs:3747-3781`): a relay drops the owner's connection, a member marks it removed; for this device's own memberId, it is this device's own removal (`Subscriber.hs:3734-3746`, forgetting the link connection without `DEL`, Part 5). Authority checks are role-based, so without this an owner whose removal was never announced would keep its powers; `x.grp.del` is also accepted only from a current, non-revoked owner (today a role check, `Subscriber.hs:3828-3831`). Relays never call it; a relay applies the chain the same way in its periodic check, which already fetches the link data every 15 minutes (`checkRelayServedGroups`, `Commands.hs:6001-6020`), and at once when an owner join or `x.grp.owner.add` names a memberId it does not hold as owner — relays don't forward to each other, so an owner event from an owner not connected to a relay never reaches it otherwise. Run it **on channel open** (owners run `APIGetUpdatedGroupLinkData` like subscribers — remove the owner exclusion at `Commands.hs:1968` and the apps' owner branch, `ChatView.swift:764-779` and its Kotlin counterpart), **at chat start** for each channel the user owns (owners that never open the channel view — CLI, bots — still heal and publish the count), **on a CAS conflict** (adopt the returned blob, rebuild), and as the **missed-event backstop**.

Without it no owner can connect to a relay another owner added, so its posts never reach that relay's subscribers. On the owner's side, completing the join (the relay answers with `XGrpLinkInv`, handled for a `GCHostMember` at `Subscriber.hs:830-842`) updates only the relay member: `updatePreparedUserAndHostMembers'` (`Store/Groups.hs:821-844`) would replace the owner's group profile with the relay's copy and, unless the membership is `GSMemConnected` (the creator's is `GSMemCreator`), rewrite its membership role and status. Keep the starting profile in memory; on a conflict, merge field by field against it — a field only this owner changed keeps its value, a field only the other owner changed takes theirs, a field both changed differently keeps the published value and is surfaced as "profile edit superseded" — then retry.
- **Removal heal** (runs during reconcile, and it is what makes the revoke-first ordering crash-safe): for each `group_revoked_owners` row with `key_drop_enforced` false and a known `member_key`, issue an `RKEYH` whose expected set is the believed set plus that key and whose new set is the believed set; on a conflict, drop the key from the returned set and retry while it is still there; then set `key_drop_enforced`. Merging `revokedOwners` into local state alone does *not* evict a still-live key; this explicit `RKEYH` is required. An owner that receives the removal or leave event sets `key_drop_enforced` directly — the event is sent only after the key drop — so only a revocation first seen in the link data (the crash case) costs a direct connection to the link server. A removal this device runs and that crashed is resumed from its `removal_step` at chat start, through the announcement.
- **Relay activation** stays on the `LINK` event (and, for a foreign write, its `OK`, through the extracted function above), which the agent emits only after the server accepted the write (`Agent.hs:2255-2258`); under CAS it follows the accepted `LSETH` and carries the data written after any re-merge. Relays another owner removed produce no `LINK` here (the TODO at `Subscriber.hs:1475-1477`); the owner relay step deactivates them.
- **Roster** (overview §4): the event gate stays **version-only, author-blind** (`applyAtRosterVersion`'s `fresh` check, `Subscriber.hs:3414`, `version >= held`), so concurrent *different-member* deltas both apply. The `(version, authorMemberId)` tie-break is added **only at the completion gate** (`Subscriber.hs:3572-3578`): keep the existing downgrade reject (`pendingVer < roster_version` gate) and, at the equal-version case that today overwrites by arrival order, accept iff `pendingVer > stored_roster_version` **or** (`pendingVer == stored_roster_version` **and** (`stored_roster_owner_id` is no longer a current owner **or** `author > storedAuthor`)) — comparing the incoming blob's signer against `stored_roster_owner_id`, never the gate. Store the cross-device author with the blob in `setGroupLiveRoster` (`:3578`; `Store/Groups.hs:1716-1724`). A completed blob reverts privileged members absent from it (`processRosterEntries`, `Subscriber.hs:3610-3619`), so the losing owner's delta is reverted on relays until its retry. Applying any roster skips members who are currently owners (in `processRosterEntries`, `Subscriber.hs:3610-3630`, which today sets each listed member to its listed role, `:3601-3608`, `:3622-3628`): a member promoted to owner from a roster role stays in relays' stored blob, which a later joiner receives right after its owner intros (`Internal.hs:1330-1331`), and would otherwise be set back. **Relay setup under concurrent roster changes:** a roster ack below the owner's current version during relay setup re-sends the current roster to that relay (`sendGroupRosterToRelay`, `Internal.hs:2657-2662`) instead of only warning (`xGrpRosterAck`, `Subscriber.hs:3654-3667`) — another owner's delta can advance the version between send and ack, and this owner re-sends only when it bumps the roster itself (`broadcastRoster`, `Internal.hs:2642-2654`), so the relay would stay unpublished. **Owner-side ordering** (an owner's own blob goes to relays only, `broadcastRoster`, `Internal.hs:2649-2654`; a relay forwards nothing its gate drops, `Subscriber.hs:3423-3425`, `:1133-1144`, and can reorder one owner's events, `Store/Delivery.hs:178-202`): on an owner, a role or removal event — original, retry, passed on by a relay whose gate dropped it (Part 4), or a relay's catch-up (below) — carries a key: made-at version (`retryOf`'s, or the event's own) and author (`retryOf`'s, or the signer). The owner applies it, instead of through `applyAtRosterVersion`'s gate (`Subscriber.hs:3404-3446`), exactly when its key beats the member's stored key (`roster_key_version`/`roster_key_author`, or the `group_revoked_owners` row for a removed member): a removal beats a role change; an empty key loses only to an event whose wire version is above `roster_key_floor`; otherwise the higher made-at version, then the higher author. It then stores the key with the event's `prevKey` (a retry carries the original change's), raises its gate to the event's version if higher, clears `roster_key_resent` and `roster_key_reported`, and, when the beaten key was its own and differs from that `prevKey` (the replacing change was made without seeing it), surfaces "your role change to X was overridden". Re-delivered events are dropped by message id first (`saveGroupFwdRcvMsg`, `Internal.hs:2956-2959`), and an older event never beats the key that superseded it. **Re-send triggers**, coalesced — after the first, the owner waits a short quiet period with no further roster event, within a bound, since SMP delivers one message per queue per acknowledgement (pinned `Server.hs:2091-2092`) and a bulk change arrives over several messages — and, for triggers (1)–(3) and (6), skipping members whose current key it has already re-sent (`roster_key_resent`), so a bulk change costs one re-send per member however a relay splits or spaces it — safe because a relay forwards every group-scope channel event in the order it received it (Departures, below), so a later re-send never overtakes an earlier one; triggers (4), (5) and (7) report a value a relay or its members hold wrongly and always re-send it: (1) it applied another owner's event whose wire version is below its own gate — relays and members with a gate as high dropped it; (2) it applied another owner's event whose wire version is at or below `roster_blob_sent_version` — its own blob at that version may have won the relays' equal-version tie-break without the change (`Subscriber.hs:3573-3578`) and reverted it there (`:3614-3618`); (3) an event lost to a member's non-empty key with a different value, its wire version is at or above that key's made-at version, and the member has no `group_revoked_owners` row — devices may have applied the loser, while a replayed change below the change that superseded it triggers nothing, and a removed member needs no repair since every device ignores its role events; (4) a relay's `x.grp.roster.dropped`, received directly from a current relay member (never as a forward) and acted on at most once per relay per interval (later ones deferred, not discarded), names this owner's change at a version above the owner's gate whose `proof` is an owner-signed event or roster header at that version, verified against an owner key the owner holds — a departed owner's (its `group_revoked_owners.member_key`) only within the departed-owner margin above the owner's gate, 2^20 versions (`ChatConfig`) — each role-change call adds one version, so no remaining owner falls that far behind a departed one, while rate-limited notices one margin at a time never bring a gate near the `Int64` limit — so a relay cannot inflate the `Int64` gate (`Types.hs:2282`; changes are made at gate+1, `Internal.hs:2644`) and freeze every role change; the owner raises its gate to that version and re-sends that change; (5) a relay passes back a kept copy (below) whose key equals this owner's key for that member, for a member with no `group_revoked_owners` row — the relay lost a change this owner holds (no honest relay passes back a removed member's copy, as applying a roster skips such members, and a removed member's row may be cleaned up, leaving nowhere to record the re-send); this owner may hold that very message, so a pass-back is compared by key before the message-id dedup (`Internal.hs:2956-2959`); it is acted on at most once per member and this owner's current key (`roster_key_reported`), at most once per relay per interval (deferred work kept as a set of members per relay), and re-sends that member only — a relay keeps a genuine owner-signed copy for every member, so a replayed pass-back must not re-send the roster; (6) it applied another owner's departure (Departed owners' changes, below) — adoption: every member whose key that owner authored, since it can no longer re-send its own changes and devices that learned of its departure before receiving them dropped them; when the skip leaves no member, the blob alone goes out at the version this owner holds; (7) a relay's kept copy of a departed owner's role event, received after this owner applied that departure (in the relay's departure report, passed back, or served as catch-up), verified against `group_revoked_owners.member_key` and made at or below that owner's `revokedOwners` `rosterVersion` plus the departed-owner margin of trigger (4), whose key differs from this owner's key for that member, for a member with no `group_revoked_owners` row — undo: some devices applied a role change of the departed owner that this owner does not hold; it is acted on at most once per member and this owner's current key (`roster_key_reported`), at most once per relay per interval (deferred work kept as a set of members per relay), re-sends that member only, and the copy's wire version never counts toward the highest version seen; if another remaining owner holds the change, that owner receives the re-send as a losing different value, re-sends the change under trigger (3), and this owner adopts it by key. The owner then re-sends, as deltas with `retryOf` = each member's stored key and `prevKey` = that key's stored `prevKey` (a role event with the member's key for TOFU, a removal with its kept `with_messages`), the current value of the triggering events' members and of every member whose key was made at a version at or above the lowest triggering made-at version, with its blob, at one above the highest version seen, records that version in `roster_blob_sent_version` and sets `roster_key_resent` on the members it re-sent, and the bit of `roster_key_reported` for (5) or (7) on the members those triggers named. ## Part 8 — version gating and compatibility

- **Link server:** detect the link queue's negotiated server version (the relay-handshake `thVersion`, through the agent read in Part 1.2); **require ≥ v24 to promote a second owner** (the hash-CAS `LSETH`/`RKEYH` all need it). On an older link server, block promotion with a clear error before sending `inv` rather than degrade — a blind `RKEY` there evicts other owners (replace with no CAS). A sole live owner on an older link server keeps writing with today's blind `LSET` when the CAS call fails with `TEVersion`; with two or more live owners (the server was ≥ v24 at promotion and has since been downgraded) writes, removal and leave fail closed and are surfaced. Because the negotiated version is the min of the two peers' relay ranges, both relay constants (Part 1.1) must reach 24 before a client perceives v24.
- **Relays:** a relay invited to a channel with two or more owners throws on the owner it has no row for (`updateRelayGroupKeys`, `Store/Groups.hs:2366-2368`, called from `Subscriber.hs:4604`), so adding a relay to such a channel fails. A relay that predates multi-owner also never forwards `x.grp.owner.add` (`isForwardedGroupMsg`, `Protocol.hs:528`, unknown events → `False`), keeps the promoted owner an observer and drops its posts (`memberCanSend`, `Subscriber.hs:1737-1738`), rejects that owner's join (Part 6), and sends no `x.grp.relay.count`. So the relay side — tolerant `updateRelayGroupKeys`, `x.grp.owner.add`, the owner join, `x.grp.relay.count` — ships in a release before promotion is enabled, and at runtime promotion requires every current relay to support `multiOwnerVersion` (Part 4; owners already check a relay's version, `supportsVersion`, `Subscriber.hs:933`), else it is refused with a clear error. Adding a relay to a channel with more than one owner cannot be checked up front — a relay's version is known only once it answers — so it fails closed: an older relay throws before answering (`Subscriber.hs:4604`, its error recorded only on the relay, `:4565-4567`), and the owner times out the unanswered invitation and shows an error — checked by the same `cleanupUser` step as the promotion TTLs (Part 5), since today nothing on the owner's side expires an `RSInvited` relay. A creator that is the sole owner and whose relays predate the count event falls back to its own tally (Part 6).
- **Older members** ignore `x.grp.owner.add`: they keep rejecting the new owner's admin messages until they upgrade — failing closed rather than trusting a relay-asserted key. Its unsigned posts as the channel reach them (relays forward those as `FwdChannel`, `Store/Delivery.hs:159`); its signed ones are forwarded under its identity and dropped like its admin messages, and the profile still reaches them through link-data refresh. **Older joiners** take every chain entry as an owner, including revoked ones; a revoked owner's key is gone and relays have dropped its connection, so its messages do not reach them.
