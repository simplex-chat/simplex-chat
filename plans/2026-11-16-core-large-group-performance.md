# Performance: large groups and many messages

One pull request for three core fixes of slow database queries. The chat database has one connection, so each slow query delays every other action of the app. Each fix has its own plan and was reviewed in its own pull request; this plan states the problems, the approach of each fix and the decisions open for review.

## Problems

| # | Problem as users meet it | Fix branch | Plan |
|---|---|---|---|
| P1 | In a large group, a send in a member support chat is slow and delays every other chat action (178 ms average, 4.8 s maximum on a reporter's device) | nd/group-members-role-index | member-role-index.md |
| P2 | In a large group without relays, the admin's app holds the database for up to seconds per forwarded message; a channel bucket of 10,000 recipients takes about 1.5 s | nd/forwarding-recipients-one-query | 2026-10-27-forwarding-recipients-one-query.md |
| P3 | Switching profiles is slow when any profile has many messages, even to a profile with few chats | nd/profile-switch-unread-count (#7969) | 2026-11-01-profile-switch-unread-counts.md, 2026-11-01-profile-switch-unread-counts-postgres.md |

## Approach

- P1: migration 20261027_member_role_index adds an index on `group_members (user_id, member_role, group_id)` and a partial index on `(group_id, contact_id)`, so the moderator lookup reads only matching rows.
- P2: on SQLite, the delivery worker loads all forwarding recipients with one `json_each` query instead of one query per recipient; an empty list runs no query.
- P3: migration 20261101_chat_items_unread_index replaces the index `(user_id, item_status)` with one that adds `contact_id`, `group_id` and `user_mention`, so the unread counts of each profile read only its unread messages.

## Combination

The two migrations are kept in date order after master's last migration, 20261021_badge_subscriptions, in both SQLite and Postgres lists. chat_schema.sql and chat_query_plans.txt are regenerated by the tests.

## Decisions for review

1. Order of merge: one pull request (recommended), or one per problem.
2. P1: the role index has a different column order on SQLite and Postgres; one name and one order on both backends is an option.
3. P3: the query of the first unread item gains `GROUP BY user_id` on SQLite to use the new index; its result is unchanged.

## Evidence

Each plan has its measurements of master against the fix. CI: the reduced build with the group, direct and schema tests.
