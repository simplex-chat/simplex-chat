# UI test catalogue 3: groups, channels, business chats

Groups, channels and business chats, mapped to the desktop code and the core tests: **312 test cases in 20 sections, 4 of them `@Ignore`** (see `## Count`). Format, Needs codes, user names and ownership of overlapping features follow `00-legend.md`.

**How to read the tables**
- The GUI user is **alice** (display name only). CLI peers are bob, cath, dan and eve; their role in a row (host, moderator, member, joiner, customer, team member, channel owner) is given in the Notes or Verification text. Chat relays are CLI peers started in relay mode (`cli("relay1", PeerFlags(relay = true))`, §0); they type commands and print events like any peer, so relay-side lines can be asserted.
- When a Haskell test is cited, its lines are rewritten for these roles: the GUI user's own output is asserted on the GUI, and CLI lines name the GUI user `alice` without a full name.
- Labels in «» are the exact English values from `apps/multiplatform/common/src/commonMain/moko-resources/base/strings.xml`.
- **Group info** means: click the chat title in the group's toolbar.
- Paths: `C/` and `H/` as in the legend; `V/` = `C/views/`.

## 0. Harness facts (setup, not tests)

- **Relays.** A relay is a CLI peer in relay mode: `cli("relay1", PeerFlags(relay = true))` runs `simplex-chat --relay --user-display-name relay1 -d <dir> -s <smp1> --xftp-server <xftp1>` under a pty like any other peer (desktop `CliPeer`; on Android the bridge starts it with `start relay1 relay`). On the first start the CLI asks `Create relay address (Yn):` (`src/Simplex/Chat/Core.hs:181-196`); the harness answers `y` and reads the link printed after `Chat relay address is created:` into `relay.relayAddress` (on Android the bridge replies `ok <link>`). `registerChatRelaysViaApi(relay, …)` adds relays to alice's custom server group (a precondition; registering a relay through the UI is tested in catalogue 04); a CLI owner registers its relay with `/relays name=relay1 <link>` and creates the channel with `/public group relays=1 #team` (`CliPeer.createChannel`, as prepareChannel' `H/Groups.hs:9743`). The web flags (`--relay-web-domain relay.example.com --relay-web-dir <dir>`, `src/Simplex/Chat/Options.hs:295-298`) are not wired yet: rows with `RELAY (web flags)` stay blocked.
  - Relays type commands like any peer (`/leave #team`, `/da`), so no stop/run/restart cycle is needed for them; `PEERCTL` on a relay row means the relay is stopped or restarted (`relay.stop()`, `relay.start()`), which keeps its database and address.
- **CLI subscribers** join with `/c <shortLink>` (testConnectChannelCLI, `H/Groups.hs:9206`, which runs with `testOptsNoFullLinks`). The `/_connect plan` + `/_prepare group` route of the Haskell helpers is not usable from a real CLI: the plan's link data is printed only in test view (`src/Simplex/Chat/View.hs:2281`).
- **Group host helpers:** `createGroup2'` (`H/Utils.hs:815`) and `fullAddMember` (`H/Utils.hs:917`). On the peer you will see `#team: alice invites you to join the group as member` and `use /j team to accept`.
- **Member screening on a CLI host:** `/set admission review #team all` (`H/Groups.hs:3684`). The "pending approval" path (as opposed to review) needs Haskell `chatHooks`, which a CLI process can't set (see the `IGNORE` rows in §6).
- **Business address on a CLI peer:** `/ad` then `/auto_accept on business [text …]` (`H/Profiles.hs:1950`). The GUI's own business address is set up with the catalogue-01 address flow (01 owns address settings).
- **Channels need current-build peers.** `S` is used only on plain-group compatibility rows.
- **Channel name.** Channel rows (§18–§19) use the channel `#team`; Haskell lines with other names are rewritten to it.
- **SimpleX names** use the `NAMES` server mode (legend).
