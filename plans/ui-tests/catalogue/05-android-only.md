# UI test catalogue 5: Android-only UI

Rows follow `00-legend.md` (row format, `Test case(s)` cells, Needs, users and CLI output, ownership), with the additions below. This catalogue covers only UI that exists on Android and not on desktop, or that behaves materially differently on Android. Every row of catalogues 01–04 that is not desktop-only also runs on Android (research doc `20261012-android-ui-test-automation.md` §5.3), unchanged unless `05-android-carryover.md` lists it, so 01–05 together cover the Android app. Totals: **251 test cases, 20 of them `@Ignore`**, in 15 sections (details in `## Count` at the end).

## Paths, runtime and runner

- Paths as in `00-legend.md` (`C/` = commonMain), plus:
  - `A/` = `apps/multiplatform/common/src/androidMain/kotlin/chat/simplex/common/`
  - `APP/` = `apps/multiplatform/android/src/main/java/chat/simplex/app/`
  - `MAN` = `apps/multiplatform/android/src/main/AndroidManifest.xml`
  - `US/` = `C/views/usersettings/`, `NS/` = `US/networkAndServers/` (as in 04)
- Line numbers are those of master `d72f68e6d` at `~/wt-uitest-ref`, as in 01–04.
- **Runtime:** Waydroid (LineageOS 20, Android 13 / API 33, x86_64 with libndk arm64 translation) through `~/waydroid/wd.sh`; one instance per host, so every test in this file runs serially. The APK is the default `foss` flavor, debug build (flavors at `android/build.gradle.kts:40-50`); its package is `chat.simplex.app.debug` only with `application_id.suffix=.debug` in `local.properties` (root `build.gradle.kts:23-25`, default empty; `android/build.gradle.kts:55`), as `local.properties.example` and `~/build/android.md` set it; without it the debug package is `chat.simplex.app`.
- **Runner:** instrumented tests in the app process (`createEmptyComposeRule()`, with `MainActivity` launched by `ActivityScenario.launch` after the reset, setup item 4), sharing the desktop plan's `UiDriver`, screen objects and `Ui` keys; CLI peers, relays and `uitest-servers` run on the host and are reached through the peer bridge over `adb reverse` (research doc §5.1). `ComposeRootRegistry` sees every Compose root in the process, so `CallActivity` (a second activity) is found by the same queries.
- **Package:** `chat.simplex.app.ui.android` (proposed; its class map lives with the Android harness, not in `00-legend.md`, whose class map covers 01–04 only).

## Needs codes added by this file

The shared codes of `00-legend.md` keep their meaning (`P`, `XFTP`, `RESTART`, `FIXTURE`, `ONBOARD`, `TOAST`, `DT`, `MCAST`, `SLOW`, `REC`, `AV`, …); `restart()` for `RESTART` still needs an Android mechanism (open question 14). `URI` and `CB` have no `TestRoot` stubs on Android, since the test composes the real root (setup item 1), so they change mechanism (carry-over rule R13): `URI` is `INTENTS` (Compose's `AndroidUriHandler` calls `startActivity` with an `ACTION_VIEW` intent, which Espresso-Intents records and stubs so nothing launches), and `CB` is the real system `ClipboardManager`, which persists across tests and which the reset clears (setup item 4). `NTF` (the recording notification manager of the desktop harness) is not used here: Android rows read the real system notifications (`SYSNTF`). `FD` is replaced by `INTENTS`. `MCAST (bridge)` is the cross-bridge variant of `MCAST`: the multicast announcement goes from the host-side CLI controller to Android across the Waydroid bridge (`waydroid0`), not over loopback; like every row here it runs serially (one Waydroid instance), and the legend's loopback `MCAST` rows don't run on Android (Notes). `TOAST` on Android is the toast recorder of carry-over rule R11: `showToast` is the system `Toast.makeText(…).show()` (`A/platform/UI.android.kt:23`), with no in-process list as on desktop, so the test registers `UiAutomation.setOnAccessibilityEventListener` and records the `TYPE_NOTIFICATION_STATE_CHANGED` events from the app's package whose class is `android.widget.Toast`, with the toast text from the event; "no toast is recorded" means none arrives within the step's wait. To be confirmed in the Android P1 (open question 13).

| Code | Meaning |
|---|---|
| `PERM` | runtime-permission state set by the runner before `am instrument` (`pm grant` / `pm revoke` / `pm clear-permission-flags`), written as `PERM (<permission> granted\|denied)`. A revoke kills the app process, which is also the instrumentation process, so tests that need a permission denied are grouped into their own `am instrument` invocation; a grant inside a test uses `UiAutomation.grantRuntimePermission` |
| `SYSUI` | UiAutomator (`UiDevice`) acts on system UI outside the app: the runtime-permission dialog ("Allow" / "Don't allow"), the device-credential screen of `BiometricPrompt`, the notification shade |
| `SYSNTF` | the app's real notifications, read in-process with `NotificationManager.getActiveNotifications()` (title, text, actions, channel, group) and acted on with `contentIntent.send()` / `actions[i].actionIntent.send()` |
| `INTENTS` | Espresso-Intents: outgoing activity intents (system pickers, camera, share chooser, settings screens, `ACTION_VIEW`) are recorded and stubbed with an `ActivityResult`; replaces the desktop `FD` |
| `INTENT` | an inbound intent delivered to an app activity: to `MainActivity` with `startActivity(intent.addFlags(FLAG_ACTIVITY_NEW_TASK))` while the setup's `MainActivity` runs, which reaches the `singleTask` activity's `onNewIntent` (`APP/MainActivity.kt:64-68`), or with `ActivityScenario.launch(intent)` only in place of the setup's plain launch, which reaches `onCreate` (:44-48; `ActivityScenario` tracks only an activity whose `getIntent()` matches its start intent, and `onNewIntent` doesn't call `setIntent`); to `CallActivity` the way the full-screen call notification starts it (`APP/model/NtfManager.android.kt:177-180`). The intent is explicit (component set), so the manifest's host and path filters don't apply; `appLink_intentFilter_matchesOnlyConnectionPaths` checks them. For `ACTION_SEND` / `ACTION_SEND_MULTIPLE`, `deliverToApp` first checks that the same intent without the component, limited to the app's package, resolves to `MainActivity` with `MATCH_DEFAULT_ONLY` through the share filters (`MAN:121-130`), so SimpleX would appear in the share sheet |
| `BG` | the app goes to the background and back inside the test: `UiDevice.pressHome()` (lifecycle `ON_STOP`, `isAppOnForeground = false`, `APP/SimplexApp.kt:138`) and the launcher intent to return (`ON_START`/`ON_RESUME`) |
| `BACK` | the system Back key (`UiDevice.pressBack()` or `Espresso.pressBack()`), which runs Compose `BackHandler`s and then `MainActivity.onBackPressed` (`APP/MainActivity.kt:91-118`); the desktop harness's `escape()` covers only the `BackHandler` part |
| `IME` | the real soft keyboard of the runtime (AOSP keyboard on Waydroid) and the `WindowInsets.ime` state the app reads (`A/platform/UI.android.kt:46-55`) |
| `VIEW` | Espresso on Android Views embedded through `AndroidView`, which Compose semantics don't reach: the message field is an `EditText` (`A/platform/PlatformTextField.android.kt:99-197`), and the emoji picker, video player and camera preview are Views too |
| `SHELL` | a device shell command run in-process through `UiAutomation.executeShellCommand`: battery-optimisation allow-list (`dumpsys deviceidle whitelist +/-<pkg>`), background restriction (`cmd appops set <pkg> RUN_ANY_IN_BACKGROUND ignore\|allow`), device PIN (`locksettings set-pin` / `clear`), airplane mode (`cmd connectivity airplane-mode enable\|disable`), running a scheduled job (`cmd jobscheduler run -f`) |
| `ROT` | a configuration change: `UiDevice.setOrientationLeft()`/`Natural()`, or `ActivityScenario.recreate()` where only recreation matters. Rotation on Waydroid's fixed-size output is unverified (open question 3) |

## Setup every test needs

1. **Compose the real root** through `MainActivity.onCreate` → `setContent { AppScreen() }` (`APP/MainActivity.kt:57-59`); alerts, the user picker and full-screen modals are composed there (`C/App.kt:203-207, 254-255`). `MainActivity` is `singleTask` (`MAN:57`).
2. **Pre-set prefs** as on desktop (plan §11.1), plus Android prefs that change what every test sees:
   - `notificationsMode = OFF` and `backgroundServiceNoticeShown = backgroundServiceBatteryNoticeShown = true`, so neither the foreground service nor the background-service alerts (§2) appear in tests that are not about them (`C/model/SimpleXAPI.kt:105-114`; `APP/SimplexService.kt:430-468`).
   - `privacyProtectScreen = false` for screenshot capture (failure screenshots; §7.7 shots once open question 17 is settled): it is `true` by default and sets `FLAG_SECURE` on the window (`C/model/SimpleXAPI.kt:123`, `APP/MainActivity.kt:49-55`); §10 tests it with the default restored (open question 4).
   - `canAskToEnableNotifications` is left at its default (except rows that pre-set it to false: §2 `ntfMode_serviceNotStartedWithoutNotificationPermission`, §3 `sysNtf_permissionDenied_nothingPosted`, §4 `notificationPermission_grantedLater_reenablesAsking`); `POST_NOTIFICATIONS` is granted by the runner (`PERM`) except in §2–§4 rows that say otherwise, so the chat list does not open the system permission dialog on first composition (`C/views/chatlist/ChatListView.kt:276-283`, `A/views/onboarding/SetNotificationsMode.android.kt:13-33`).
   - `CAMERA` and `RECORD_AUDIO` are granted by the runner too, except in the `PERM (… denied)` groups: on Android the new-chat entry "Paste link / Scan" opens the connect screen with the camera section, whose scanner requests the camera at once (`C/views/newchat/NewChatSheet.kt:61`, `A/views/newchat/QRCodeScanner.android.kt:139-143`), and the voice button requests the microphone (`A/views/chat/SendMsgView.android.kt:7-17`), so carried-over rows (01 §8, 02 §E) would otherwise meet the system dialog (Notes).
3. **Network validation.** The app reports the network as offline when Android hasn't validated it (`NET_CAPABILITY_VALIDATED`, `A/helpers/NetworkObserver.kt:56-66`) and passes that to the core (`apiSetNetworkInfo`, `:75-92`). With `wd.sh net isolate` the captive-portal check can't reach the internet, so the runner sets `settings put global captive_portal_mode 0` before the run; open question 2 asks to verify that the network then counts as validated.
4. **Reset.** In-process `resetForTest` as on desktop (research doc §3.2), run before `MainActivity` is launched: the reset's pre-set prefs and `clearUiState` (plan §7.3, including file-level UI state such as the chat list's saved scroll position, read when the list is first composed, `C/views/chatlist/ChatListView.kt:240,907`) must be in place before `onCreate` reads `privacyProtectScreen` (`APP/MainActivity.kt:49-55`) and composes the root, so the test uses `createEmptyComposeRule()` and calls `ActivityScenario.launch(MainActivity::class.java)` after `app(…)`, instead of an activity rule that launches before the test body; at its end each test finishes every app activity (every `MainActivity` and `CallActivity` instance, found through `ActivityLifecycleMonitorRegistry`; a notification tap replaces `MainActivity` through `TaskStackBuilder`, `APP/model/NtfManager.android.kt:270-286`, so closing the scenario alone can leave an instance alive) and waits until they are destroyed, before the next reset, because `MainActivity` is `singleTask` and a live instance would be reused through `onNewIntent` with no fresh composition, and its later `onDispose` handlers would run after the reset (`C/views/chatlist/ChatListView.kt:978-980`, `C/views/chat/ComposeView.kt:1447-1462`). Once per process, before the first reset, a boot step handles the app's own startup: `SimplexApp.onCreate` already started `initChatControllerOnStart()` in the instrumentation process (`APP/SimplexApp.kt:83-87`, `C/platform/Core.kt:59-74, 188`), which after `pm clear` creates the first database (~45 s under translation), longer than the reset's 10 s wait for `ctrlInitInProgress` (plan §7.2); the boot step waits for it (`chatDbStatus != null && !ctrlInitInProgress`, 120 s bound; `initChatControllerOnStart` only launches a coroutine, `C/platform/Core.kt:59-67`, so the flag alone can still be false at first), stops and closes that core, undoes init's pref writes the way `deleteChatDatabaseFilesAndState` does (`C/views/database/DatabaseView.kt:577-580`: `ksDatabasePassword.remove()`, `newDatabaseInitialized = false`, and `storeDBPassphrase = true` as it also sets, and the `initialRandomDBPassphrase`, `privacyDeliveryReceiptsSet` and `onboardingStage` keys removed; init wrote them at `C/views/helpers/DatabaseUtils.kt:56-59`, `C/platform/Core.kt:128,154,168`; otherwise every reset would restore the boot database's key and fixture databases would be opened with it), sets `AppearanceBarsBlurRadius` to 0 (toolbar blur off in every test, for performance, as on desktop, plan §7.2; devices on API 32+ default it to 50), and only then takes the plan's `ModelSnapshot`/`PrefStores` captures (plan §7.3), with no user in that state because the runner runs `pm clear` before every `am instrument` except the second half of a test split by a process restart (open question 14), which runs alone in its invocation; after `pm clear`, which revokes all runtime permissions and clears all notifications (SDK `android/app/ActivityManager.java:3544-3550`), the runner applies that invocation's `pm grant`/`pm revoke` (setup item 2, the `PERM` groups) and only then runs `am instrument`. The captured `ChatModel` state is the post-init state, so the boot step first sets the fields init wrote (`chatDbStatus` to null, `chatDbEncrypted` to false, `conditions`, `currentUser`, …; `chatRunning` and `localUserCreated` are reset too, harmlessly) back to their declared initial values before capturing (`ChatModel` is an object, so the list of fields init writes is fixed by P1 and checked against the desktop snapshot, which is taken before any init), as plan §7.3's reset and `restartCore`'s wait for `chatDbStatus` need; Android's `PrefStores` captures the app's two `SharedPreferences` files and restores them through `SharedPreferences.Editor` (clear, put, commit), not by rewriting the XML files, which the per-process cache would not see (`ContextImpl.java:635-646`, `MODE_PRIVATE`); the files are the `SHARED_PREFS_ID` and `SHARED_PREFS_THEMES_ID` preferences (`A/platform/Resources.android.kt:40-41`, wrapped at :43-44) instead of the desktop properties files, and `themes.yaml`, a plain file in `shared_prefs` (`A/platform/Files.android.kt:21`), as on desktop. A process that continues a test split across two `am instrument` runs (open question 14) skips the boot step's stop, undo and capture and the per-test reset (no `resetForTest`; it launches `MainActivity` as soon as init's wait completes), since its state is the first half's and must be kept; `pm clear` (1 s; the first database after it takes ~45 s under translation) only as above. The system clipboard is cleared (`ClipboardManager.clearPrimaryClip()`; it persists across tests, carry-over rule R13). Notifications are cancelled (`NotificationManager.cancelAll()`), `WorkManager` work is cancelled and the battery/background shell state is restored at the end of every test that changes them.
5. **Message field.** On Android the compose field is an `EditText` inside `AndroidView` (`A/platform/PlatformTextField.android.kt:99-197`), not a Compose text field, so `performTextInput` can't type into it. The shared `UiNode.type()` (plan §7.4) uses Espresso `replaceText` on that `EditText` on Android and then puts the cursor at the end (`setSelection(editText.length())` on the `EditText`; or it types with `typeText`): `EditText.setText` resets the selection to 0 (SDK `android/widget/TextView.java:7504,7519`, `android/text/method/ArrowKeyMovementMethod.java:364`) and the app forwards the selection into the compose state (`A/platform/PlatformTextField.android.kt:123-128,160-167`), where the mention picker reads it (`C/views/chat/group/GroupMentions.kt:104-137,291-310`; carry-over rule R12). With the cursor at the end, carried-over compose and mention rows need no other change. Reads of the message field also go to the `EditText` through Espresso, since Compose semantics don't reach it: its `text` and its `hint`, the placeholder (`editText.hint = placeholder`, `A/platform/PlatformTextField.android.kt:140,177`; e.g. 03 `channel_broadcastPlaceholderAndDelivery` «Broadcast», 02 `compose_clearTextButton_clears`, the 02 draft rows, 02 `mention_picker_select_insertsAndSends`). Shared tests therefore read the field only through `ChatScreen.messageText` and `ChatScreen.placeholder` (plan §9.1), which the Android driver answers by reading `EditText.text` / `.hint` in an Espresso `ViewAction` on the `EditText` (`withText`/`withHint` are matchers that need the expected value, so they can't return it) and the desktop driver from semantics; they don't use `assert(…)` or a text lookup of the placeholder on the field, because a `SemanticsMatcher` can't be re-run on a View and no Compose node carries the hint (on desktop the placeholder is a Compose `Text`, `D/platform/PlatformTextField.desktop.kt:186-191`). The disabled-state overlay text ("you are subscriber", "contact deleted") is a Compose `Text` (:200-212) and is read as on desktop. Rows below that test the field itself have `VIEW`.
6. **One pane.** Android shows either the chat list or a chat (`C/App.kt:313-360`), and modals share one manager (`C/views/helpers/ModalView.kt:253-258`), so screen objects own navigation (research doc §5.3).
7. **Battery state.** On API 33 both Instant and Periodic modes need the app exempt from battery optimisation (`A/helpers/Extensions.kt:8-16`). The runner allow-lists the app before the run (`dumpsys deviceidle whitelist +chat.simplex.app.debug`) and allows background work; §2 rows that need the optimised or restricted state change it with `SHELL` and restore it.
8. **Notification taps recreate the activity.** Notification intents are built with `TaskStackBuilder` (`APP/model/NtfManager.android.kt:270-286`), which clears the task, so `MainActivity.onCreate` runs again and handles the action (`APP/MainActivity.kt:44-48,121-142`); queries keep working through `ComposeRootRegistry`, but tests must not hold references to the old activity.

## Notes

- `AV` marks rows that assert sound or playback; rows that only incidentally play a sound (the foreground incoming-call ringtone, `C/views/call/IncomingCallAlertView.kt:31-33`, and the outgoing connecting sound, `A/views/call/CallView.android.kt:152`) carry no `AV` in this file; as on desktop, the harness installs the seam fakes for every test (plan §11.2, R10), so no real sound plays.

**Carry-over from 01–04.** `05-android-carryover.md` names every 01–04 test whose Android behaviour or harness mechanism differs, with its class (REPLACED by a named 05 test, DESKTOP-ONLY, or ADAPT), what changes and the code refs; a test not listed there runs on Android unchanged. The general rules behind it (its R1–R13):
- Right-click does nothing on Android (`Modifier.onRightClick` returns the modifier unchanged, `A/platform/Modifier.android.kt:16`); every `onRightClick` in the shared code sits next to a `combinedClickable(onLongClick = …)` with the same action, so the driver uses `longClick()` (01 setup item 8) for "right-click" entries, and rows named for the right-click test the long press of the same handler.
- The message field is an `EditText` that handles no keys (`A/platform/PlatformTextField.android.kt:60-63`): Enter inserts a line break, the send button sends (`C/views/chat/SendMsgView.kt:452-490`), and Shift+Enter, Up, Ctrl+V and typed file paths (`D/platform/PlatformTextField.desktop.kt:97-110,123-150`) don't exist; files are attached through the §6 "File" stub.
- `FD` rows use `INTENTS` stubs (§6, §11); `shareText`/`shareFile` open the system chooser (§6 note); the item menu's "Copy" sets only the item's text, with no toast (§6).
- Onboarding has no passphrase step and no "Link a mobile", the welcome button is "Get started", and "Continue" on "Your network" applies the notification mode (§1).
- The new-chat entry is "Paste link / Scan" and opens the connect screen with the camera section (`C/views/newchat/NewChatSheet.kt:61,194`); `CAMERA` and `RECORD_AUDIO` are pre-granted (setup item 2).
- `NTF` rows assert through `SYSNTF` (§3); 04 §C lock rows set "Lock mode" to "Passcode" first and read the Keystore-encrypted passcode prefs through `DatabaseUtils.ksAppPassword` (§10, §11); calls start `CallActivity` instead of the URI handler (§9); Esc becomes the system Back key (§13); `REC`/`AV` rows need Android actuals of the plan §11.2 seams (`A/platform/RecAndPlay.android.kt`, `A/platform/VideoPlayer.android.kt`).
- `TOAST` steps read the accessibility events of the system toast (R11; Needs codes, open question 13); the Android `type()` leaves the cursor at the end of the text, which the mention picker needs (R12, setup item 5).
- `URI` steps assert the outgoing `ACTION_VIEW` with `INTENTS`, and `CB` steps use the real system clipboard, which the reset clears (R13, setup item 4); 02 §B link-preview rows fetch `http://127.0.0.1:<port>`, which needs a debug-only network-security-config allowing cleartext there (open question 15).
- Desktop-only areas: 04 §K "Link a mobile" (Android is the host, §12), 04 §M window and tray, the update checker, text selection across messages, `IMGCB`, and `MCAST` on loopback.

**Excluded.** Badge display and purchase screens are excluded as in the plan (Play Billing is in the `google` flavor only). `showUnlinkDesktopAlert` (`C/views/remote/ConnectDesktopView.kt:570-579`) has no caller and no visible entry point, so it has no row (plan §11.3). `androidAskToAllowBackgroundCalls` is reached only from the call pill (§9).
