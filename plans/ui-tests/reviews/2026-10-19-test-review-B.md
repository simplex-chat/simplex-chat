## Summary

### (1) Verdict counts (39 tests)
- **KEEP: 29**
- **STRENGTHEN: 7**: presetFilterFavorites, presetFilterContacts, presetFilterBusinesses, createListDuplicateNameError, deleteListConfirm, searchFiltersByDisplayName, searchFiltersByAlias
- **MERGE: 3**: createListWithEmoji → editListNameAndEmoji; chatListTitleAndProfileButton → chatListScrollToTopOnTitleClick; subscriptionIndicatorConnected → subscriptionIndicatorPercentageToggle
- **DROP: 0**. searchFiltersByDisplayName becomes a DROP if it is not strengthened.

### (2) The 5 most valuable
1. **presetFiltersCollapsedMenuWhenMany**: covers the most intricate logic in `TagsView` (the chip/menu threshold, menu contents, the "All" item shown only while a filter or search is active, the selected icon). It checks both presence and absence on both sides of a state change.
2. **unreadFilterToggle**: real peers. It is the only test of the muted branch of `unreadTag`, and it is guarded so the muted negative is not trivially true.
3. **searchPasteLinkTriggersConnectPlan**: one UI path that covers link detection, the read-only field, the core connect plan, the alert, and cleanup.
4. **listUnreadDot**: `unreadTags` bookkeeping across message arrival and mark-read. That counter code is hand-incremented in several places (CM:380-391, 1052-1085), so it is easy to regress.
5. **presetFilterReports**: the full report flow through three clients into the GROUP_REPORTS counter and the always-shown chip next to the collapsed menu.

(Close runners-up: addChatToListFromContextMenu, which covers both entry paths, and searchPasteKnownGroupLinkFiltersToGroup.)

### (3) The weakest 5
1. **searchFiltersByAlias**: vacuous on desktop. The contact becomes the open chat, and the open chat is always listed, so the alias assertion passes regardless (traced above).
2. **searchFiltersByDisplayName**: a strict subset of searchClearsWhenFilterChanges, and its only negative is the notes folder.
3. **chatListTitleAndProfileButton**: a string-resource check plus navigation that dozens of other tests already do.
4. **subscriptionIndicatorConnected**: its "%" step duplicates the toggle test, and its only state is the trivial 1/1 = 100%. The useful states (partial or offline) are untested.
5. **presetFilterBusinesses**: the negative set is only the notes folder, so a BUSINESS filter that over-matches groups or contacts passes.

### (4) Important untested features, ranked by regression risk
1. **Auto-clearing the active filter when its set empties** (`clearActiveChatFilterIfNeeded`, CM:1121-1128; called from CM:346/356/377/1117 and TLV:456). Cases: un-favoriting the last favorite, deleting the active list, archiving the last report. A regression leaves the user on an empty list with no chip to tap. No test covers any of these paths.
2. **The open-chat-always-listed rule** (CLV:1568, 1571). Nothing tests it directly, and it silently masks other search and filter assertions on desktop (see searchFiltersByAlias).
3. **Unread filter semantics beyond All/None**: mentions-only groups (CM:1477), "Mark unread" chats (`unreadChat`), and a chat appearing live while the filter is on.
4. **Search with an active filter**: with search text entered, `filteredChats` ignores `activeFilter` entirely (CLV:1569-1582) while the chip stays highlighted. There is also no test of case-insensitivity, full-name or group-name matches, or exclusion of `chatDeleted` / `contactCard` contacts (CLV:1568, 1573).
5. **Lists on groups**: every list test uses contacts. The `ChatInfo.Group` branches of `setTag` and `deleteTag` (TLV:430-435, 465-469) are untested.
6. **Contacts preset breadth**: requests, pending connections, business-customer chats (CLV:1597-1603). The catalogue promises these.
7. **Catalogue rows with no test**: `searchKnownNameFiltersChat` (needs NAMES), `presetFilterChannels` (needs a relay), `reorderListsDrag` (no semantics action), `subscriptionIndicatorServerDown` (needs SRVCTL). I confirmed none of them exists anywhere in the tree.
8. Smaller gaps: the Connect-to-name row tap, the delete-list Cancel path, hidden users being excluded from the profile badge, and pasting a one-time invitation into search.

### (5) Overall judgement
These tests exercise real user features through real UI paths. Most use real CLI peers and assert on what the user sees: row presence, chip and menu texts, alert texts, editable field state. Model reads are mostly preconditions or membership facts that directly drive the UI (`chatTags`, `activeChatTagFilter`), so the keys-only rule costs little here. There are no tests of the harness itself and no trivially-true assertions, with one exception: searchFiltersByAlias on desktop.

The filter and list suite is the stronger half. Each preset test has at least one chat of another kind that must disappear, and the collapsed-menu test covers the trickiest branch logic. The weakness is coverage shape. The tests check that each filter selects correctly on entry, but none checks that the filter state stays coherent when its underlying set changes (filter auto-clear, open-chat exemption, search overriding the filter), which is where regressions are most likely in this code.

The toolbar and search half has two redundant tests, one test that is vacuous on desktop, and one trivial smoke test. The link-paste tests in it are good.

Net: useful for catching regressions in selection logic, preset layout, list CRUD and link-paste. They would miss most regressions in state-transition and edge cases. The 7 STRENGTHEN changes are each a few lines, and together they would close the top two gaps.
