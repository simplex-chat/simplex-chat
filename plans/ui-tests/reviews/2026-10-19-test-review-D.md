Scope: 31 `@Test`s in `common/src/uiTestShared/kotlin/chat/simplex/app/ui/{chat,groups,main}` (classes listed in the brief). Paths below are relative to `apps/multiplatform/common/src/` unless they start with `plans/`, `scripts/` or `src/Simplex`.
Abbreviations: S = `uiTestShared/kotlin/chat/simplex/app/ui/harness/Screens.kt`, H = `.../harness/Helpers.kt`, PL = `.../harness/PeerLines.kt`, UT = `desktopTest/kotlin/chat/simplex/app/ui/harness/UiTest.kt`, CIV = `commonMain/kotlin/chat/simplex/common/views/chat/item/ChatItemView.kt`.

## Cross-cutting findings (apply to several rows)

- X1 "Compat" is only a name. CONFIRMED. Every peer is the CLI built from the current tree: `scripts/uitest.sh:32` (`cabal list-bin ... exe:simplex-chat`), written to `env.properties` (`:68`) and read as one value `UiEnv.cli` (`desktopTest/.../UiEnv.kt:16`). Android peers come through `UiBridge`, which uses the same `UiEnv` (`desktopTest/.../UiBridge.kt:19-21`; `scripts/uitest-android.sh:53`). There is no `peerVersion`, no `CliVersion`, no `…CompatStableTest` and no `StableCompat` category. The plan itself says so: `plans/ui-tests/2026-10-10-desktop-ui-test-dsl-plan.md:1011` and `:1084` ("none of the category, Compat-stable or traceability machinery is built"). The `-f uitest` flag only adds the `uitest-servers` executable (`simplex-chat.cabal:37-38,684-687`), so the CLI is the same as the app's core. So the 4 Compat tests in scope check nothing about version skew. They are also each a strict subset of another test (rows 13, 17, 20).
- X2 The send helper hides "Enter did not send". CONFIRMED. `ChatScreen.enterWhenSendable` (S:270-276) presses Enter, waits 5 s, and presses Enter again if the field is still full. A regression where the first Enter is dropped (focus or IME handling) passes every test that uses `send`, including the one whose whole point is "Enter sends" (`sendText_enter_peerReceives`).
- X3 `Ui.Alert.Confirm(Shared)` is one key for every alert's confirm button. CONFIRMED (`commonMain/.../views/helpers/AlertManager.kt` diff: `Modifier.ui(Ui.Alert.Confirm(uiSource))` on every confirm button; `commonMain/.../ui/Ui.kt:172`). Tests that click it without first checking which alert is open (`joinGroupFromList` H:412, `leaveGroup_fromChatListMenu`, `MemberInfoScreen.changeRole` S:318) cannot catch a wrong or missing alert title. They still catch the wrong action, because the CLI checks the result.
- X4 `ChatListScreen.gone()` checks only the model (S:72-74). It cannot catch a row that is still drawn after the model drops the chat. That is unlikely, but the fix is cheap: capture the id first, then poll `!exists(Ui.ChatList.Row(id))`.
- X5 `ChatListScreen.request()` (S:56-60) looks for "Open to accept" anywhere on screen (`seesText(..., substring = true)`), not in the named row. This is harmless with one request. It would pass for the wrong row once two exist. PLAUSIBLE.
- X6 The harness swallows two app errors. CONFIRMED (UT:45-55, 352-358). "Controller is not initialized" and "database closed" are retried and ignored when they are thrown before the body starts or after it finishes. A regression in start-up or shut-down that throws these errors would never fail a test in this scope.
- X7 Catalogue traceability. CONFIRMED. The legend maps `reply_menu_sendQuoted_peerSeesQuote` to `ReplyTest`/`ReplyCompatTest` (`plans/ui-tests/catalogue/00-legend.md:149`), `edit_menu_updatesPeer` to `EditMessageTest` (:150), `reaction_add_peerSeesAdded` to `ReactionTest` (:154), `sendText_enter_peerReceives` to `ComposeTest`/`ComposeCompatTest` (:143), `contactRequestMenuAccept` to `ChatListRequestsCardsTest` (:127) and `editProfileDisplayName` to `ProfileEditTest` (:131). The tests actually live in `MessagingTest`, `SendCompatTest` and `ContactsTest`, classes the legend never names. The planned traceability check would flag all of them.
- X8 Peer-line timeouts are uneven. PLAUSIBLE flake. `expects`, `eventually` and `nextLine` default to 15 s (PL:451,469,508). `connect()` waits 60 s for "contact is connected" (H:372). Yet `OneTimeLinkCompatTest:11` waits for the same line with a strict 15 s `expects`. The same 15 s default applies to `deleteContactAndNotify:36`, `editProfileDisplayName:53` and `leaveGroup_fromChatListMenu:43`, all of which are network round trips.
- Setup note (not a defect): most tests connect through `apiAddContact` (H:367-373) and set up groups through CLI hosts (H:383-389), not through the UI. Only the OneTimeLink tests create a link in the UI; only `ownGroup` (S:327-341: create a group, then invite members in the sheet) and `createGroup_opensChatAndInviteSheet` create a group in the UI.

## Summary

### (1) Verdict counts
31 tests in scope:
- KEEP: 24
- STRENGTHEN: 6 (`notes_sendText_saved`, `sendText_enter_peerReceives`, `groupInvitation_tapRowShowsJoinAlert`, `profilesAddProfile`, `contactRequestMenuReject`, `userPickerSwitchProfile`)
- MERGE: 1 (`addressCliConnectsAndRequestAppears`)
- DROP: 0 as written. `sendText_enter_peerReceives` and `groupInvitation_tapRowShowsJoinAlert` become DROP if they are not strengthened, because they are exact duplicates.

### (2) The 5 most valuable tests
1. `oneTimeLinkSwitchToIncognito` checks the privacy promise end to end. The footer depends on the API result, the CLI must see a name other than "alice", and the model must flag the contact incognito. A leak of the real profile fails it.
2. `contactInfoVerifyCodeMatchesCli` compares the screen with a second, independent implementation (the CLI's `/code`). Any change to computing, formatting or wrapping the code fails it.
3. `groupSend_allMembersReceive` covers core group delivery to two independent members, and its wait for the member connection matches the protocol's real behaviour.
4. `delete_received_onlyForMe` checks the option that must be missing (`forEveryone`), the local removal in both model and UI, and that the peer saw nothing, by requiring the next peer line to be the later message.
5. `search_direct_filtersResults` checks the exact set of results in the model and that the matching item nodes are present and the non-matching one is absent. It is hard to pass by accident.

Close behind: `memberInfo_removeMember` (two peers check the relay), `oneTimeLinkCliConnectsViaShortLink` (the only plain UI-made link) and `reaction_received_chipCount` (a UI count from a peer event).

### (3) The weakest 5
1. `addressCliConnectsAndRequestAppears`: a strict prefix of three other tests, and "Compat" is not wired, so it adds nothing.
2. `groupInvitation_tapRowShowsJoinAlert`: never checks the alert it is named after. It clicks a generic confirm key, and its body is the setup of `leaveGroup_fromChatListMenu`.
3. `sendText_enter_peerReceives`: the same text and assertion as ChatSearchTest:12-14. It cannot catch "Enter needs two presses", because the helper presses Enter again after 5 s (S:273-275).
4. `profilesAddProfile`: model-only, contained in `userPickerSwitchProfile`, and it skips the catalogue's "lists it" check.
5. `userPickerSwitchProfile`: it never shows the list changed while the other profile was active, so it misses a list that never reloads.

(`notes_sendText_saved` is next: "saved" is never checked across a restart.)

### (4) Important features in this area with no test, ranked by regression risk
1. Files, images and voice messages: send, receive, auto-receive, preview, open and save. These go through XFTP, JNI and the file views. Nothing in the 157 tests in the repo sends or receives a file.
2. Delivery and read receipts, and item status ticks (`CIMetaView`): every regression here is user-visible, and nothing tests it.
3. Group links: creating a group link and joining by link. All joins in the suite are CLI `/a` invitations. Pasting a link in the UI only covers the connect plan (`searchPasteLinkTriggersConnectPlan`), never connecting or joining.
4. Disappearing (timed) messages: the preference, the timer, and deletion when it expires.
5. How received messages look in the GUI: quotes from the peer, group messages received by alice, jumping to a quoted item. Every check of message content is on the CLI side, except edit, search, chips and notes.
6. Group moderation: deleting a member's message for everyone, blocking a member, and admin rights in member info beyond change-role and remove.
7. Mentions in group compose (sending `@member`). Only the row badges are tested (`mention*` in ChatListRowsTest).
8. Contact and group preferences (full deletion, voice, reactions off) and how they gate the item menu (`delete_forEveryone_fullDeletion_peerSeesDeleted` is not written).
9. Incognito outside 1-time links: joining a group incognito, "Accept incognito" on a request (`contactRequestMenuAcceptIncognito` is not written).
10. Message info and edit history, live messages, drafts kept across a chat switch (only the row preview of a draft is tested).
11. Calls: there is no test even at the level of the invitation reaching the peer.
12. Hidden profiles and profile passwords, and deleting a profile.

### (5) Overall judgement
- **Real features.** Nearly every test drives a real feature through the real UI and checks the result with an independent oracle, usually the peer CLI's output. That catches regressions in the app, the protocol and the core, not only on screen. Model-only assertions are rare and mostly justified (edited flag, member role, incognito flag). Only `profilesAddProfile` relies on the model where a UI check was easy and was the point of the catalogue row.
- **Thin coverage.** The 31 tests are mostly one happy path per feature. They cover text messaging, reply, edit, delete, reactions, forward, search, contact requests, verification, alias, profile rename, 1-time links and basic group membership. Media, receipts, timed messages, group links, moderation and how received messages look are not tested at all, and that is where the regression risk is highest.
- **Compat is not wired.** The 4 "Compat" tests run against the same-tree CLI (`scripts/uitest.sh:32`) and are duplicates of other tests. Version compatibility between app and CLI, the one class of regression only these tests could catch, is untested.
- **Harness masking.** Two harness behaviours hide real regression classes: the second Enter press (X2) and the ignored "Controller is not initialized" / "database closed" errors around the test body (X6). The generic `Alert.Confirm` key (X3) means alert titles are never checked unless a test checks the text itself.
- **Usefulness.** High for catching a break in a core flow (send, edit, delete, join, leave, connect). Low for UI-detail regressions and for any feature outside that list. Fixing X2 and X1, plus the 6 strengthenings, needs no new keys and would turn the 3 duplicates into tests that each catch something.
