Harness facts that the verdicts depend on (all CONFIRMED):
- H1. `app(null)` copies a DB template and sets `storeDBPassphrase=true` and `EncryptedDBPassphrase` *before* the test starts (`T/harness/DbTemplate.kt:17-23`, `T/harness/UiTestApp.kt:67`).
- H2. `app("alice")` makes the user through the API, sets `OnboardingComplete` and calls `setLastVersionDefault` (`T/harness/UiTestApp.kt:76-83`). So no onboarded test goes through onboarding or sees What's New unless it sets that up itself.
- H3. On desktop, `restart()` stops the core, clears UI state and runs `initChatControllerOnStart` (`T/harness/UiTest.kt:93-101`, `UiTestApp.kt:87-99`, `Reset.kt:54-62`). It does **not** reload `settings.properties` or `AppPreferences` state from disk. Prefs survive a restart in memory, so a "persists across restart" check only proves persistence through its `storedSetting(...)` file check.
- H4. `escape()` calls the top `simplexWindowState.backstack` entry directly (`T/harness/UiTest.kt:200-204`) and skips the Window key handler (`D/DesktopApp.kt:126-127`). That's acceptable: the handler is a one-line mapping.
- H5. `OnboardingSharedState.selectedOperatorIds` is a global (`C/views/onboarding/YourNetwork.kt:39-41`) that the model snapshot does not reset (`S/harness/CommonReset.kt:19`). Each YourNetwork composition overwrites it (`YourNetwork.kt:54-56`). That makes the leak harmless for these tests, but a test that enters Step4 directly would read stale data (`ChooseServerOperators.kt:51`). PLAUSIBLE leak.
- H6. Both preset operators are `enabled = True` (`src/Simplex/Chat/Operators/Presets.hs:27,41`), and onboarding starts its selection from the enabled set (`YourNetwork.kt:50-52`).

## Summary

### (1) Verdict counts (34 test methods; the HarnessResetTest pair counted separately)
- KEEP: 18 (`onboardingWhySimplexIsBuiltOpensHowItWorks`, `onboardingCreateProfileButtonDisabledForEmptyName`, `onboardingCreateProfileInvalidNameShowsCorrectionAlert`, `onboardingCreateProfileBackReturnsToWelcome`, `onboardingMigrateFromAnotherDeviceOpensMigrationScreen`, `onboardingSetPassphraseMismatchDisablesButton`, `onboardingYourNetworkShowsSetupRouters`, `onboardingHowItHelpsPrivacyInfo`, `onboardingConditionsLinkOpensConditionsText`, `onboardingLinkAMobileShowsQrAndDeviceName`, `onboardingLinkAMobileBackReturnsToWelcome`, `whatsNewNotShownForNewUser`, `whatsNewFromSettings`, `whatsNewShowsViewUpdatedConditions`, `bootShowsChatListForNewUser`, `cliConnectsToGuiInvitation`, `a_leavesStateBehind`, Android `bootCreatesUserAndShowsChatList`)
- STRENGTHEN: 8 (`onboardingUseRandomPassphraseAlert`, `onboardingPassphrasePersistsAcrossRestart`, `onboardingChooseOperatorsCannotDeselectAll`, `onboardingAcceptConditionsCompletesOnboarding`, `onboardingThenConnectToCliPeerViaLocalServers`, `whatsNewShownAfterVersionUpgrade`, `appearance_settingsPersistAcrossRestart`, `b_startsClean`)
- MERGE: 6 (`onboardingWelcomeShowsDesktopActions`, `onboardingCreateProfileValidName`, `onboardingSetDatabasePassphrase`, `onboardingContinueGoesToConditions`, `onboardingNoNotificationsStepOnDesktop`, `whatsNewOkCloses`)
- DROP: 2 (`onboardingChooseOperatorsToggle`, `measureResetsFramesAndCapture`)

Net effect if applied: 34 → 26 methods with strictly more coverage, and about three fewer 30 s encryption runs and five fewer onboarding boots.

### (2) The 5 most valuable
1. `onboardingPassphrasePersistsAcrossRestart`: checks a real security property end to end (no stored passphrase in the settings file, plus a real prompt after restart). A regression here is silent and serious.
2. `onboardingThenConnectToCliPeerViaLocalServers`: the only test proving a freshly onboarded app actually has a running chat that can connect. It catches "onboarding finished but chat not started" (`SetNotificationsMode.kt:121-129`).
3. `whatsNewShowsViewUpdatedConditions`: asserts core state (`notifiedAt`), not just a screen, and isolates the conditions trigger from the version trigger.
4. `onboardingLinkAMobileShowsQrAndDeviceName`: covers the desktop-only path (passphrase detour, then `startRemoteHost` producing a real `xrcp:/` invitation). It would catch the remote-host FFI breaking.
5. `onboardingCreateProfileInvalidNameShowsCorrectionAlert`: exercises the core `chatValidName` FFI through the UI, the info icon, the alert and the write-back. A cheap test with a high regression yield.

Runners-up: `whatsNewNotShownForNewUser` (a negative check made non-vacuous by its precondition) and `onboardingChooseOperatorsCannotDeselectAll` (a real guard, `ChooseServerOperators.kt:191`).

### (3) The weakest 5
1. `onboardingChooseOperatorsToggle`: fully subsumed by `CannotDeselectAll`, and model-only (`OnboardingTest.kt:196,201`).
2. `onboardingUseRandomPassphraseAlert`: its storage assertion (:137) is CONFIRMED vacuous, because the DB template pre-sets both values (`DbTemplate.kt:20-21`). Only the stage transition is real.
3. `onboardingContinueGoesToConditions`: re-asserts exactly what the `toConditions` helper already polls (`OnboardingScreens.kt:40-44`), and two other tests then click those nodes.
4. `onboardingAcceptConditionsCompletesOnboarding` (operator part): `enabledOperatorIds() == selected` holds by construction with the default selection (both presets enabled, `Presets.hs:27,41`, `YourNetwork.kt:50-52`), so "Accept applies my choice" is untested.
5. `measureResetsFramesAndCapture`: `@Ignore`'d benchmark, zero regression value. Close behind: `onboardingNoNotificationsStepOnDesktop` (one negative check on a structural `if`, at the cost of a full onboarding) and `onboardingCreateProfileValidName` (redundant with its own helper).

### (4) Important features with NO test, ranked by regression risk
1. **Unlocking an encrypted DB at startup with the passphrase.** The catalogue defers it to `dbError_enterPassphraseOnStartup_open` (catalogue 01 §1 row 5), but no such method exists in the tree. If it breaks, the user is locked out of their data. The existing test stops at the prompt.
2. **The operator choice made in onboarding reaching the core.** `acceptConditions` → `enabledOperators` → `setServerOperators` with a non-default selection (`ChooseServerOperators.kt:299-317,337-365`), including the role back-fill for the first enabled operator. This includes the catalogued `onboardingAcceptButtonDisabledWithNoOperators`, which is not implemented.
3. **The chat working after "Set database passphrase".** `startChat(newKeyValue)` re-inits the controller (`SetupDatabasePassphrase.kt:69,229-234`); nothing checks `chatRunning` or any API call afterwards, and no test completes onboarding after encrypting.
4. **The Android onboarding happy path**, including the notifications-mode step (`YourNetwork.kt:107-111,125`, `changeNotificationsMode`). No Android test in this scope goes through onboarding; only back-key tests touch it (`android/src/androidTest/java/chat/simplex/app/ui/back/BackKeyTest.kt:162,174`). The mobile profile layout's `setLastVersionDefault` (`WelcomeView.kt:305-307`) is also untested.
5. **Onboarding when only hidden users exist** (`WelcomeView.kt:398-410`, `SetNotificationsMode.kt:122-123`). Catalogued as `onboardingCreateProfileWhenOnlyHiddenUsersExist`, not implemented. It is a known source of "stuck on onboarding" bugs (see the comment at `WelcomeView.kt:406-407`).
6. **Appearance actually applied.** 23 of the 24 catalogued Appearance rows (04 §D) are missing: colour mode → `CurrentColors.value.base`, dark-theme choice, font/zoom reset taps, wallpapers, theme import/export, per-user themes. The one test only proves the prefs are written.
7. **A random passphrase opening without a prompt after restart.** This is the default path for most desktop users and the mirror of #1.
8. **What's New pagination and "Read more"** (catalogued `whatsNewPaginationPrevNext`, not implemented; `WhatsNewView.kt:150-166,253-261`).
9. **New users get `privacyShowEncryption=false`** (`WelcomeView.kt:395`). Low risk, but it is a silent behaviour difference between new and existing users.

### (5) Overall judgement
These tests drive the real composed app (`AppScreen`, real core over FFI, real alerts and modals) through real user entry points, so they are genuine UI tests, not unit tests in disguise. Using the model for operator selection and contact readiness is defensible under the keys-only rule and still catches realistic regressions. But coverage is wide and shallow. Most onboarding tests stop at "the next screen appeared": they check the step an action leads to, not what it does. The two places where the outcome matters most both stop short or assert something trivially true: the operator choice (#17 is vacuous by construction, #15 stops before Accept) and the passphrase (the random path's storage check is pre-satisfied by the harness, and the encrypt path never unlocks). Desktop restart doesn't reload prefs from disk, so every "persists across restart" claim rests on its settings-file check alone; the Appearance test is honest about that only by accident. About a quarter of the onboarding methods are duplicates of helper preconditions or of each other.

As a regression net they would reliably catch broken navigation, labels, alerts, the auto-open logic of What's New, name validation, and "chat not started after onboarding". They would not catch: the user's operator choice being ignored, a failed controller re-init after encryption, an encrypted DB that can't be unlocked, theme application breaking, or any Android onboarding regression. The suggested changes are a handful of extra clicks and model assertions in existing tests, plus one harness fix for `restart()`. Making them would turn this from "screens appear" into "choices take effect", with fewer methods.
