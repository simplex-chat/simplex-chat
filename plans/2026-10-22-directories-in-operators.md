## Summary: what ep decides

Directories become a fifth list in each operator's servers and under Your servers, stored, preset and merged at start-up exactly like chat relays, with SimpleX Directory preset for the SimpleX Chat operator (boards 10–12). A search asks every directory in use at once and shows one list, with a retry row per failed directory and a submenu saying which directories listed a result (boards 13–17); a channel or public group several directories list shows once, while an ordinary group, which each directory lists under its own link, shows once per directory (open question 15). This is plan 015's option A, re-checked against today's code, with its open review notes folded in. Changed from plan 015: searches are sent in ep's envelope as an MCP tool call, and "Test directory" checks that the directory offers that tool (section 4.6.4); consent remembers only the operators' preset directories, a directory the user adds is agreed to by adding it, and a second alert asks before a preset not yet agreed to receives a search (section 4.4); results keep settings order, with the earliest directory's entry for a shared channel and a 15 s hold per directory; a directory is in use by its own switch, whether or not its operator's servers are on; a preset its operator drops is kept turned off rather than deleted, and that rule ships only with the first version that drops one (section 4.2); the core sends no "no directories" warning, and refuses these apps' searches to anything but a directory in use in that profile (one undocumented command, section 4.2). The release order (open question 3) is a new question.

ep's newest direction, a generic MCP-style service layer in which a service fills a role when it offers the role's tools, is answered in section 4.6, against his own draft (docs/protocol/agent-protocols.md, 2026-10-19). Plainly: this design replaces "a role inferred from the tools a service offers" with "the user puts a directory in the Directories list", and then checks the one tool that list needs. Once users can add directories, whatever the apps send becomes the protocol every other directory implements, so from that release the apps speak ep's envelope with MCP to every directory, and SimpleX Directory answers it before the apps ship (pull request 2). A later move to services as the services design plans them then keeps the storage, the search, the consent, the screens' places and the request format; it renames the screens, stores each service's tools and roles, migrates the rows and keeps the old settings key for a release (~1,400 lines, or ~2,750 with the core taking over requests and the `protocols` declaration; section 4.6.3). Telemetry, the next service ep named, needs explicit consent; assuming each operator would receive its own, in this design it is a switch on the operator's screen, and if only the app vendor receives it, a switch in Privacy settings with one built-in address, as badges have; either design needs the same privacy-policy change first, and a simplexmq change so the receiving operator can't tie a report to the device (section 4.6.2).

Decisions asked of ep (open questions 1, 2, 3, 9, 13, 14, 15 and 16): this design or the service layer first; if this design, the core pull request to master right away, ideally before directory search is released; whether directory search ships before several directories (recommended) or waits for them; whether a directory follows its operator's servers switch (recommended: no, its own switch decides, so Flux-only users and self-hosters keep directory search, asked first); which protocol directories speak (recommended: his envelope with an MCP tool `simplex.directory.search`, the contract the services design also proposes, from the release that lets users add directories, with his draft documenting the core's compression of large replies); whether to ship while colluding directories can link one search (recommended: yes); whether an ordinary group two directories list may show twice (recommended: yes, each row naming its directory); and whether a directory the user added may show SimpleX names on its results (recommended: no, only operators' directories). Section 12 compares this design with the services design as both stand.

## 1. Goal and acceptance criteria

What the user gets, all parts together: directories are listed and added like chat relays; each search goes to every directory in use (section 4.1) and the results arrive as one list; a directory that fails gets its own retry row while the others' results stay; the enable alert names every directory a search will reach and asks again before an operator's directory the user hasn't agreed to receives a search; a result's long-press menu shows which directories listed it, each opening that directory's settings.

## 2. Non-goals

- The service layer itself and telemetry (the other design; sections 4.6 and 12 say how they would fit).
- Inferring a role from the tools a service offers: the user chooses directories by putting them in the list.
- The core's `protocols` declarations from ep's draft (planned there).
- Sorting results across directories by member count (a directory could inflate its counts).
- Linking-resistant reply queues (a simplexmq change the search review proposed; open question 14).
- CLI commands for directories (tests use `/_servers` JSON, as `enableNamesRole` does).
- Documenting the servers API for bots (it is undocumented today).
- Raising the remote-desktop minimum versions.

## 4. Design

### 4.1 The model

Directories become a fifth list of each operator group, stored and preset as chat relays are, so every layer that handles relays gains a list rather than a new concept: the operator screens get a "Directories" section where they have "Chat relays", Add server gets "Directory" where it has "Chat relay". The apps search the directories in use of the active profile instead of one constant, keeping per directory the state they keep today for one (cursor, count, failure), and merge the pages into the one list they already draw.

**In use:** a directory is in use when it is enabled ("Use for search") and not deleted, whether or not its operator's servers are turned on. One rule decides who receives a search, who the alerts name, whether "Search in Directory" shows, and the "No directory is in use" note. An operator's "Use servers" switch covers its message and file servers and chat relays, and turning it on accepts its conditions; a directory is a service the user agrees to by name in the consent alert, so a user who chose only Flux at onboarding, or runs their own servers with both operators off, still finds SimpleX Directory, asked first (open question 9). The apps compute the rule from `/_servers`.

### 4.2 Core: storage, presets, start-up

New mechanisms, each with its requirement:

- Type `UserDirectory' s {directoryId :: DBEntityId' s, address :: ShortLinkContact, displayName :: Text, domains :: [Text], preset :: Bool, tested :: Maybe Bool, enabled :: Bool, deleted :: Bool}`, with `UserDirectory`, `NewUserDirectory`, `AUserDirectory = AUD (SDBStored s) (UserDirectory' s)` — boards 10–12 (a list with name, test state and "Use for search"). `deleted` is the API's delete-on-save flag, as for relays; there is no `deleted` column (nothing references a directory, so delete is a plain DELETE).
- `directories :: ListDef UserDirectory` in `UserOperatorServers` and `directories :: ListDef AUserDirectory` in `UpdatedUserOperatorServers`, so a servers response or request without the key (an older phone's core in a remote session; an older app saving) parses as an empty list. An empty list in a request saves nothing and keeps the stored rows (a save only upserts the listed rows and deletes the ones flagged `deleted`) and can raise no directory error, so no "app doesn't know directories" state is needed. `ADirectory`, `directories'`, `aUserDirectory'` in `UserServersClass`. Rejected: a plain list (a missing key fails to parse); `Maybe` in the request (it would distinguish nothing); a hand-written parser with `.:? … .!= []` (an instance where the codebase already has a type).
- Table `directories (directory_id INTEGER PRIMARY KEY, address BLOB NOT NULL, display_name TEXT NOT NULL, domains TEXT NOT NULL, preset INTEGER NOT NULL DEFAULT 0, tested INTEGER, enabled INTEGER NOT NULL DEFAULT 1, user_id INTEGER NOT NULL REFERENCES users ON DELETE CASCADE, created_at, updated_at) STRICT`, `idx_directories_user_id`, unique `idx_directories_user_id_address`; Postgres with `BIGINT … GENERATED ALWAYS AS IDENTITY`, `BYTEA`, `SMALLINT` as `chat_relays` — per-profile storage, "stored like chat relays" (the teal note). The cascade removes a deleted profile's rows. `domains` is comma-joined text as for relays; the store reads "" as `[]`. `getDirectories` orders by `directory_id`, and grouping takes the list reversed, as it does for servers (it prepends each row), so every group keeps the order in which its directories were added; that is the "settings order" of section 4.4. The store's update and delete filter by `user_id` as well as `directory_id`, so a save for one profile can't change another's row. The id follows `chat_relays`; master switched eight entity tables to AUTOINCREMENT on 2026-10-19 without a stated reason, so the core pull request's reviewer should confirm (nothing keeps a directory's id beyond one save: the apps identify directories by address).
- Presets: `simplexDirectories :: [NewUserDirectory]` in Presets.hs, each built from its operator (`presetDirectory operatorSimpleXChat "SimpleX Directory" <the address above>` takes the operator's `serverDomains` as its domains, so a preset can't name another operator); a `directories` field in `PresetOperator`, set for the SimpleX Chat operator in both `defaultChatConfig` and `terminalChatConfig` (the same list: once the retire rule ships, a config that presets fewer directories under the same operator would retire the others on each start); Flux and the CLI's custom preset have none — "SimpleX Directory preset" (the orange note). A pure test asserts, for both configs, that every preset directory's domains are its operator's and that no address is preset twice (AC8): either mistake would make the operator's merge insert a row that already exists and fail every start. The same test pins the list of preset directory addresses shipped so far and fails when one disappears, with a message pointing to slice 3c: a version that drops a preset without the retire rule would leave it stored, enabled and remembered, still receiving searches.
- One pure pass over the user's flat list of stored directories at start-up, before grouping, in `getServers` (Chat.hs:309-318), with two rules, in this order:
  1. **Adopt.** A row at the address of a directory preset by an operator with a preset entry in the start-up list (`sameShortLinkContact`) is rewritten to that preset's `domains` with `preset = True`, keeping its id, name, tested and enabled flag. Grouping by domains then puts it in the operator's group only, and the per-group merge stays exactly like relays' (a preset matched within its group). This is what makes a third-party directory becoming a preset safe: without it the preset would be inserted beside the user's row and hit the unique index inside the start-up transaction. The adopted directory moves from Your servers to that operator's section, keeping its switch. Rejected: adopting inside `updatedUserServers` (the row stays in the custom group's result too, and the custom group, saved last, turns it back on every start); an upsert on insert (the same save-order problem).
  2. **Retire** (ships with the first version that drops a preset directory: open question 12). A row with `preset = True` whose domains name an operator with a preset entry in the start-up list, and whose address that operator no longer presets, is rewritten to `preset = False`, `domains = []`, `enabled = False`, keeping its id and name. Grouping then puts it under Your servers, where it stays turned off and the user can delete it (the operator screen has no delete). An operator that drops a directory thereby stops the searches it gets, with no new store function; if a later version presets the address again, rule 1 adopts it, still off. Scoping by operators with a preset entry keeps `-s` with `--xftp-server` (no preset operator at all), the CLI and bots (which don't preset Flux), and untagged operators the user made from touching any stored row. Rejected: deleting the row (plan 015's answer): a store delete outside the preset guard, and a later re-preset would insert the address enabled while the consent set (section 4.4) already holds it, so a directory the user had turned off would receive searches without a question.

  Invariants: the pass never changes a row with `preset = False` except to adopt it; it never retires a row at any preset's address; apart from adopting a row at a preset's address, it leaves every row alone whose domains name no operator with a preset entry. Directories of an operator a later version drops entirely stay stored and in use, as its servers and relays do today (Operators.hs:464-465); the plan claims nothing more.

  Costs of retiring, accepted when it ships: the pass can't tell "the operator dropped it" from "this binary presets less". A binary with the retire rule that presets fewer directories (an older app or CLI opening a newer database) retires the directories it doesn't preset, and the next start of the newer one adopts them back turned off, though the user never turned them off. A directory the user added, adopted as a preset by one version and dropped by a later one, comes back turned off, still labelled "(added by you)" if the user turns it on again. Both are silent and fail safe (off, so no search text goes anywhere new). Shipping retire only with the first version that drops a preset keeps this cost away until then; adopt has no such cost (it only rewrites rows at its own presets' addresses) and guards a start-up failure, so it ships now.
- Merge in `updatedUserServers`: every preset directory of the group's operator matched by address to the group's stored rows (kept as stored, so a renamed preset keeps its stored name, as relays do) or new, plus the group's stored custom rows: what `updatedRelays` does for relays (Operators.hs:434-447), so slice 1 turns its body into one function over a list's presets, an address accessor and the stored and new wrappers, which relays and directories both call. Grouping by `domains` likewise: `addChatRelay` (:516-521) becomes one function over a domains accessor and an add function, as `addServer` already is for servers (:510-513).
- Validation: `USEDuplicateDirectoryAddress {duplicateDirectory :: Text, duplicateAddress :: ShortLinkContact}` over the request's groups — so the settings screens can mark a duplicate. A request without directories carries an empty list, so it can't raise this error; no other user's directories are checked (other users get only missing-server errors today). No "no directories" warning: an app shows that note from its own data (section 4.3), which needs no new case in the apps' closed warning types and no "For chat profile X:" warnings about other profiles.
- A directory's name is normalised wherever app input reaches the core: the `APISetUserServers` and `APIValidateServers` handlers pass each requested directory's name through `mkValidName` (Commands.hs:6948 / 6968) before saving or validating, so a duplicate error names the directory as it would be stored; an empty result is stored as "", and the apps show "Unnamed directory" where the name is empty (not the address's host, which is its router and can look official, section 4.7). The name comes from the directory's own profile and is shown in the consent alert, so this bounds what a directory can put there (section 5.4).
- A command that sends a request only to a directory in use: `APISendDirectoryRequest {userId, address, requestTimeout, request}` (`/_directory_request <userId> <address> [timeout=<s>] <json>`) looks the address up among that user's directories (`sameShortLinkContact`), refuses with a command error unless it finds one enabled and not deleted, and otherwise sends the request to the address of the row it matched (`CTShortContact (CTLink storedAddress)`, since `sameShortLinkContact` compares servers by host and port only), as `/_service_request` does (`sendServiceRequestTo`, Commands.hs:1508-1509 and :5969 on master), answering with the same response, without parsing the request. The apps send every search through it; "Test directory" and "Test servers" keep using `/_service_request`, since a tested address may not be saved yet and they send no search text. It puts the "in use" half of section 3's invariant in the core, tested in Haskell, so a bug in how an app chooses directories can't send search text to a directory the user turned off or never added. `/_service_request` stays open for "Test directory" and for an older paired desktop of the search-only release (section 5.3), so the core doesn't guard those; making `/_service_request` also refuse an address that is one of the user's directories turned off would close the older-desktop case for ~20 lines, at the cost of refusing "Test directory" on a turned-off directory's screen (not planned). Undocumented, like the servers commands (in `undocumentedCommands`), so the generated bot API files stay the same.
- `copyServers` (Commands.hs:501-511) copies directories to a new profile as new rows, as it copies relays.
- The CLI view gains a "Directories" part in `viewUserServers` (View.hs:1668-1674).

Shared code, not copies (CODE.md: parameterise): the duplicate-address fold (Operators.hs:575-580) becomes one function over `[ShortLinkContact]`, used by the relay and the directory errors; the preset merge and the grouping by domains become one function each (above); all three are extracted in the structural slice with relays as their only user. The store's insert, update and delete-on-save keep one small function per table (different columns), as relays do.

No new response, store error or warning, and one new command, undocumented: the apps learn a directory's name from `APIConnectPlan` and test it with a `tools/list` request (section 4.3), so the bot API and its generated files don't change (AC7).

### 4.4 Search with several directories (boards 13–17)

- **Which directories.** Every network action (a search, Load more, a retry) first captures the active user id, the remote host (on the desktop only, which can control a phone; iOS has none) and the model's generation, then reads that user's servers (`/_servers <id>`, a local call) and computes from them the directories it will contact: a search, every directory in use; Load more, the search's directories still in use that have more; a retry, that directory if still in use. The same read drops the state (cursor, count, failure, rows held back) of the search's directories no longer in use, so their retry rows and their part of the load row's count go; an action left with no directory starts no load and no spinner. Right before sending, after any alert or none, it checks that the user, the remote host and the generation are still the captured ones and sends nothing otherwise (a profile switch from a notification tap, a reset); every request carries the captured user id rather than looking up the current user again. "Search in Directory" and the Search key use a model value refreshed when chat starts, the active user or remote host changes, and servers are saved (inside `saveServers`, which every save path uses: the Save button, the "Save servers?" alert on closing, the submenu's sheet); a stale value can only show or hide the row, never decide where text goes. If the fresh read finds no directory in use, nothing is sent.
- **Sending.** One request per directory, all at once, each with today's 10 s timeout (which the core starts after fetching the address's link data, so a request to an unreachable server takes longer). Each request is ep's envelope with an MCP `tools/call` of the directory tool, in one fixed shape: `{"protocol":"mcp","request":{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"simplex.directory.search","arguments":{"searchText":…,"searchCursor":…},"_meta":{"io.modelcontextprotocol/protocolVersion":"2026-07-28","io.modelcontextprotocol/clientCapabilities":{}}}}}`, with `searchCursor` only for Load more. The tool's contract keeps today's field names (`searchText` and `searchCursor` in; `entries`, `searchCursor`, `moreCount`, `pageSize` out), so the directory's paging and the apps' entry decoding carry over; it is the contract the services design proposes too, so the directory's work carries over to that design, which also needs the directory to declare `protocols.mcp` in its profile (section 12). The directory lists the tool on the first page of `tools/list` and keeps its cursor under 1,024 bytes encoded, as that design's core requires. The `id` is always 1 and `_meta` holds exactly those two keys, so every device sends the same bytes apart from the text and the cursor; the request is unsigned, without `requestKey` and without MCP's `clientInfo`. A counter `id`, a key or the app's version would let a directory link one device's searches (draft :441-446). An answer counts as results only when it is the envelope's `response` holding a JSON-RPC result whose `structuredContent` reads as search results; an envelope error, a JSON-RPC error, `isError`, or anything else is that directory's failure. iOS sends each blocking call from a concurrent dispatch queue (`DispatchQueue.global`, not a serial one, which would send them one after another; the core runs each command on the calling thread and takes no lock for service requests, Mobile.hs:382-383, Commands.hs:1508-1509) rather than the cooperative pool (otherwise a few slow directories stall the app's async work for that long); Kotlin already sends on `Dispatchers.IO`. The sender knows nothing of directories (one request to many addresses through a command it is given, each answer or failure reported), so another role can reuse it (section 4.6.3).
- **State.** `OnlineSearchModel` keeps, per directory address: name, whether the user added it, cursor, count, loading, failed. The results reset on a profile switch in the chat list view, unchanged.
- **Order.** Your chats first (as built); then each load's results in settings order (the operators' directories in the order `/_servers` lists the operators, which the settings screens show too, then yours, each group in the order its directories were added), each in the directory's own order. `getServerOperators_` has no ORDER BY (Profiles.hs:861-870), so operator order is the stored order SQLite returns, unchanged by this design. A directory's rows appear once every directory before it in that order has answered or failed in this load, so results already shown don't move. The app gives each directory 15 s from the start of the load (its 10 s plus time to fetch the link): one that hasn't answered by then counts as failed, gets its retry row, and its late answer is ignored; so a slow earlier directory delays the later ones' rows by at most 15 s. Results are matched by link, as today (DirectorySearch.swift:40). A channel or a public group publishes one link in its profile, which every directory lists; an ordinary group has none, so each directory lists it with the group link it created itself (Listing.hs:175-180, Service.hs:1398-1405 at 4afce4931), and nothing in two entries tells the apps they are one group. So an ordinary group listed by two directories shows as two rows, each in its directory's place and naming its directory in the submenu (open question 15); the rest of this paragraph is about shared links. A link several directories list shows once, with the entry of the earliest directory in settings order: within a load the hold rule gives that for free; when an earlier directory lists, in a later load, a link already shown from a later one, the row keeps its place and takes the earlier directory's name, description, image and counts (Open goes to the same link). The result remembers every directory that listed it (for the submenu). One exception, as built: a result that is one of your chats joins your chats at the top. No sorting across directories (open question 6).
- **Cancel.** The spinner's Cancel: with one directory in use, as today (the request's answer is ignored; nothing new shows; a cancelled first search brings "Search in Directory" back, a cancelled Load more keeps its load row). With several, it shows the held rows of the directories that have answered, and gives each that hasn't its own row "[name]: no answer, tap to retry"; the same on both platforms.
- **One load at a time,** as today: a search, a Load more and a retry are each a load. A search with new text starts a new generation and replaces the running load, whose timers and answers are then ignored (DirectorySearchView.swift:52-66); Load more and retry don't start while a load runs (:69-81). Each request and each 15 s timer carries the model's generation, its directory and a request number; an answer or a timer whose number is no longer that directory's latest is ignored, so a request still running in the core after its 15 s can't overwrite its retry.
- **Footer.** The retry rows of a load appear when that load is complete (every directory answered, failed or past its 15 s), so they don't move as rows are added above them; while any load runs, earlier retry rows hide and the load row stays, greyed, as the designer drew for Load more, moving down as released rows are added above it (it can't be tapped while greyed). The spinner in the field follows the load, from its start until it completes or is cancelled. One retry row per failed directory, in settings order: with one directory in use, today's "Search failed, tap to retry"; with two or more, "[name]: search failed, tap to retry", which retries that directory's last request alone while the others' results stay (board 15). Then the load row, last, when any directory that hasn't failed has more: "Load more · N left" when only one directory has more and it sent a count, "Load more · about N left" when two or more have more and at least one sent a count (N their sum, saturated, summed in 64 bits on both platforms; "about" because a channel or public group listed by two is counted twice, though it shows once), "Load more" without counts (open question 5). A tap loads the next page from every such directory. The spinner appears after 1 s, as built.
- **Bounds.** At most 50 entries are taken from one response (the directory sends 10); the rest are dropped. Each kept entry costs a local connection plan, so this caps the local work one directory can cause per page.
- **SimpleX names.** A result's row shows the SimpleX name its entry carries (DirectorySearchView.swift:202-207, .kt:224-228 at 4afce4931); SimpleX Directory sends one only for a group whose domain it verified (Listing.hs:188, Store.hs:208-211), but a directory the user added can send any. The row shows the name only from an entry an operator's directory sent, and none from a user-added directory's entry (open question 16).
- **Consent** (board 13). The one "Directory search" switch in Privacy settings stays, device-wide. Beside it the apps remember the addresses of the operators' preset directories the user has agreed to: public addresses, the same for every user, never a directory a user added. A directory the user adds is agreed to by adding it or turning it on, on the screen that says what it receives. Before an action sends:
  - with the switch off: "Enable Directory search?" — "Search text is sent to SimpleX Directory and Your directory (added by you), each search separately and without your profile." — naming every directory the action contacts, the user's own marked "(added by you)"; Enable turns the switch on, remembers the preset ones and sends; Cancel sends nothing;
  - with the switch on, if the action would contact a preset directory not remembered (an app update presets one, the user turns a preset back on, or the switch was turned on in Privacy settings, which names nothing): "Search in these directories?" — "Search text is sent to [names], each search separately and without your profile." — naming only those; Search remembers them and sends to every directory of the action; Cancel sends nothing and leaves the results as they are;
  - turning the switch off forgets the remembered addresses, and every servers save (in `saveServers`, so every save path) forgets any remembered address that is not an enabled preset of the profile just saved, so a preset the user turns off, or a retired one the user deletes and a later version presets again, is asked about before its next search. Accepted: the set is device-wide and directories are per profile, so a user who keeps a preset on in one profile and off in another is asked again in the first after saving the second's servers.
  - a new profile copies the current one's directories, the user's own included and in use, as it copies relays (section 4.2). Agreement to a directory the user added belongs to the device, like the switch, so it covers the new profile, hidden ones included, without an alert; the new profile's settings list it. The alternative, copying user-added directories turned off, is in open question 4.

  Board 13's last clause, "so they can't build your search history", is dropped (it no longer holds: section 5.4). With one directory in use, the first alert is today's wording with that directory's name, marked "(added by you)" when it is the user's. If directory search ships a release before several directories (open question 3, recommended), a one-time step on the first start of the new version remembers exactly the address that release searched (today's `DIRECTORY_SERVICE_LINK`, kept as a literal in the step), only if the switch is on (that release already sent their searches to SimpleX Directory, whether they turned search on from the alert or in Privacy settings), and records in its own key that it ran, which turning the switch off doesn't clear, so the step never runs again. It records that on the very first start of the new version whatever the switch says, a fresh install included, so a later start after the user turns the switch on never remembers SimpleX Directory without a question. Accepted: a down migration drops the table while the remembered address stays, so after a downgrade and an upgrade SimpleX Directory comes back enabled and receives searches without a question, though the user may have turned it off before; a down migration loses every directory setting anyway, and that directory had received the user's searches before.
- **Submenu** (boards 16–17). With two or more directories in use, the long-press menu gains "Directories ›" listing the directories that listed the result's link (one, for an ordinary group), the user's own marked "(added by you)"; a tap opens that directory's settings screen in a sheet, which saves with `saveServers`, so it refreshes the row's visibility value and forgets as every save does. With one directory in use the menu keeps Open only (as built). It is also how a user sees where a result came from.
- **Remote desktop.** The desktop reads the phone's profile's directories through `/_servers` and sends each request through the phone's core, as today. Its consent switch and remembered addresses are the desktop's own.

### 4.6 Other services, and a service layer later

#### 4.6.1 What is generic today, and what is per kind

Generic already: the transport (a service request: one request, one response, a new connection each time, no profile), the bounds on a reply (the branch), the reply-queue choice. Per kind: where the address comes from (a constant in the apps for the directory, a core config value for badges, Chat.hs:74), consent, and the message shapes: three envelopes exist today (badges `{version, purchaseKey, request}`, the directory `{type:"search"}`, ep's draft `{protocol, request}`); this design moves directories onto ep's.

ep's direction makes a role a set of required tools and lets any service whose tools include them fill it. This design doesn't infer roles: the user puts an address in the Directories list, and it is a directory; "Test directory" then checks that it offers the role's one tool. It configures each kind where its nature puts it: directories are many and chosen by the user, so they are a list per operator and under Your servers; a service with one receiver per operator is an operator setting; a service of the app vendor alone (badges) stays a core config value.

#### 4.6.2 Telemetry in this design

- Configured: ep named telemetry but not its receiver. Assuming each operator that wants it receives its own: it presets one telemetry address in its `PresetOperator` (not user-added, so no list); the user turns it on per operator on the operator's screen ("Send usage statistics", off by default), stored as one more column of `server_operators`, which is device-wide like the operators themselves. A sketch of that screen is on the page. If only the app vendor receives it, it sits where badges do (section 4.6.1): one address in the core config and one switch in Privacy settings, at about the same cost.
- Run: a core worker, like the badge retry worker, sends an unsigned service request to each consenting operator's address at most once a day at a random time, with aggregates only (app version and platform, feature switches, counts in coarse buckets), no identifiers, each time on a new connection. In ep's envelope, it would be an MCP `tools/call` of a telemetry tool, as search is.
- What the operator can learn or link: the request carries no profile, but its reply queue is on one of the user's servers (a self-hosting user names the same host every time), and a rare combination of buckets can single out a device; a request needs one profile's servers, so the worker must use the same profile every time or the operator could correlate profiles. For a default device every reply queue is on a SimpleX Chat server (section 5.4), so if SimpleX Chat receives telemetry it can link each report to the device's session; keeping reports away from the receiving operator needs a simplexmq change in which the agent routes and refuses a request by operator (the services plan's sketch, ~600–1,000 lines, its own plan in simplexmq). These hold in any design, and that change is a prerequisite of telemetry in either.
- Before any of this: the privacy policy, which the core shows as the operators' usage conditions, says the apps "should not include any tracking or analytics code" and "must not send anything not directly required for users communications without explicit users' consent" (PRIVACY.md:201, :203). Telemetry needs that text changed, a new conditions version users review, and explicit consent, whichever design carries it.
- Cost here: ~500 core lines (preset field, a column and migration, the worker, the payload, tests), ~200 per app (the switch, its alert), the policy change, and the simplexmq change above. A services list doesn't reduce this: consent, payload, routing and policy are the cost.

#### 4.6.3 Moving to a service layer after this ships

If ep later picks services, as the services design plans them (section 12: services in each operator's servers and under Your servers, each with its tools and the roles the user turned on), from this design:

- Kept: the stored rows (one migration copies `directories` into a services table: nothing references them), the start-up pass and merge (they work for any kind configured per operator), validation, the search (fan-out, per-directory state, order, retry rows, load row, consent naming each receiver, submenu, bounds), the screens' places, and the request format: the apps already send ep's envelope with the same tool contract, and "Test directory" already reads a service's tools.
- Changed or added: the "Directories" sections and the New directory screen become "Services" in the same places, with a switch per role and the roles a service can fill (~200 lines per platform); each service's tools and roles are stored, and the migration seeds them without contacting anyone (a preset takes its preset's tools and every user-added row the directory tool, since it was already being searched; each gets the directory role if it was in use; a user-added row's tools change afterwards only when the user tests it); the apps pick a role's services by their tools (~100 per platform); CI adds its test directories through the renamed screens (~100 per platform); the `directories` key in `/_servers` stays a release beside a new key, for older apps and remote desktops, with the migration and tests (~600 in the core).
- Cost: ~1,400 lines, ~800 in the apps and ~600 in the core, keeping this design's "Test directory". If ep also wants the core to build and check every request, as the services design does (one parser, and the core refusing a call to a service not in use for its role), and its "Test service", which requires the address's profile to declare `protocols.mcp`: add the `protocols` key and its MCP client in the core (~700 lines: its plan gives ~1,000 for those and the bot helper, which is ~300 here and already built), its role call (its slice B4, ~200 lines by our estimate), and remove this design's ~150-line request command and the apps' request code (~150 per platform): ~1,400 + 700 + 200 + 150 + 300 ≈ 2,750 changed lines in all (removed lines count as changed, as in every estimate here). A directory added or re-tested after that move must then declare the protocol in its profile, which a core without the key can't publish (`toChatPrefs` drops untyped preference keys, Types/Preferences.hs:539-550); migrated directories keep being searched, since that design's role call reads their seeded tools, except that under its rule directories of an operator whose servers are off stop being searched (open question 9). Had the apps kept today's request, the move would also keep both request forms in both apps for as long as any directory a user added spoke only the old one (~150 lines per platform, with no end date), and every directory operator would implement the protocol twice.

Choices in this design that keep the move cheap:

1. Storage: a table nothing references, whose row (address, name, domains, preset, tested, enabled) is a service row without its tools.
2. API: `directories` optional both ways (`ListDef` in responses and requests), so a later key can sit beside it and old apps ignore it.
3. Protocol: the apps speak ep's envelope with MCP to every directory from the release that lets users add them, so no directory anyone builds speaks a SimpleX-only request; the core stays unaware of the search JSON and only bounds bodies.
4. Discovery: "Test directory" asks the directory for its tools; when the core reads ep's `protocols` declaration from link data (his draft, :124-171, planned), it can check that first, without a request.
5. The apps' sender is role-agnostic: it takes the command it sends through as a parameter (section 4.4).

#### 4.6.4 What to include now

In the plan, because it is what keeps the move cheap once users can add directories: **directories speak ep's envelope with MCP** (open question 13). From the release that lets users add directories, the apps send each search as `{"protocol":"mcp","request":<tools/call of "simplex.directory.search">}` (section 4.4), and "Test directory" sends `tools/list` and checks that the directory offers that tool: ep's role-by-tools, for this one role, with the role chosen by the list. SimpleX Directory answers both this and today's request (slices 4a and 4b, pull request 2, deployed before the apps ship). The tool's contract is ep's to change before pull request 2 merges.

Also in the plan, at about the same size as handling the envelope inside the directory: **the Service RPC half of the bot helper ep's draft plans** (agent-protocols.md:459; the draft's helper also serves the conversation transport, `/_call mcp`, which stays planned). Slice 4a puts the envelope, `server/discover`, `tools/list`, `tools/call` dispatch and the draft's errors into a library module for bots (`Simplex.Chat.Bot.MCP`, as the services design also proposes) rather than into Directory/Rpc.hs, so SimpleX Directory is its first user and a telemetry receiver, or any bot, its next.

Not now: a generic services table or a `tools` column (nothing would read them; later it is one migration, and the rows to migrate are seeded without contacting anyone, section 4.6.3); the core's `protocols` declarations (planned in the draft; "Test directory" asks the directory itself meanwhile); the core building and checking MCP requests, as the services design does (section 12); telemetry (the policy change, and a simplexmq change, come first: section 4.6.2).

Free now, and in the plan: the role-agnostic sender (given the command it sends through), the optional settings key both ways, and a core that doesn't know the search JSON.

### 4.7 Alternatives considered

- **The service layer first** (the services design, compared in section 12): services stored in each operator's servers and under Your servers as this design stores directories, each with its tools and the roles the user turned on; a role filled by namespaced tool names; the core building and checking every request. It pays when several kinds of user-chosen services are coming; telemetry is not one (section 4.6.2).
- **Today's request kept, with a version field** (open question 13, option b): no dependency on ep's draft, but every directory anyone adds speaks a SimpleX-only protocol, and a later move keeps both forms in the apps (section 4.6.3).
- **Only preset directories until the envelope is final** (open question 13, option c): no protocol commitment, but adding a directory (boards 11–12) waits, and with SimpleX Directory the only preset, several directories change nothing until another operator presets one.
- **One list on screen, separate storage** (plan 015's B1): this design's core, plus a kind per row and merged screens nobody has drawn.
- **Presets in config only, overrides stored** (the round-1 review's suggestion): the table holds the user's own directories plus, per preset address, the user's on/off; the readers (`APIGetUserServers`, validation, `copyServers`, new-profile setup) join config presets with stored rows at read time. Adopt, retire, the start-up writes and their unique-index failure class disappear; an older binary changes nothing; a user's own directory that a version presets becomes theirs again when dropped. Rejected for now: presets would work two ways in one codebase (relays stored at start-up, directories joined at read time), which is worse for the next reader than either way alone; the right change would move relays too, in its own pull request.
- **Directories in `chat_relays` with a kind column:** one table, but one type for two business concepts, and every relay query filters by kind; relays are referenced by groups, directories by nothing.
- **App-local storage:** no migration, but presets duplicated in two apps, no per-profile lists, and a desktop connected to a phone would show the desktop's list for the phone's profiles.
- **No core check of where a search goes** (the apps alone choose the directories): ~150 lines fewer, but the main privacy rule would rest on Swift and Kotlin code that has no unit tests; rejected in favour of the request command of section 4.2.
- **A core command that searches every directory**, returning at once and reporting each directory's answer as an event: it would fix the iOS thread issue once and could apply the in-use rule in the core, but adds a command, an event and their cancellation (Cancel, per-directory retry) to the core's API and its docs, while the apps still keep per-directory state; the apps' sender is ~40 lines per platform.
- **A core `APITestDirectory`** like "Test relay": the core would learn the request's shape (open question 7).
- **`getUserServers` returning a record:** clearer than a 5-tuple, but a structural change to every caller for no behaviour.
- **The host beside a user-added directory's name:** rejected: a link's host is its SMP router, by default SimpleX Chat's or Flux's, so it would make a look-alike look official; "(added by you)" says where it came from.

## 5. Compatibility and security

### 5.1 Protocols

The chat protocol and the agent are untouched. The apps' search request changes from today's `{"type":"search"}` to ep's envelope with an MCP `tools/call` of `simplex.directory.search` (section 4.6.4), which every directory a user adds must answer; SimpleX Directory answers both, so the apps of the search-only release keep working. This makes ep's draft, at MCP revision 2026-07-28, the protocol of directories: a later change to the envelope or the tool must stay compatible or be versioned (MCP names its revision in `_meta`; the directory answers -32022 to one it doesn't serve and lists those it does).

The protocol is the draft plus one thing it doesn't yet say. The draft has a request and a response "SHOULD NOT exceed 10,000 bytes of JSON" (agent-protocols.md:270). On the search branch the core compresses a larger service body, marked by a leading `X`, up to 10,737 bytes compressed and 64 KiB decompressed, with JSON nesting up to 32 (Protocol.hs:1066-1110 at 4afce4931), and SimpleX Directory fits each page to that bound (Rpc.hs:93), so its answers can exceed 10,000 bytes of JSON. The core compresses and decompresses on both sides, so no bot or app sees it, but a directory written against the draft alone wouldn't expect it. Recommended: the draft gains a paragraph on it (the marker and the three bounds) before pull request 2 merges (open question 13). Otherwise other directories are asked to keep their MCP answers under 10,000 bytes of JSON, and SimpleX Directory keeps its compressed pages (the draft says "SHOULD NOT", and a 10,000-byte fit would drop most group pictures from its results, since one near-limit picture doesn't fit alone).

### 5.2 Database

One migration, `M2026MMDD_directories`, dated after the newest migration on master and on the branch when the core pull request starts (today: SQLite `20261018_autoincrement_ids`, Postgres `20261016_badge_store_receipts`; the branch adds none), up and down, SQLite and Postgres, registered in both Migrations.hs and simplex-chat.cabal. No backfill: the preset arrives through the start-up merge. While unreleased, the migration is edited in place; once a release ships it, a change (a consent column, or a services table later) is a second migration.

### 5.3 Older and newer apps and cores

- An older app (or an older desktop's command through a newer phone's core) sends `/_servers <json>` and `/_validate_servers` without `directories`: the core parses an empty list, saves no change to directories, and returns no directory error (AC4).
- An older phone's core answers a newer desktop's core: no `directories` key; `ListDef []` parses (AC4's JSON test). The desktop shows no directories for that phone and can't search through it, until the phone updates. If the core pull request lands before directory search is released, that release's phones already answer with directories and SimpleX Directory preset, so this case can't arise with any phone that has directory search.
- A newer core answers an older app or an older desktop's core: the key is ignored. A newer desktop saving through an older phone loses directories silently (the phone ignores the key); harmless.
- An older desktop of a search-only release, connected to a newer phone, still sends every search to the address built into it, in today's request, through the phone's core, which can't tell a directory search from any service request: SimpleX Directory receives that desktop's searches even if the phone's user turned it off. The desktop's own consent still applies. Until the desktop updates. Exists only if directory search ships before several directories (open question 3).
- Apps of the search-only release send today's request to SimpleX Directory, which keeps answering it; a directory a user adds is contacted only by newer apps, so it needs only MCP. A SimpleX Directory not yet redeployed with pull request 2 fails every search of the newer apps (section 8).
- The apps decode `directories` with their normal decoding (Swift synthesized; Kotlin default `emptyList()`): an app only ever reads its own core, which always sends the key (a desktop's core re-encodes a phone's reply with it). They add `duplicateDirectoryAddress` to their closed error types in the same release that the core can send it.

### 5.4 Threat model

Who can do what, and what bounds it. Today's only directory is the SimpleX Chat operator's; this design lets a user add any address, so a directory is untrusted.

| Adversary | What it can do | What bounds it | Test |
|---|---|---|---|
| A directory the user added | Receives every search text, unsigned, without a profile, with a reply queue on one of the user's servers; may store the texts (the SimpleX Directory policy says it stores search requests, PRIVACY.md:126) | The New directory screen says what it receives; it is named "(added by you)" in the first alert; turning it off stops it at the next action (each action re-reads the servers); every request has the same fixed shape (`id` 1, no `requestKey`, no `clientInfo`), so nothing in it links one device's searches | `testDirectoryRequest` (the core refuses a search to a directory turned off or not in the list); runner: the first alert names both test directories; after A is turned off, Load more on a search that included A, a retry of A's failed request and a new search send A nothing (A's log); the request's shape by review |
| A hostile reply | A large, deep or malformed body; hundreds of entries; a huge count; bad links; any image up to the body bound (decoded with no dimension check, the same exposure as any profile image today); an envelope or JSON-RPC error | The core: ≤ 10,737 bytes compressed, ≤ 64 KiB decompressed, depth ≤ 32; the apps: anything but results is a failure, entries decoded one by one, bad ones dropped, ≤ 50 taken, counts clamped and summed without overflow, only group and channel links; "Test directory" reads at most 3 pages of `tools/list` | the core's parser tests; the apps' decoding, cap and sums checked by review (the apps have no unit tests for this, by the team's choice) |
| A slow directory | Holds a request; under the hold rule delays later directories' rows | At most 15 s from the start of the load, then its own retry row | runner: one test directory stopped (it fails on the core's own timeout); the 15 s deadline by review |
| A fast directory | Answers first to put its claims (name, description, image, counts) on channels another directory lists | The earliest directory in settings order wins for a shared link (channels and public groups); the operators' directories come first. An ordinary group has a link per directory, so a second directory's entry is its own row, in that directory's place, naming it in the submenu | runner: a shared channel described differently by the two test directories; a shared ordinary group shown twice |
| A look-alike | A user-added directory calls itself "SimpleX Directory"; it lists a channel named like a known one; it attaches a SimpleX name to a result; a service that isn't a directory lists a search tool | Names normalised by `mkValidName` (≤ 50 characters, no direction-changing or format characters); "(added by you)" in the alert and the submenu; the submenu shows who listed a result; a result's SimpleX name shown only from an operator's directory (section 4.4, open question 16); the directory tool's namespaced name, so a bot with its own search tool fails "Test directory" | `testGetSetDirectories` (normalised name); the name rule by review |
| The directory's own server | Sees the user's IP when it fetches the address's link data or receives the request, if private routing doesn't cover that server | The user's private-routing setting: by default "always" through a proxy; on iOS that is the default only since 2026-10-21 (3126d9b54), and iOS users who saved network settings before keep "unknown servers", under which a request to a server in their list, SimpleX Directory's included, goes directly | none (documented) |
| A directory, at Open | Lists a link of its own making (a different one per search, say), so the link-data fetch at Open, from its server, ties that search to the Open | Open is the user's action; the fetch goes through private routing as above, so the server sees no IP by default; nothing is fetched before Open (DirectorySearchView.swift:118 at 4afce4931) | none (documented) |
| Colluding directories, or a directory and a server operator | Link one search across directories by text and timing; link a self-hosting user's searches by the reply queue's host. With default servers every reply queue is on a SimpleX Chat server (Flux's servers don't store by default, Presets.hs:42), so SimpleX Chat, which runs SimpleX Directory, can link each search to the device's session on that server; and on some default devices the proxy to SimpleX Directory's server is SimpleX Chat's own too (the services plan estimates about 4 in 7), so it also sees the IP address | Not bounded: the alerts promise only "each search separately and without your profile"; the fix is a simplexmq change (reply queues on their own transport session; count the target's operator as used), proposed by the search review, not planned (open question 14) | none (documented) |
| Another app or a backup on the device | Reads app preferences | They hold the switch and the operators' public directory addresses only | none |
| Many directories | Each search opens one connection and one reply queue per directory | The user adds each directory; no cap planned (open question 11) | none |

## 12. Comparison with the services design

From the services design's plan as of 2026-10-22 22:04 UTC (/workspace/shared/directory-search/several-directories/services/plan.md; its page https://claude.ai/artifact/493JgCBa4ZCLZQXwAQpVQT). - **The same in both:** directories in each operator's servers and under Your servers, SimpleX Directory preset, one search to every directory in use, a retry row per failed directory, the alert naming each directory; consent in the apps (the switch and the alerts); storage like chat relays with the start-up merge; older apps and remote desktops; directory search shipping first; board 13's clause dropped; ep's envelope with MCP 2026-07-28, `id` 1 and no `clientInfo`; the same tool contract (`simplex.directory.search` with today's fields); the directory answering both request forms, through a bot helper; search linkability left to a simplexmq change.
- **What makes a directory:** here, an address in the Directories list, checked once for the directory tool; there, a service whose stored tools include the directory tool and whose profile declares `protocols.mcp`, with a switch per role.
- **Who checks where a search goes:** in both, the apps ask for consent and the core refuses a search to a directory not in use in that profile, so a bug in choosing directories can't send search text to a directory the user turned off: here through the request command (section 4.2), which looks the address up and sends the apps' request as it is; there through its role call (role on, tool present, operator enabled), which also builds and reads every request in the core, with one parser, through two new commands.
- **What users see that differs (policies either design could adopt):** remembered consent: there, plan 015's list, which keeps every directory named when the user tapped Enable, user-added ones included, and asks again for any not on it; here only the operators' presets are remembered, and adding a directory is its consent (section 4.4: user-added addresses would otherwise sit in app preferences outside the encrypted database); result order: both in settings order (boards 14–15), but here a directory's rows wait for the earlier ones, up to 15 s, and a shared link takes the earliest directory's entry, while there results show as they arrive, without a hold (its section 5), and a shared link most likely keeps the entry that arrived first (its slice C1 says only "merge and dedupe by link"; the rest is our inference from today's dedupe); there, turning an operator's servers off also turns off its directories, enforced in the core (open question 9 here recommends the opposite); at most five services per search there, no cap here (open question 11); the host shown under a service's name there, rejected here (section 4.7); SimpleX names from user-added directories hidden here (open question 16), not addressed there; the submenu in the first release here, in a later one there (its slice C3).
- **What ep's draft must settle first:** here, the envelope and MCP binding, the tool contract and the compression paragraph (section 5.1); there, the same, plus the `protocols` profile key (still "planned" in the draft). Both propose the compression amendment to the draft; that plan also proposes the role-naming rule and no `clientInfo`; both have fallbacks if ep declines (here other directories keep their answers under 10,000 bytes; there the rules live in code comments).
- **First release with several directories, submenu included:** here ~4,950 lines (core ~1,050, directory ~600, iOS ~1,700, Kotlin ~1,600, CI included); there ~5,400 (core and bots ~2,500, apps ~2,900; ~5,000 without its submenu; that plan notes its app figures may be low by a few hundred).
- **Statistics:** both need the privacy policy changed and a simplexmq change that keeps reports away from the receiving operator (that plan's sketch, ~600–1,000 lines); here an operator setting, ~900 lines; there a role with its switch in Privacy settings, ~900 lines.
- **Later:** here, moving to services as that design plans them is ~1,400 lines, or ~2,750 with the core taking over requests and the `protocols` declaration (section 4.6.3); a directory added or re-tested after that move then has to publish the declaration, which a core without the key can't (`toChatPrefs` drops untyped preference keys, Types/Preferences.hs:539-550); migrated directories keep being searched, as that design's role call reads their seeded tools, except those of an operator whose servers are off. There, nothing to move.
- **In short:** two things decide. Whether more kinds of services users pick from a list are coming: ep wrote that the layer should run "all the other services we need", starting with telemetry, which this design assumes is one receiver per operator, not a list. If such services are coming, the services design costs less in total (~5,400 lines against ~6,350–7,700 for this design and the move); if not, the two are about the same size now (the ~450-line gap is inside both estimates' error), and this design is simpler and changes no profile format. And whether the core should also build and read every request, with one parser (the services design), or only check where each goes, the apps building and reading requests in Swift and Kotlin (this design).
